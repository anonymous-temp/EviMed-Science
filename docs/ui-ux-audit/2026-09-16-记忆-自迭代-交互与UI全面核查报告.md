## 2. 自迭代（学习回路）

### 2.1 设计一览

`feedbackEvents`（反馈事件）→ `distill` 作业（`methodDistillationRuns`，在项目自己的容器里跑 `method-distillation` 内部能力）→ `learningService.createCandidate`（**永远** `candidate`，生成者无法给自己盖章）→ 夜间 `consolidate`（`methodConsolidation`，SkillPyramid）→ 配对评测（`learningEvaluation`，`OPEN_SCIENCE_LEARNING_EVALUATION_COMMAND`）→ `approve` 重算 `promotionVerdict` → `learnedMethodMount` 只挂 approved → `methodObservations` 按交付项计数 → 贡献度 / 退休提议。`POST /api/methods` 让研究者自己写方法（显式来源立即生效）。

### 2.2 生产实况

| 计数 | 值 | 含义 |
|---|---|---|
| `documents` 中 `learned-method` | **0** | 从未蒸馏出任何候选 |
| `jobs` 中 `distill` / `consolidate` | **0 / 0** | 触发器从未点火 |
| `feedback_events` | 92，全部 `memory-inference-accepted` | 记忆接受，不是交付反馈 |
| `deliverable-adopted` / `deliverable-edited` | **0 / 0** | 见 2.3 |
| `LEARNING_EVALUATION_COMMAND` | 已配置（method-release-v1，hold-out） | 但一次评测 = 100 briefs × 2 臂 × 3 重复 |
| 学习窗口 | 22:00–09:00，`TZ=Asia/Shanghai` 已生效 | 09-15 修复 |
| 观察计数（`recordObservation`） | 无 approved 方法，故为 0 | 死锁只有评测台的 `trialMethodIds` 出口 |

### 2.3 为什么是零

1. **触发器 (a) 采纳/编辑交付物没有生产者。** 服务端 `POST /api/feedback/events` 在（`server.mjs:2534`），客户端 `reportWebDeliverableFeedback` 在（`apiClient.ts:1346`），**没有任何页面调用它**（子任务确认它是 12 个无引用导出之一）。运行记录页有"复查与复现 / 打开对话"，没有"采纳 / 我改过这份"。
2. **触发器 (b) `repair_accepted`** 要求 `status=succeeded` 且至少一轮修复且 `transcript.completeness=complete`（`server.mjs:1490-1494`）。生产近期运行以验收与评测为主，多数失败或被门禁退回；评测账号显式排除；且 09-16 之前"完整"是谎报的（子会话未被发现），之后会更少标 complete。
3. **触发器 (c)** 记忆推断被接受只在 `memory-value-edited` 配对时产生 lesson（`feedbackEvents.mjs:395-410`），生产里没有编辑事件。

### 2.4 结构性缺口

- 研究者看不到方法：没有方法页，`/api/methods` 只有 HTTP；候选、试用、晋升、退休、回滚全部不可见。
- 外部 agent 无法回报观察（"挂了哪个摘要、成没成"），所以回路外放只能是半个（09-15 方案 §三.3）。
- 蒸馏语料在 a48c91c2 之前缺主体（子会话不在转录里）；已有的 26 份评测转录不能作为训练材料。
- 贡献度公式 20 条轨迹起判、账号活跃上限 50：在今天的运行量下多年到不了阈值。

### 2.5 判断与建议

回路的每一段代码都在，且几个"结构上不可能"的性质（生成不能自批、只挂 approved、评测台是唯一试用口）有变异测试钉住。但按原则 11，它今天没有一条实测证据。最便宜的启动顺序：① 运行记录页给交付物加"采纳 / 我改过"两个按钮（触发器 a 的第一个生产者，也是 UX 上本来就该有的）；② 用真实账号跑 3–5 次会经历修复的运行，看 `distill` 是否入队、候选长什么样；③ 再决定配对评测的规模（100 briefs 是发布判据，不是首次观察的规模）。

### 4.2 结论

- **可行**：内核 45 个包全部 MIT；品牌包 README 明说"a deployment with its own brand composes a different package into the same slots"，我们做的正是这件事，不碰 `node_modules`，不改 DOM。
- **应当**：DeepSeek 开放平台服务条款 §5.2 "Without our permission, you or your end users shall not use any trademarks … including 'DeepSeek'"，§5.3 禁止把其名称/标志放在显著位置暗示合作。条款**没有**署名或 "powered by" 义务。换掉他们的标不但允许，而且是不持有其商标授权时的正确默认。
- **合规边界**（我的理解，请法务确认）：换标不等于隐瞒底层模型来源；生成式 AI 备案材料与用户协议里应如实写明使用的模型，产品界面无需展示对方标志。

### 4.3 剩余四处的改法

1. 帧文档标题与图标：在 `runtimeUiShell.apply` 里设置 `document.title = 'EviMed 研究会话'` 并替换 `<link rel="icon">`——与现有注入 `<style>` 同一类"仅呈现"的动作；webmanifest 可忽略（只在把帧当 PWA 安装时可见）。
2. 顶层打开帧地址：二选一——`runtimeUiShell` 不再在 `parent === self` 时早退（同样应用品牌与语言包），或控制面对非嵌入访问的帧请求答一页"请从 EviMed 打开"。前者改一行，后者更严。
3. `UsageCard.tsx:35`："按模型供应商价目折算"。
4. 折叠区与运维台的模型 id、检查名保留（排障需要），但把标签写成"模型"而不是裸 id 放在首位。
