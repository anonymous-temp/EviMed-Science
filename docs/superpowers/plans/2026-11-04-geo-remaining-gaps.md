# GEO redesign: remaining release gaps

The November 3 Profound-based specification remains the acceptance target. This document records work that was investigated but is not established by the current candidate. A fixture walkthrough, an isolated DSH conversation, CI, main integration and deployment are different evidence.

1. **Project goal, selections and memory.** A versioned/CAS goal implementation was prototyped and excluded from the candidate: appending the context to a user message makes the pinned OpenViking capture plugin merge it with the user's text, after which the memory gateway discards the entire message. The same limit applies to the existing GEO plan-selection and result-revision blocks. The revision block is now registered as platform context so it cannot be mistaken for a user's memory; until the transport is changed, a captured message carrying either block is withheld in full, including the user's own words. Text-only tag removal also cannot distinguish a literal user-written tag. A producer-owned, separately injected context needs a request/session-bound durable proof, exact revision and membership checks, observable failure and a recovery protocol that preserves input when the pinned kernel has already claimed it. Verify owner and shared sessions, queue/steer, attachments, retries, revocation, stale versions, restart and the user's actual memory before exposing persistent project context or claiming that these selected turns are learned.
2. **First-open native initialization.** Scoped navigation waits for its exact retained session. The scoped transport now holds the real workspace stream until the native client has retained that root; other streams continue, buffering remains bounded, and a timeout is visible and retried with a fresh frame. In an isolated pinned DSH + Chrome run, cold open, reload with the same session, a saved assistant response, and an intentionally delayed session-list timeout followed by retry all produced zero native `session/create` requests. One shared editor also opened the project and lost history access after revocation; a missing owner primary required the owner's explicit retry first. This does not establish every shared-member or child-session scenario. The scoped frame now receives only the platform's fixed, read-only chat presentation via an exact HTTP settings read, with membership and generation checks; the kernel's settings document and all settings writes remain denied. In Chrome, the client accepted the fixed schema, grouped an in-progress tool step while an intentionally blocked settings read left the step flat, and opened a synthetic link in a new tab with its network request intercepted. `settings/mutate`, command/skill discovery and GoalBar continue to return scoped 403s in the isolated trace. The denied catalogue requests identify a session or agent; the GoalBar request was a read. The pinned client uses these catalogues for slash and skill-reference suggestions; an initial rejected GoalBar read has no snapshot and leaves the bar hidden. A synthetic keyboard exercise showed no visible slash/skill suggestion, but does not prove every local slash command fails. Determine their supported access without widening authority.
3. **Action-to-article completeness and concurrent placement.** The article catalogue and safety-review list search and page the project with a snapshot check and exact article deep links. For action derivation, `GeoSpine` now checks complete bounded reads of articles, choices, active errors, orders, owned links and sources (up to 10,000 each), and bounds the associated citation read; exceeding a bound produces an explicit error rather than treating a truncated list as complete. Other legacy callers retain their previous limits, other spine inputs still lack a count bound, and separate reads are not one transactional snapshot. Independently, the market can read skip/source choices and then read newly registered or reassigned articles as candidates; those articles were not in the earlier expanded choice IDs and could be planned despite the choice. The market's project lock does not cover choice writes or article registration, and reserving an order occurs in another transaction. Existing order recovery runs separately and must remain available. No real placement was made in this investigation. A nonblocking shared-lock prototype was withheld because its transient refusal can exhaust the current in-process import retries, leaving a delivered file or saved card without its GEO article registration. A separate durable-intent prototype has not been wired into production: it does not yet preserve all importer fields and update semantics, durable version proof after restart, exact plan outputs, or user-visible failure and retry. Design an atomic choice/candidate protocol with durable idempotent repair, then test registration and reassignment while a market tick is paused, skip/source changes, existing order recovery, and action-to-exact-version navigation beyond the old boundary.

   Market decision, funding and reconciliation inputs now use bounded complete reads instead of silently using a prefix. Existing plans outside the first 5,000 candidate media are checked by exact media key before withdrawal. New articles can additionally consider their explicitly preferred outlet by exact verified domain or host outside that window, subject to the same gates and bounded complete read; a display name cannot impersonate the chosen domain and the outlet is not offered to unrelated articles. Hostnames use the same IDNA/public-suffix rules in the domain and server, including private suffixes and historical keys. A person with edit access can request a bounded, throttled recheck of the selected catalogue source; temporary read failures retain the previous evidence, and explicit source vetoes are combined across host and canonical records. A planned order cannot be newly sent on a missing or incompatible domain proof; the order remains planned with a visible recovery reason, while accepted and unknown orders retain their recovery path. Invalid proofs no longer occupy the entire send batch, and catalogue rechecks advance past invalid or temporarily unreachable rows. The final permission/choice read and shared media write are not yet one transaction. A newly created supplemental plan does not persist its special freshness requirement, so an already planned order can outlive the proof before a later send; do not treat this as fixed by the new preview or recheck. When a required 10,000-row bound is exceeded or the supplemental read is interrupted, the affected project's current tick fails closed, including its existing planned submissions; poll, publication verification and settlement do not yet have durable advancing cursors beyond that limit. The worker's incomplete-project diagnostic covers the named capacity error and recognized English statement timeouts; other PostgreSQL cancellation messages are a generic interrupted-read error and do not name a project. Capacity project identifiers are restricted to operator-authorized metrics and retained only for the current process's latest tick. Earlier successful independent reconciliation writes are not rolled back by a later capacity error. General new-media ranking still uses its first 5,000 rows; no production-scale performance test is implied.

   A further isolated PostgreSQL prototype exercised 21 cases, including mixed workers, atomic media replacement, preserved article version/digest, competing orders, long transactions, recovery and attempts to forge the decision. It is not product code. A safe implementation still needs an internal trusted producer for the exact action, skip, medium and article-version decision, complete dependency tracking and bounded retention, a mixed-version migration fence, and a visible recovery path for legacy planned orders without a retained article-version digest. The existing database role does not by itself distinguish a trusted decision producer from another control-plane SQL caller. The prototype does not establish vendor or user-interface acceptance. Bound run imports and preserved-output refreshes now report incomplete discovery or missing snapshots instead of silently calling the capped 64/20/128-path prefixes complete, and retain the ordinary readable artifacts. Their scope is the recorded inventory or selected business candidates; upstream inventory completeness remains unknown, and repeated refreshes do not page beyond the cap. Those receipts are currently available to the server/API only: the existing refresh API has no frontend caller, and an automatic import failure has no durable user-facing recovery state. A persistent import queue, trusted original-output capture, complete correction/version reconciliation and restart sweep remain unimplemented.
4. **Analysis and journeys.** All registered views retain a business area, but several remain separately selected analyses rather than a single integrated metric or dimension within the original chart. Validate every view's filter, selection, export and return behavior against the approved mapping. The visibility overview now pairs its trend with a competitor comparison from V08's actual eligible cohorts, preserving selection/digest across pages and distinguishing historical names; unrelated cohorts are not ranked. In isolated real PostgreSQL and Chrome, a 20-competitor synthetic project exercised the second page, historical rename and return to its time/engine filters. The first-diagnosis prompt is suppressed when existing observations or a scoped selection do not prove the project is unstarted. M-13 keeps the historical P1/P2 mention-rate formula and ID but is now labelled as a dimensionless ratio, not a user conversion rate or a universally positive target; the analysis and exports disclose its interpretation. The platform's existing three-control-group minimum and unmeasured-noise default remain implementation limits, not proof of causality or delivery acceptance. A local synthetic project was created, a real DSH + DeepSeek response was saved, and a synthetic file was uploaded, parsed and read by DSH. This does not establish the three complete specification journeys: real diagnostic sampling and failed samples, article generation/revision/version/publication, and scoped finding-to-task-to-return. The consumer-AI probe and social collection services were outside the authorized available test environment.
5. **GEO skills.** A private 3.1.0 archive was found in another local worktree and its archive digest, tree digest and 51 names match the previous handoff. A read-only inspection of the configured Tencent runtime base image found the installed 3.0.1 tree and verified its 285 files against its stamp; it has the same 51 skill names as the unreleased 3.1 candidate, but all 51 bodies differ and 89 files exist only in the deployed tree (including 43 Python and 38 YAML files). The candidate cannot be assumed to replace it without reconciling those dependencies. The inspection did not establish every possible project-specific runtime override. A separate unreleased candidate repairs a number of conflicting legacy instructions and broken resource references. Five isolated DSH + DeepSeek synthetic cases loaded four skills: question grouping, correcting an unverified screenshot, unknown label scope, undiagnosed medication use, and the distinction between literal disease names and an approved broader concept. The last response overstated a classification requirement; two subsequent instruction changes have not been rerun because the disposable Docker filesystem ran out of space before the next project was created. These narrow cases do not validate other branches, the other 47 skills or all clinical facts. The committed release receipt still binds 3.0.1; the candidate is not part of the public repository or established on the build host. This layout iteration has not independently revalidated all 51 deployed GEO skills or their actual runtime versions and tool grants. Do not label the redesign or its visual walkthrough as skill acceptance.

   The removed standalone probe, monitoring and distribution scripts are deliberately retired in the candidate and must not simply be restored. The candidate's workbook, cross-artifact and proposal checks still lack a verified one-to-one hosted validator; it now labels unavailable checks unperformed. Map each to a tested read-only platform operation or a separately tested pure validator before releasing the private pack.
6. **Clinical severity and judge comparability.** The GEO display and new notifications describe severity as potential clinical risk and do not claim a patient was harmed. S0–S4 is not an automatic NCC MERP patient-outcome category. Existing error rows with no recorded severity now show it as unknown in the list and detail; a mixed group keeps an individual ungraded row distinct. This display change does not alter judging, metrics or actions. A proposed clarification to the judge prompt was withheld: its hash changes the persisted judge version, while historical error aggregation and net-effect comparisons do not yet isolate judge versions. Before changing it, compare the old and new prompts on a frozen pharmacist-labelled corpus, examine changes across the S3 notification threshold, preserve version provenance and prevent incompatible judgments from being reported as comparable. Separately, an otherwise supported wrong verdict is currently discarded when its severity is missing or invalid; preserving it also changes accuracy and confirmation eligibility. A safe change must retain the existing evidence checks and explicit confirmation authorization, handle duplicate statements with known versus unknown severity, and distinguish the current assessment from the error record's highest known historical severity. Existing historical notifications are not rewritten by the new copy.
7. **Error confirmation authority and cutover.** Automatic confirmation now requires a separate explicit authorization bound to the current question-set version, engines, repeat count and project generation; the screen states the scope, maximum retries and that actual costs are unknown. Scope changes invalidate consent, and legacy records are not silently authorized. New workers persist a dispatch marker before an external confirmation ask, preserve accepted references, and stop an ambiguous dispatch rather than automatically sending it again; sample start and authorization use the PostgreSQL clock, while historical samples without a trustworthy start remain unknown. Isolated PostgreSQL, fake-provider and Chrome tests cover scope changes, role revocation, delayed acknowledgement, retries and crash recovery. No real consumer-model call was made for these tests. A historical confirmation with no dispatch marker can briefly display queued and stale counts when an unknown snapshot commits concurrently; the next lease refuses it and a later recovery stops it. More importantly, an older worker cannot enforce these safeguards. There is no database version fence: before any future release, stop and verify every older GEO worker and reconcile in-flight leases and accepted references as described in `OpenScience/docs/GEO_CONFIRMATION_ROLLOUT.md`. A rolling overlap is a release blocker.
8. **Runtime packaging.** The domain's browser-safe public-suffix implementation is a licensed, integrity-checked self-contained upstream bundle so source-only host operations and runtime copies need no network or runtime package install. The full, AgentBay and delta recipes now copy all socket source dependencies; isolated source-only socket builds and an offline Docker import smoke pass. These checks are not full builds of all three runtime images, a deployed release or a verification of every previously installed project runtime.

No production deployment was performed as part of this work.
