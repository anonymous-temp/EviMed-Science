## 0. 一页结论

**我们在哪。** 内核、证据门禁、记忆召回、主动科研、专科引擎和评测体系都已经在线上运行。生产实测：缓存命中率 98.3%，一份深度报告的模型成本约 ¥4，容器冷启动 5 秒。这一类产品比拼的第一项是"结论可审计"，这正是我们最强的地方：逐字引文门禁、报告里每条结论的 ✓/⚠、评审者与写作者分离。离世界级差的不是这条主线，而是它周围的六块。

## 2. 文档解析：直接换成自研接口

**决定：直接换。接入点只有一个文件（`documentParserClient.mjs`），下游不用动。不留 MinerU，不做对照测试。接口现在缺的几样东西，我们这边先兜住，不挡接入。**

你上传的文档和仓库里的 `接口文档/多模态文档解析.md` 逐字一致。

**关于服务地址。** 接口文档里出现的地址只有示例命令里的 `http://localhost:8888`，它的意思是"跑这个服务的那台机器自己"，不是一个能从我们平台连过去的地址；我核过，开发机和生产主机上都没有这个服务（生产主机的 8888 端口是另一个产品的搜索代理）。不过另外两份接口文档（医学证据检索、指南检索）的服务都挂在同一个网关下：`https://www.evimed.com/api-evimed/medicine-api/ai-api`，用 Bearer 密钥鉴权，而这把密钥平台本来就有（控制面的 `evimedApiKey`）。我从外面试过：这个网关对任何路径都先查密钥（一律回 401），所以不带密钥看不出解析接口在不在它后面。**动手的第一步就是用平台已有的那把密钥发一个小文件过去试一次；通了，解析器这件事就不需要你做任何事。** 不通，才需要你一句话：服务跑在哪。客户端的地址和密钥做成两个配置项，默认值就填这个网关。

### 2.1 现在的解析链路（已对代码核实）

- 控制面调解析容器的 `POST /v1/parse`，拿回协议 v1：`extractor`、`units[]`、`summary`、`text`、`facts`、`methods`。
- 下游实际只用四样：`text`（切成 8000 字一块、带 UTF-16 偏移的采集单元，存进 PostgreSQL）、`units`（只用来算覆盖率）、`summary`、`extractor`。`facts` 和 `methods` 在物化时被丢弃。`index.md` 是四行头部加正文，没有页码标记。
- 生产上的 MinerU 容器上限给到 6 GB、4 核，而主机一共 4 核、15.5 GB。删掉它，主机上少一个最大的内存隐患。
- 还有第二处解析：运行时里的 `open_access_fulltext.py` 用 pypdf 读开放获取论文，只取文字层，表格不还原，扫描件读不了。
- 生产上知识库现在是 0 份资料，没有存量要迁。

### 2.2 字段对照，以及缺的东西我们怎么兜

| 我们需要的 | 自研接口现在给的 | 我们的做法 |
|---|---|---|
| 完整正文 `text` | `content` | 直接用，当纯文本处理，不依赖它是不是 Markdown |
| 摘要 `summary` | `abstract`（可能为空） | 有摘要用摘要，没有就沿用"正文前 500 字" |
| 解析器版本 | 没有 | 我们自己在配置里记一个修订号（`OPEN_SCIENCE_DOCUMENT_PARSER_REVISION`）。解析服务升级时改一下，索引按"文件哈希 + 修订号"重建 |
| 逐页覆盖和页码 | 没有 | 先按"整份一个单元"入库，一切照常。接口哪天返回分页信息，"引用跳到原文第几页"自动点亮（协议里 `pageMap` 是可选字段） |
| 鉴权 | 没有 | 配了密钥文件就带 Bearer，没配就不带。服务放内网，或者前面加一层带鉴权的反向代理，都行 |
| 大小和超时 | 没写 | 我们这边设客户端超时（默认 300 秒，可配）和已有的上传大小上限。超时、429、502、503 退避重试 3 次；413、415、422 直接判失败，并把原因告诉用户 |
| 没有 | `title`、`authors`、`doi`、`source`、`publication_date`、`keywords` | 新增收益：来源卡片和引用元数据。DOI 用 Crossref 再核一遍（模型抽取、代码复核） |
| 上传格式白名单 | 接口支持 pdf、doc(x)、ppt(x)、xls(x)、图片、epub、mobi、html、md、rtf、txt；不支持音视频 | 知识库的上传白名单按这张表放开；音视频继续拒收，并说明原因 |
| —— | `/extract/text/url` | 不调用。字节由我们自己的网关抓取（已有内网地址拦截），再走文件上传接口 |

### 2.3 接入设计

- **`documentParserClient.mjs` 改成调自研接口。** 文件字节用 multipart 发过去，`checksum` 用我们已有的 sha256（来源编号本来就是内容哈希）。`parse()` 的返回形状不变，下游一行不改。不再需要共享暂存目录。
- **协议 v1 加两个可选字段**：`pageMap`（页到字符偏移的映射）和 `metadata`（书目信息）。
- **`index.md`** 头部加标题、作者、DOI；有 `pageMap` 时正文按页插入标记。"引用跳到第几页"的路径是：引文的字符偏移 → `pageMap` → 页码。
- **不新开网关：给现有的公开来源网关加一个"经解析"模式。** 这是 09-15 生态清单里已经定过的形状。3.5 节的 `web_read` 抓到 PDF（学会指南、监管附件大多是 PDF）时，网关把字节交给解析服务，返回正文。运行时仍然不持有任何密钥、不直接访问任何主机。运行时里那条 pypdf 路径顺带改走这个模式，但不为它单独排期：09-15 量过，170 份会话记录里它被调用 0 次。
- **MinerU 在切换的同一个提交里删掉**：`deploy/document-parser`、ingestion overlay 里的服务、`deps-version.json` 里的 pin、`health()` 里对 `mineruVersion` 的判断。不留开关，不留备选，和 09-01 删 OpenCode 是同一个做法。
- **版本登记。** `deps-version.json` 加自研接口一项；`packages/contracts/evimed-extract` 的契约样例从真实接口录一次，不手写。

### 2.4 给解析服务同事的一段话（想转就转，不转也不挡接入）

只有三条，都是小改动，现有字段全部保留：

1. **分页信息。** 响应里加 `pages: [{index, start, end, status}]`，`start`/`end` 是 `content` 里的字符偏移（请写明按什么单位计，我们内部用 UTF-16 码元），`status` 取 `ok` / `empty` / `ocr_failed`。PPT 按张，Excel 按工作表。有了它，报告里的引用才能跳到原文第几页。
2. **版本。** 响应里加 `parser: {name, version}`，再提供一个 `GET /health`。
3. **正文这条路径上不要有大模型改写文字；有文字层的 PDF 直接取文字层，只有图片页才做 OCR。** 我们的交付门禁是拿引文去和 `content` 逐字核对的，解析器如果"整理"过文字（合并断行可以，改字改数不行），假引文也会被判成真的。视觉模型类解析器改数字是有记录的：把置信区间"84-89"读成"84.89"，把"0.5mg"读成"5mg"。

```json
"parser": { "name": "evimed-extract", "version": "1.4.2" },
"pages": [
  { "index": 1, "start": 0,    "end": 3120, "status": "ok" },
  { "index": 2, "start": 3120, "end": 3120, "status": "ocr_failed" }
]
```

## 3. 分领域方案

### 3.1 沙箱与运行时：搬到 AgentBay

**现状（代码和生产主机都已核实）。**

- 每个项目一个 Docker 容器，容器内是 root，运行时只有 runc；只接内部网络，不能出网，对外访问全部经控制面网关。
- 主机 4 核、15.5 GB，6 个产品的 34 个容器共用，交换分区 100% 用满，控制面数据库也在这台机器上。并发上限全局 4、每人 2，4 个容器各 4 GB 已经超过整台主机的内存。
- 主机没有 KVM，做不了微虚拟机；文件系统是 ext4，做不了按容器的磁盘配额。
- **代码里量出来的默认值，被 compose 文件里的旧兜底值盖掉了。** 进程数上限在代码里是 1024（注释写明：在 256 下连续有三个 run 死掉，报 `fork(): EAGAIN`），compose 的兜底值还是 256，生产上实际生效的就是 256。内存上限同理（代码 8 GB，compose 4 GB）。

**决定：运行时整体搬到 AgentBay，控制面留在现在的主机上。** 不可信代码离开这台主机以后，"容器内 root、和数据库及其他产品同机"这个风险就不存在了，所以不用另买主机；运行时容器和 MinerU 容器一走，这台主机的内存压力也一并缓解。

**AgentBay 核实到的事实（官方文档和 SDK 仓库）：**

| 我们要的 | AgentBay 给的 |
|---|---|
| 比容器更强的隔离 | 每个沙箱跑在一台有独立客户机内核的虚拟机里；不分配公网 IP，没有对外端口；沙箱之间默认互相隔离 |
| 跑我们自己的镜像 | CodeSpace 类镜像可以用 CLI 加 Dockerfile 自定义：`FROM` 必须是它的系统镜像（Ubuntu 24.04），模板开头几行不能改，其余随我们装。规格 2 核 4 GB 到 16 核 32 GB；一个镜像绑定一个地域、一个规格。需要 Pro 或 Ultra 订阅 |
| 控制面连进去 | `get_link(protocol_type="wss", port=…)` 返回一条带令牌的 wss 或 https 链接，端口范围 30100–30199，明确支持"连接会话里自己起的 WebSocket 服务"。同样需要 Pro 或 Ultra |
| 长任务 | 单次运行上限和空闲释放都可配，1–1000 分钟；SDK 的默认值是 30 分钟和 5 分钟，要显式调大 |
| 文件持久化 | Context：每个 Context 对应一个对象存储目录，会话创建时自动下载、释放时自动上传，运行中可以手动 `sync()`；**会话不在的时候也能读写**（预签名上传和下载地址、`list_files`、`delete_file`） |
| 不能随便出网 | 安全白皮书写明客户可以配安全组规则（IP 段）和域名管控策略 |
| 并发 | Pro 档 200 个并发会话 |
| 地域 | 大陆只有 `cn-hangzhou` |
| SDK | Python、TypeScript、Go、Java；控制面用 TypeScript 这一个 |

两个会影响设计的限制：它的命令执行接口单次最长 50 秒、代码执行接口 60 秒，所以**不能**用这两个接口来驱动我们的 run，只能用来启动内核进程；run 本身走内核自己的 WebSocket。暂停和恢复还是白名单内测，不依赖它。

**怎么接（形状不变，换的是"容器"这一层）：**

1. **运行时提供方做成可选。** `runtimeManager` 的启动计划里已经有 `sandboxMode` 这个概念，加一个 `agentbay` 提供方。生产切到 AgentBay；Docker 提供方只留给本地开发。切换完成后，生产上不再需要那个握着 Docker 特权接口的 runtime controller。
2. **镜像：一份安装脚本，两个 Dockerfile。** 把 `deploy/runtime-dsh/Dockerfile` 里的安装步骤抽成一份脚本，Docker 版和 AgentBay 的 CodeSpace 版都调它，两者只差 `FROM` 和 AgentBay 模板规定的开头几行。DSH 版本照旧只从 `deps-version.json` 取，新 Dockerfile 纳入"所有派生副本等于 pin"的那条测试；profile 照旧在构建时预初始化，HMR 关闭，遥测在镜像、patch、环境三处关闭。安装目录归 root，内核和它执行的代码以普通用户运行，改不了自己的安装。规格定 4 核 8 GB（08-26 在 4 GB 下 OOM 过，代码默认值已经是 8 GB）。
3. **内核连接加一种传输，内核的启动方式一个参数都不改。**
   - DSH 的 web 宿主**拒绝** `--host 0.0.0.0`（会直接报用法错误退出），并且它的 `/api` 围栏会拒绝 `Host` 头既不是回环、也不是声明过的可信主机的一切请求，会话 cookie 的名字也是从 `Host` 头推出来的。现在的启动脚本因此让内核只听回环，前面用 socat 桥成一个 unix socket。
   - 在 AgentBay 里保持同一个形状：内核照旧 `--no-open --port … --trusted-host dsh.runtime` 只听回环；前面的桥从 socat 换成一个几十行的会话内反向代理，听 30100 端口，把 `Host` 改写成 `dsh.runtime`，校验一个控制面在会话启动时生成的密钥头，再转给回环。这个代理不认识 DSH 协议，只转 HTTP 和 WebSocket。
   - 这样内核看到的请求和今天逐字节一样，`dshMux.mjs`、`dshBrowserAuth.mjs`、录制的 golden 帧都不用动；控制面只换"怎么建立这条 socket"（`OPEN_SCIENCE_RUNTIME_TRANSPORT` 在 `unix` 之外加 `wss`，地址来自 `get_link`）。内核自带的界面照旧由控制面代理给浏览器，浏览器永远看不到 AgentBay 的地址。
   - 连接上每 25 秒发一次心跳；断了就重连并用 `session/page` 续上，run 的进度本来就是按消息数和工具数观察的，所以一次断线不会丢 run。
4. **工作区：主机上的项目目录仍然是"正本"，AgentBay 的 Context 是搬运通道和保险。** 这样文件预览、知识库、分享、备份、额度这些现有功能一行不用改（控制面读写项目目录的代码集中在 `store.mjs` 一个模块里）。
   - 每个项目一个 Context，挂两条路径：`/workspace`，和内核状态里真正属于用户的两个目录：`$DSH_HOME/sessions`（对话历史，JSONL 文件；内核的 SQLite 检索索引本来就只在内存里）和 `$DSH_HOME/storages`（插件的 storageDomain 状态，JSON 文件）。`$DSH_HOME` 的其余部分不同步：它里面是指向镜像内只读种子的链接（对象存储不支持链接），每次启动由现有的 `evimed-profile-seed.mjs` 按摘要重建。
   - 凭据文件、控制面生成的 profile patch、令牌文件**不进 Context**，由控制面在会话启动后经文件接口直接写进去。工作负载令牌现在 300 秒过期、靠控制面原地改写文件续期；搬过去以后续期改走会话文件接口，这个提供方的有效期放到 900 秒、仍然每 300 秒续一次，容得下两次续期失败。
   - 会话启动前，控制面把主机上有变化的文件经预签名地址传进 Context（大文件走对象存储，不挤会话那条 5 Mbps 的共享出口）；会话创建时自动下载。
   - 会话活着的时候，界面和交付门禁要读的文件**直接向会话读**；会话不在，读主机上的正本。
   - run 结束和会话释放前各同步一次，把变化拉回主机；会话意外死掉时，Context 里最后一次自动上传就是保险。
   - `knowledge-base/` 这条路径设成只下载不上传，run 改不了源文件（对应 v1.0 的"知识库只读挂载"）。
   - 胶囊的方法目录今天是只读挂载进容器的（用户能上传的地方不能出现 SKILL.md，否则就是用户能注入的指令）。搬过去以后由控制面在会话启动后写进一个归 root 的目录，运行用户只读，性质不变。
   - 同步代码沿用现在的规矩：不跟随符号链接，路径必须落在项目目录内，控制面永远不执行、不导入工作区里的文件。
5. **网关走公网的 443。** 运行时现在按容器名访问控制面的各个网关（模型、公开来源、搜索、胶囊、修订）；搬走以后改成 `https://<我们的域名>/runtime-gateway/…`，沿用现有的按运行时签发、带时间戳的签名令牌，再加限速。对内核来说只是 profile patch 里 `baseURL` 换了一个地址，这本来就是 DSH 文档化的配置项。六个专科引擎现在是运行时带签名令牌直连的，同样收到这个入口后面。腾讯云安全组本来就只放行 80 和 443，不用动。
   - 镜像的网络类型选"高级网络"（独享带宽）。原因：内核每次模型请求都把整段上下文发给我们的模型网关，平均 18.4 万 token，约 0.6–0.8 MB；标准网络是所有会话共享 5 Mbps，几个并发的深度任务就会把它占满。
6. **出网只放行我们的网关域名**，用 AgentBay 的域名管控策略加安全组规则；镜像里再加一道只有 root 能改的防火墙规则作为第二层。"运行时不持密钥、不直接访问任何主机"这条原则原样保留。AgentBay 的 API 密钥只放在控制面的密钥目录里。
7. **生命周期。** 空闲 30 分钟释放（和现在一样，不缩短），单次运行上限 240 分钟，会话带 `{user, project}` 标签，控制面重启后用会话编号接回去。全局并发上限从 4 提到 100（配置项不变），每人 2 不变。
8. **顺带把第 2 轮记下的四个体验问题修掉：**
   - 登录时预热最近用的那个项目（登录后就创建会话），用户点进项目时环境已经在了；
   - 名额满了报的 429，现在被界面误显示成"冷启动慢"，改成说实话；
   - 就绪等待的文案按新的启动过程重写（准备环境 → 同步文件 → 启动内核）；
   - 夜间自主研究的 run 不被空闲回收停掉（spec G16）：正在跑的 run 不算空闲。
9. **接入的第一步**（拿到密钥当天开始）：镜像构建出来 → 内核起得来 → 控制面连得上 → 走通一次对话和一次 40 分钟的深度任务。这是施工的第一步，不是试点；中途遇到硬阻塞，我当场换做法并告诉你，不回头做 gVisor。
   - **第一分钟先看一件事：会话里的内核版本（`uname -r`）和 DSH 自报的 Landlock 状态。** 这是唯一一条从文档里裁决不了的。DSH 在托管环境里限制写操作靠的是 Landlock：内核 6.10 及以上是满级；5.13 到 6.9 DSH 自报 `partial`（文件读写的约束实测同样有效，缺的是 6.10 才有的设备 ioctl 限制）；低于 5.13 没有 Landlock，DSH 的 bash 工具会整体拒绝启动。我们的生产配置要求满级（为此 08-24 把现在这台主机的内核升到了 7.0）。AgentBay 的客户机内核版本文档里没有写。
   - 三种结果的处理现在就定好：满级，照常；`partial`，给 `agentbay` 这个提供方把 `OPEN_SCIENCE_RUNTIME_SANDBOX_ENFORCEMENT` 设成 `partial` 并写明理由（每个项目一台虚拟机才是外层边界，DSH 的写围栏是里面的第二层）。这是按提供方定的值，不是给某一台机器开例外，和规格 §30.4 的意思不冲突；没有 Landlock，AgentBay 就承载不了 DSH 内核，我当天告诉你，运行时留在 Docker 上并把非 root 改造做掉，不会硬凑。

**切换之前只做一件过渡的事：把 compose 里的兜底值改成代码默认值**（进程数 1024、内存 8 GB），web 和 controller 两个容器都要重建；同时加一条测试：compose 的资源上限兜底值不得低于代码默认值。v1.0 里 Docker 这条路上的其他加固（非 root、按内存准入、内存曲线落账、容器间网络隔离）都不做了，因为做完几周后就会随 Docker 提供方一起退出生产。

共享工作区这类逃逸（agent 写下一个文件，沙箱外的组件后来执行了它）的第一轮核查结果是干净的：控制面没有任何一处执行或导入工作区里的文件；HTML 交付物在不允许脚本、不同源的沙箱框架里预览；Markdown 渲染没有原始 HTML 这条路径。做报告分享链接时沿用同一套渲染，不另写。

### 3.2 知识库

**现状（已核实）。** 上传或从 OpenList 导入 → 按内容哈希编号 → 解析 → 正文切成 8000 字的采集单元存 PostgreSQL → 可选的资料理解 run → 写一份 `index.md` 到项目目录 → agent 用读文件和 grep 找内容。没有检索工具；只在单个项目内可用；生产上目前一份资料都没有。

**决定：知识库检索放在我们自己的 PostgreSQL，OpenViking 只留给记忆。** OpenViking 的检索结果没有页码和字符偏移，接不上逐字引文门禁；没有关键词这条腿，而药名、剂量、缩写恰恰要靠关键词；每份文档都要用大模型生成分层摘要；没有 docx、pptx、xlsx 的解析器。

**要做的：**

1. **P0 解析器替换**（第 2 节）。
2. **P0 知识库检索工具 `kb_search`**，经控制面网关提供，运行时照旧不持密钥。直接上线，不做多臂对照；只留一组固定问题当回归测试，防以后改坏。
   - **它是一个由模型自己决定用不用的工具，不是每轮强制检索**（原则 12）。作为现有 `evimed-research` MCP 服务里的一个工具提供，不新增 DSH 接缝；有自己的开关 `OPEN_SCIENCE_KB_SEARCH_ENABLED`，关掉以后对话照常；它不依赖记忆、胶囊和能力目录（通用工具保持独立）。
   - **小库不检索，但这句话写在工具结果里，不写在控制流里**（原则 7）。项目内资料总量在 15–20 万 token 以内时，`kb_search` 直接返回"这个库很小，请直接读这几个文件"和文件清单，由模型去读（Anthropic 的建议是 20 万 token 以下不要做检索；我们有 100 万上下文和 98% 的缓存命中率，重读很便宜）。
   - **大库做混合检索。**
     - 分块：PDF 按页、PPT 按张、Excel 按表、其余按标题层级；超过约 1000 token 再细分；表格整块不拆；每块前面加一句"文档标题 › 章节路径"的上下文前缀（Anthropic 的 Contextual Retrieval 实测检索失败率降 49%，再加重排降 67%）。接口还没返回分页时，PDF 先按标题层级和长度切。
     - 向量这条腿：pgvector，查询按"查询"编码，文档按"文档"编码，从一开始就做对。
     - 关键词这条腿：用我们已有的中文双字切分（`memoryRecallPolicy.mjs` 里的 `searchTokens`）写进 `tsvector`，再加 PostgreSQL 自带的 `pg_trgm` 处理药名和拼写。不引入新扩展，也不引入新服务。
     - 融合与重排：RRF（k=60）加现有的 `qwen3-rerank`，和记忆召回同一套。
     - 每条命中返回原文片段、来源、页码（有的话）、字符偏移。引用和逐字门禁用同一份出处。
   - **索引是派生物，可重建**，按"文件哈希 + 解析器修订号"做键。检索服务不可用时，agent 照旧可以读文件和 grep，对话不中断。
   - **pgvector 原地换镜像。** 生产的 PostgreSQL 是官方原版 `postgres:16.14-bookworm`，没有 pgvector；`pgvector/pgvector:0.8.6-pg16-bookworm` 是在同一个基础镜像上加装扩展，数据目录兼容。随一次正常发布换：先备份，按摘要固定镜像，确认小版本不低于 16.14。
3. **P1 知识库只读**：见 3.1 第 4 条，`knowledge-base/` 只下载不上传。
4. **P1 个人文库。** 在项目知识库之外加跨项目的个人文库，任何项目只读引用。这就是胶囊的"资料"分区。
5. **P1 资料进胶囊的发布路径**，护栏见 3.3。

### 3.3 记忆胶囊

内容以配套方案为准，顺序不变：先改内容，再让回路转，再重摆页面，然后是时间轴和分享。你的 7 个决定已经定了方向，这里只写五处修订。

1. **全自动，不加确认（你的第 5 个决定）。** 那份方案 4.8 节让"资料产出的理解停在待确认"，改成四个不需要点击的护栏：
   - **来源标签永久保留。** 推断出来的内容可以直接用，但永远标"推断"或"来自资料"，不会变成"你说过"（原则 18）。
   - **资料和工具结果只能成为"带出处的事实"，不能成为"偏好"或"指令"。** 这是对记忆投毒的结构性防御：网页或文档里写着"以后都用某某方法"，最多成为一条"某文档这样说"的项目事实，进不了画像。
   - **每次改动进修订史，可以撤销。** 时间轴从修订史派生，被取代的内容标"曾经如此"。
   - **短期模式自然淡出。** 用过期时间和新近度加权，避免把"某一周压力大"固化成长期画像。
   - 唯一的人工关口：命中 `clinical-safety-rules.json` 的内容。
2. **学习回路的触发改成自动。** 现在要同一份交付物"既点采纳又点我改过"才入队，默认配置下回路启动不了。另有一个同类的小缺陷要一起修：夜间窗口的时区开关 `OPEN_SCIENCE_LEARNING_WINDOW_TIMEZONE` 代码里有，compose 却没有把它传进容器，容器是 UTC，所以"22:00–09:00"现在实际是北京时间的白天（原则 17）。改成三个自动信号：交付完成、用户在对话里纠正、同类操作重复出现；再加 22:00–09:00 窗口内的夜间整理。学到的方法要不要启用也不靠人点头：代码里已有"新方法对旧方法的配对评测"，候选方法只会挂进评测账号的运行时里去量，通过了才对研究者生效。缺的只是回路的输入，不是把关的人。
3. **"本次用到的背景"按标配来做，做完整。** 召回的每一条、挂载的每一条方法都列出来，每条可以当场"不对"或"本次不用"。数据在运行账本里是全的。
4. **分享来的胶囊整包信任、自动扫描（你的第 3 个决定），借用模式只留一种。**
   - 三样检查都自动完成：签名校验（不过就拒收，这是工程边界）；确定性检查只查闭集的东西（从 `toolNames.mjs` 派生的工具名、网址格式）；"这句话是不是在对 agent 下指令"属于语言判断，交给模型判断、代码复核可核对的部分（原则 5：正则不做语言）。被判有问题的条目直接剔除并列给用户看，其余照常生效；然后预览、试用一次、一键生效、一键停用。
   - 现在胶囊页面上每个胶囊有一个下拉框，三个选项："主要胶囊""参考胶囊""合并参考"。后两个在服务端的行为完全一样（整个服务端只判断"是不是主要胶囊"）。前期不需要这么细：**页面上只留"主要胶囊"和"参考胶囊"两个选项**，别人分享来的一律按"参考"生效（带来方法和标准，不带来身份）。已经存成"合并参考"的记录按"参考"处理，不用迁数据。
5. **数据层补两个字段。** 记录表已有 `expires_at`，缺"被哪一条取代"和"从何时起失效"。用药和剂量这类会变的事实需要它，时间轴的"曾经如此"也靠它。
6. **加"无痕对话"开关。** 打开时这次对话不提取记忆。第 4 轮提过，v1.0 和配套方案都漏了。
7. **配套方案里和你的决定冲突的四处，以你的决定为准：**
   - 第 73 行"未经确认不进账号级"、第 124 行"待你确认"、第 191 行"待确认托盘"：都按上面第 1 条改成"直接生效、事后可撤销"，不设待确认的界面。

### 3.5 网页阅读

全部放在网关侧，分三层：

1. **接口优先**（已有约 70 个生物医学接口）。
2. **直接抓取加正文提取**：把 `official_page_fetch` 扩成通用的 `web_read`；白名单不再决定"能不能读"，改成"官方来源"标签，只影响证据等级。对所有公开网站开放，遵守 robots.txt，标明我们的 UA，对同一站点限速。
3. **按需渲染**：只有遇到空壳页面或 JS 挑战页才用。**决定：渲染层用 AgentBay 的云浏览器，不自建。** 我们的公开来源网关用 `browser_latest` 镜像起一个会话，`get_endpoint_url()` 拿到 CDP 地址，Playwright 连上去打开页面、等它渲染完、取回 HTML，正文提取仍在我们的网关里做。理由三条：
   - 陌生网页的 JS 跑在阿里云的虚拟机里，不在我们的内网里，"页面里的 JS 自己去打内网地址"这个风险直接消失；
   - 我们的主机不用再背一个 Chromium 服务；
   - 和运行时同一个供应商、同一把密钥；它自带指纹伪装、代理和滑块验证码处理，对付 JS 挑战页够用。

   渲染只做"打开、等待、取回"，不点击、不登录、不填表。每次请求用一个全新的无痕上下文，不保存 cookie，不登录任何账号；并发数和单页超时都有上限。有流量时留一个热会话，空闲就释放。某个站点渲染后仍然读不到，就返回一个有名字的错误码，agent 改用别的来源（NMPA 有我们自己的药学数据库兜底）。

`web_read` 的几个细节照第 5 轮定的做：长正文分页返回；一个启用开关；作为 `evimed-research` MCP 服务里的一个工具提供（由现有的 `official_page_fetch` 扩出来，不是第二个工具）。PDF 走 2.3 节公开来源网关的"经解析"模式。

**和 DSH 自带的网页能力的关系（09-15 已定，这里不变）：** DSH 内核自带的 `tool-web` 和 `web-fetch-http` 继续不挂，因为 MCP 已经有同一件事的工具，挂了就是一件事两个名字，而且 `web_fetch` 是规格点名的 SSRF 面。内核的 `ctx.web` 注册表里，我们 09-15 已经注册了自己的 `evimed-gateway` 提供方，它指向的是同一个公开来源网关，所以网关学会渲染和读非白名单页面以后，这条缝自动跟着受益，不用再改插座。

**前端不展示浏览器。** 在运行记录和「依据」弹窗里显示"已阅读的网页"卡片：标题、网站、时间、原文链接和快照。

### 3.6 手机端：先把飞书跑通，其余只留接口

两条结论不变：IM 接在控制面；运行时按需启动。

**只做飞书，用"扫码创建机器人"。**

- 用户在我们的网页上扫一个码，就在他自己的飞书租户下创建一个专属机器人，个人版也可以。这是飞书公开并写进官方 SDK 文档的能力：Node SDK 的 `registerApp`（"一键创建应用"，OAuth 2.0 设备授权流程），可以预设应用名称、头像、权限和事件。不需要服务商资质，也没有白名单；主动推送是允许的。
- 控制面里的形状：`imService`、路由、租约 worker、一个开关 `OPEN_SCIENCE_IM_ENABLED`。渠道层的代码可以借 `dsh-im`，把它的 `harness-client.mjs` 换成调我们 run 接口的客户端。
- 每个用户一份 App ID 和 Secret，放进现有的按用户加密的凭据库。只发通知不需要长连接；要对话的用户，控制面为他的应用挂一条长连接。
- 消息进哪个项目：单聊默认进用户最近用的项目，说一句"换到某某项目"就切（由模型理解，不设命令）；一个群对应一个项目。扫码这一步是用户在我们已登录的网页上发起的，所以账号绑定不用另走绑定码。
- 长任务的呈现：收到时应一声；进度写在同一张流式卡片上原地更新，不刷屏；完成时发结果消息和报告文件（飞书单文件上限 30 MB，超过的发链接）。`dsh-im` 的超时补发机制一起借过来，正好适合十几到几十分钟的 run。托管环境的审批策略是 `never`，所以没有审批卡片这回事。
- 收件箱通知和主动科研的晨间摘要也从这里发。
- 借 `dsh-im` 的代码时，把它在聊天里切工作区路径、切模型、切 preset、改 `/permission` 的那几条指令去掉。这些在我们这里都归控制面管，而且 `/permission` 能绕过方法拒绝名单。只拿纯渠道层的模块（飞书接口客户端、卡片拼装、附件、超时补发），凡是 `import '@deepseek-ai/*'` 或 cordis 的文件一律不拿：控制面里没有内核，也只有 `harness-port` 一个包允许碰那些依赖（spec D3）。飞书这个模块和 DSH 内核之间没有任何新的接触点，它派任务走的就是网页现在用的 `session/prompt`。
- 飞书消息里的链接会在手机上打开我们的网页，所以报告页和 run 页要做手机适配；创建机器人时把应用主页预设成我们的网页，用户在飞书工作台里点开就是完整界面。`apps/web` 现在没有 PWA manifest，顺手加上。
- 两个已知的边角，直接在代码里处理：扫码链接要用 SDK 拼出来的那个（直接用接口返回的会显示"链接已过期"）；企业租户如果要管理员审批，或者是数据驻留类的 Lark 租户，轮询会返回相应状态，我们原样告诉用户"需要管理员批准"或"暂不支持"。
- 做完的标准：手机飞书上给机器人发一句话派出一个 20 分钟的任务，完成后在飞书里收到结果消息和文件。

**其余渠道和自有 App：只留接口，默认关，不做任何配置。**

- **渠道端口**只有三个方法，飞书是第一个实现：
  - `bind(userId)`：建立绑定（渠道、对方身份、凭据引用）；
  - `deliver(binding, message)`：发出一条消息，返回 `{delivered, messageId}`，拿不到消息编号一律按没送达处理；
  - `onInbound(event)`：把一条进来的消息归到某个用户的某个项目，变成一次普通的 run 请求。
- **预留的渠道编号**：`wechat-service`（服务号模板消息）、`wechat-clawbot`、`email`、`app`（自有 App 推送）、`dingtalk`、`wecom`。每个渠道就是一个适配器文件加一个 `OPEN_SCIENCE_CHANNEL_<编号>_ENABLED` 开关，默认关；凭据走现有的凭据库。以后你要配哪个，加一个适配器、打开开关就行，控制面其他地方不用动。
- **通知偏好**里的渠道校验现在写死成只有站内（`notificationService.mjs`），改成"站内，加上任何已启用的注册渠道"。
- **自有 App 预留两样**：一是 `app` 渠道（推送令牌登记接口加厂商推送适配器的位置）；二是给非浏览器客户端用的 Bearer 令牌登录（现在的接口只认浏览器会话 cookie），放在 `OPEN_SCIENCE_APP_API_ENABLED` 后面，默认关。App 用的就是网页现在用的那一套 run 接口和事件流，不另做一套 API。

### 3.10 和 DSH 内核机制、开发原则的对照（定版前的最后一遍复核）

**结论：本方案不改内核、不给 `node_modules` 打补丁、不新增任何 `@deepseek-ai/*` 的引用点、不新增 DSH 接缝。DSH 升级仍然是"改 `deps-version.json` 一处、跑一遍夜间矩阵和接缝自检"的一个 PR。** 复核中发现 v2.0 有四处和 DSH 现有机制对不上、三处和开发原则对不上，都已在正文里改掉，列在下面。

**上游现状（今天查的 npm）：** 我们钉的 `0.1.5-rc.2` 就是 `latest`，没有落后；alpha 通道走到了 `0.1.6-alpha.2`（09-17），由夜间矩阵跟着。

**每一项改动碰不碰内核：**

| 改动 | 和 DSH 的接触点 | 升级时要不要跟着动 |
|---|---|---|
| 运行时搬到 AgentBay | 无新增。内核的启动参数、`Host` 头、会话 cookie、mux 帧和今天逐字节一样；换的只是控制面"怎么建立这条 socket"，以及内核前面那个不认识 DSH 协议的桥 | 不用。版本只从 `deps-version.json` 来，新 Dockerfile 纳入 pin 一致性测试；golden 帧与传输方式无关 |
| 网关改走 443 | profile patch 里的 `baseURL`，DSH 文档化的配置项 | 不用 |
| `kb_search`、`web_read`、来源网关的"经解析"模式 | 都是现有 `evimed-research` MCP 服务里的工具或参数，经已有的 `dsh-mcp-client` 配置行进来 | 不用 |
| DSH 自带的 `tool-web` / `web-fetch-http` | 继续不挂；`ctx.web` 的提供方 09-15 已注册 | 不用 |
| 解析器换成自研接口 | 无。全在控制面 | 不用 |
| 记忆：自动学习、无痕对话、"本次用到的背景" | 无新增。无痕由胶囊网关对该会话返回空来实现，插座的 `capsule` 插件不用改；面板数据来自控制面的运行账本 | 不用 |
| 关掉两处思考、重排加指令 | 无。都是控制面经模型网关发的请求，不经过内核 | 不用 |
| 飞书和渠道端口 | 无。派任务走网页现在用的 `session/prompt`；借来的代码不含任何内核依赖 | 不用 |
| 上下文压缩 | 不动。仍用 `dsh-compaction-basic` 提供的那个基类 | —— |
| `dsh-annotation`、`dsh-mermaid` | 社区 bundle，走 `dsh-cite` 那条已有路径，固定版本、各带开关 | 每次升级随夜间矩阵重测，装不上就关掉，不挡升级 |

**v2.0 里和 DSH 机制对不上、已经改掉的四处：**

1. 启动命令写成了 `--host 0.0.0.0`。DSH 的 web 宿主会拒绝这个参数，而且它按 `Host` 头设围栏、按 `Host` 头推 cookie 名。改成：内核照旧只听回环，前面放一个改写 `Host` 的桥（3.1 第 3 条）。
2. 漏了工作负载令牌 300 秒过期、靠原地改写文件续期这个机制。改成经会话文件接口续期，凭据不进 Context（3.1 第 4 条）。
3. 漏了 DSH 的写围栏靠 Landlock、对内核版本有要求，而且没有 Landlock 时 bash 工具会拒绝启动。改成接入第一分钟先查，三种结果的处理预先定好（3.1 第 9 条）。
4. 打算同步整个内核状态目录。它里面有指向只读种子的链接，对象存储存不了。改成只同步 `sessions` 和 `storages` 两个目录，其余每次启动重建（3.1 第 4 条）。

**和开发原则对不上、已经改掉的三处：**

1. 原则 5（正则不做语言）：胶囊自动扫描里"是不是在对 agent 下指令"原本写进了确定性检查，改成模型判断（3.3 第 4 条）。
2. 原则 12 和 7（不强制检索；先验放在上下文里，不放在控制流里）：`kb_search` 明确为模型自选的工具，"小库直接读"写进工具结果（3.2 第 2 条）。
3. "生态优先"和 09-15 已有的裁决：v2.0 把三个社区插件一律写成"不引入"，还把已经做完的 `ctx.web` 缝排进了第 2 阶段。按实物改正（3.9）。

**其余原则逐条过了一遍，没有冲突，做的时候要守住的几条：**

- 原则 11 和分层表：每个新工具、新模块各有一个开关，全部关掉以后原生的 DSH 加 DeepSeek 对话照常可用。开关清单：`OPEN_SCIENCE_KB_SEARCH_ENABLED`、`web_read` 的开关、`OPEN_SCIENCE_IM_ENABLED`、各渠道开关、`OPEN_SCIENCE_APP_API_ENABLED`、两个社区 bundle 各一个、运行时提供方。

- 原则 19：工作区同步失败不推翻已经完成的 run。交付物先向活着的会话读，Context 的自动上传兜底。
