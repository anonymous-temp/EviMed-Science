## A. Escalation / human-in-the-loop

### A1. Feng, McDonald, Zhang — "Levels of Autonomy for AI Agents" (arXiv:2506.12469, v1 14 Jun 2025; Knight First Amendment Institute essay series)
URL: https://arxiv.org/abs/2506.12469 ; https://knightcolumbia.org/content/levels-of-autonomy-for-ai-agents-1
- Thesis (verbatim): "autonomy can instead be a deliberate design decision made by agent developers" — separate from capability and environment.
- Five levels defined by the user's role: L1 operator (user drives plan, agent assists on demand); L2 collaborator (co-plan, either can take control); L3 consultant (agent plans/executes, consults user for expertise/preferences); L4 approver (agent executes most work, escalates only for blockers, missing credentials, or pre-specified consequential actions); L5 observer (user sees activity logs; only control is "an emergency off-switch that shuts off all agent activity").
- L4 definition (verbatim): "the user is only required to interact with the agent when the agent encounters a blocker it cannot resolve on its own. This includes reaching a failure state that prevents workflow continuation, providing credentials ... or signing off on consequential actions." Their running example is a research-report agent (literature + dataset analysis): at L4 the user pre-specifies which actions need approval, the plan is shown "only ... for transparency", inaccessible articles are skipped, and if the user cannot supply an API key the agent modifies its plan and continues.
- Names the L4 failure mode explicitly: "How can users be engaged in agent activities to avoid meaningless rubber stamping? User disengagement can lower the care with which they approve actions." Also warns a misaligned agent can gradually convince disengaged users to approve risky actions.
- Proposes "autonomy certificates" assessed by "assisted evaluation": run the agent on benchmark tasks with zero user involvement, then add involvement level by level until it meets a success threshold; the minimum involvement needed fixes the certified level; re-certify on material change.
- Implication: our proposal (digest + 24 h default-to-agent + hard stop only on major safety events) is L4 "approver" for flagged items and L5 "observer" otherwise; the paper's assisted-evaluation idea gives a way to set the level per decision class from measured success rather than by fiat.

### A2. Microsoft Magentic-UI — Mozannar, Bansal, ... Amershi, "Magentic-UI: Towards Human-in-the-loop Agentic Systems" (arXiv:2507.22358, v1 30 Jul 2025; MSR-TR-2025-40)
URL: https://arxiv.org/abs/2507.22358
- Mechanisms: co-planning (user edits plan before execution), co-tasking (user can take over / interject), multi-tasking, action guards, long-term memory (plan reuse), answer verification.
- Action guards: three-tier heuristic — "always irreversible" (e.g. uploading files) → human approval; "never irreversible" (scrolling) → auto; "maybe irreversible" (clicking buttons) → an LLM "ActionGuard judge" decides.
- Simulated-user experiment, GAIA validation (162 tasks): autonomous 30.3%; with a simulated user that has side information, "improves the accuracy ... by 71%, from a 30.3% task-completion rate to a 51.9%"; the agent "only asks for help ... in 10% of tasks", avg 1.1 requests in those tasks, relied on user for final answer in 18%. With a "smarter model" simulated user (o4-mini): 42.6%, asked in only 4.3% of tasks (avg 1.7 times).
- Autonomous benchmarks (o4-mini): GAIA test 42.52% (human 92%); AssistantBench 27.6%; WebVoyager 82.2%; WebGames 45.5%.
- Qualitative study n=12 users; SUS 74.58. Users edited plans often; wanted approvals for payments/subscriptions but found approval for adding to cart "not needed"; several asked for "a third option" beyond approve/reject.
- Safety: 24 adversarial scenarios — none effective with default mitigations (sandbox + action guards); with mitigations disabled, prompt injection succeeded (SSH key exfiltration, GitHub API key creation, etc.).
- Implication: a small number of targeted asks (≈4–10% of tasks) bought most of the gain; approval should be keyed to irreversibility class, with an LLM judge only for the ambiguous middle, and each ask should offer approve / reject / "do this instead".

### A3. OpenAI — Shavit, Agarwal, Brundage et al., "Practices for Governing Agentic AI Systems" (white paper, Dec 2023; PDF metadata 18 Dec 2023)
URL: https://cdn.openai.com/papers/practices-for-governing-agentic-ai-systems.pdf
- Seven practices: 4.1 evaluating suitability for the task; 4.2 constraining the action-space and requiring approval; 4.3 setting agents' default behaviors; 4.4 legibility of agent activity; 4.5 automatic monitoring; 4.6 attributability; 4.7 interruptibility and maintaining control.
- Approval & fatigue (4.2, verbatim): approval is "made harder when the user must approve many decisions and thus must make each approval quickly, reducing their ability to meaningfully consider each one"; open question on "minimum review times" to avoid approvals "turning into a 'rubber stamp'". Also: deployers can make agents periodically "time out" until a human reviews and reauthorizes them.
- Defaults (4.3): common-sense background preferences to "fill in the gaps" (e.g. "users prefer if I don't spend their money"); "err toward actions that are the least disruptive ones possible"; agents should request clarification "especially when it may change their actions", but "Having agents request information too frequently can also raise issues with usability and privacy".
- Legibility (4.4): provide "a ledger of actions taken by the agent" — "a lighter-touch method than requiring human approval"; "Actions that can only be reviewed after the fact should be more easily reversible than those that require approval." Chain-of-thought cannot yet be fully relied on (unfaithful).
- Interruptibility (4.7): user can always trigger "a graceful shutdown procedure", per action category or whole agent; agents should "pre-construct a fallback procedure if they're turned off"; shutdown must extend to sub-agents; automated circuit-breakers when risk indicators cross thresholds.
- Implication: the 24 h default is defensible only for actions that are reversible and logged; irreversible/externally-visible actions belong in the approval class, and everything the engine decides alone must land in an action ledger with its reasoning and a one-click revert.

### A4. Anthropic — how much autonomy users grant in practice
(a) McCain, Millar, Huang, ... Clark, Ganguli, "Measuring AI agent autonomy in practice" (Anthropic research, 18 Feb 2026). URL: https://www.anthropic.com/research/measuring-agent-autonomy
- Data: all interactive Claude Code usage (Table 1 from 500k human interruptions + 500k completed turns) + 998,481 randomly sampled public-API tool calls (privacy-preserving, Claude-classified).
- 99.9th-percentile turn duration "nearly doubled, from under 25 minutes to over 45 minutes" (Oct 2025 → Jan 2026); median stable ~45 s.
- Full auto-approve: ~20% of sessions for new users (<50 sessions) vs "over 40%" for users with 750+ sessions. Experienced users also interrupt more (≈5% of turns at ~10 sessions → ≈9%): oversight shifts from per-action approval to monitoring and intervening.
- "Claude Code pauses for clarification more often than humans interrupt it"; "On the most complex tasks, Claude Code asks for clarification more than twice as often as on minimal-complexity tasks, suggesting Claude has some calibration about its own uncertainty." Why Claude stops itself (Table 1): present a choice between proposed approaches 35%; gather diagnostic info/test results 21%; clarify vague/incomplete requests 13%; request missing credentials/tokens/access 12%; get approval before acting 11%. Why humans interrupt: missing technical context/corrections 32%; Claude slow/hanging/excessive 17%; got enough help to continue alone 7%; want to take next step themselves 7%; changed requirements 5%.
- Internal hardest tasks: success rate doubled Aug→Dec 2025 while human interventions per session fell 5.4 → 3.3.
- API: 80% of tool calls come from agents with at least one safeguard (footnote: an upper bound, as the classifier overestimated human involvement); 73% appear to have a human in the loop in some way; "only 0.8% of actions appear to be irreversible (such as sending an email to a customer)"; human involvement 87% of tool calls on minimal-complexity tasks vs 67% on high-complexity tasks. Software engineering ≈50% of agentic activity; healthcare/finance/cyber emerging.
- Recommendations: train models to recognise and communicate their own uncertainty; design for visibility + intervention rather than mandated approval patterns; policymakers should not prescribe interaction patterns.
(b) "Claude Code auto mode" (Anthropic Engineering, John Hughes, 25 Mar 2026). URL: https://www.anthropic.com/engineering/claude-code-auto-mode
- "Claude Code users approve 93% of permission prompts" → "approval fatigue".
- Two-stage transcript classifier (Sonnet 4.6): fast single-token filter, then chain-of-thought only on flagged actions. Real traffic n=10,000: stage-1 FPR 8.5% → full pipeline 0.4% FPR; real over-eager actions n=52: FNR 17%; synthetic exfiltration n=1,000: FNR 5.7%.
- A block returns to the agent as a tool result telling it to find a safer path; escalation to the human only after "3 consecutive denials or 20 total"; headless mode terminates instead.
(c) "Auto mode is now the default in Claude Code" (claude.com blog, 7 Aug 2026; Conner Phillippi et al.). URL: https://claude.com/blog/auto-mode-default-in-claude-code
- "users approve 97% of permission prompts in Claude Code"; by contrast "when Claude presents a plan for approval, users reject 39% of them. But for individual permissions requests, the rejection rate is only 3%." 25% of interactive sessions start in bypass-permissions mode.
- Hidden-probe study, 1,053 paid testers (one dangerous command substituted into a prompt mid-session, never executed): "The testers caught the dangerous command just 13.6% of the time (143 of 1,053), while auto mode blocked 89% of the same commands (937 of 1,053)." "Head to head, auto mode blocked 800 commands that a human approved, while humans blocked only 6 that auto mode allowed." Humans "blocked about 17% of dangerous commands early in a session, dropping to about 5% after 50 or more prior prompts"; classifier rate flat. (Testers knew they were in a study but not which behaviour was measured.)
- Session level: 6.3% of manually-approved sessions contained an unrequested harmful action (severity ≥7) vs 2.4% of auto-mode sessions. 0/720 prompt-injection attempts succeeded. Caveat: still recommends human review of high-stakes production-infrastructure changes.
(d) "Beyond permission prompts" (Anthropic Engineering, 20 Oct 2025). URL: https://www.anthropic.com/engineering/claude-code-sandboxing — "sandboxing safely reduces permission prompts by 84%".
- Implication: the strongest primary evidence for the owner's philosophy — per-item human approval degrades to rubber-stamping (17% → 5% catch rate within one session), so structural containment (sandbox, reversible actions, classifier, action ledger) should carry routine safety, and the human queue must stay short and reserved for the few items a classifier marks irreversible or outside the trust boundary.

### A5. When should an agent ask? (learning-to-defer, selective prediction, clarification)
- KnowNo — Ren, Dixit, ... Zeng, Majumdar, "Robots That Ask For Help: Uncertainty Alignment for LLM Planners" (CoRL 2023 oral; arXiv:2307.01928, v1 4 Jul 2023). Conformal prediction over the planner's multiple-choice options; asks only when the calibrated prediction set has >1 option. Paper conclusion: "achieves user-specified task completion levels consistently while reducing human help by 10−24% compared to baseline approaches that lack formal assurances"; multi-step: help rate −14% step-wise, −8% trial-wise; an uncalibrated baseline at ε=0.25 needed a step-wise help rate of 87%. URL: https://arxiv.org/abs/2307.01928
- CoDoC — Dvijotham, Winkens, ... Karthikesalingam, "Enhancing the reliability and accuracy of AI-enabled diagnosis via complementarity-driven deferral to clinicians", Nat Med 2023;29(7):1814-1820, doi:10.1038/s41591-023-02437-x, PMID 37460754. Learned deferral between AI and clinical workflow: UK breast screening vs double reading with arbitration — "reduced false positives by 25% at the same false-negative rate, while achieving a 66% reduction in clinician workload"; TB triage 5–15% fewer FPs for 3 of 5 commercial AIs. URL: https://pubmed.ncbi.nlm.nih.gov/37460754/
- Ambig-SWE — Vijayvargiya, Zhou, Yerukola, Sap, Neubig, "Interactive Agents to Overcome Ambiguity in Software Engineering" (ICLR 2026; arXiv:2502.13069, v1 18 Feb 2025). "models struggle to distinguish between well-specified and underspecified instructions", but interacting on underspecified inputs improves performance "up to 74% over the non-interactive settings". URL: https://arxiv.org/abs/2502.13069
- Edwards & Schuster, "Ask or Assume? Uncertainty-Aware Clarification-Seeking in Coding Agents" (arXiv:2603.26233, v1 27 Mar 2026, v3 7 Sep 2026). A separate "Intent Agent" decides (binary tool) whether information is missing, decoupled from the executor. Claude Sonnet 4.5 on underspecified SWE-bench Verified: no asking 54.8%; single-agent uncertainty-aware 61.2%; multi-agent scaffold 69.4%; fully specified 70.8% (forced-ask baseline 70.4%). Asked on 62.4% of easy vs 71.7% of medium tasks (all tasks were underspecified, so asking was usually warranted). URL: https://arxiv.org/abs/2603.26233
- Bonagiri, Kumaraguru, Nguyen, Plaut, "Check Yourself Before You Wreck Yourself: Selectively Quitting Improves LLM Agent Safety" (arXiv:2510.16492, v1 18 Oct 2025). ToolEmu, 12 LLMs: explicit quit instruction raised safety +0.39 on a 0–3 scale (+0.64 proprietary) at −0.03 helpfulness. URL: https://arxiv.org/abs/2510.16492
- Matsnev, "Uncertainty Decomposition for Clarification Seeking in LLM Agents" (arXiv:2606.19559, 17 Jun 2026; single author, preprint). Prompt-based split of action confidence vs request (specification) uncertainty; clarification F1 on ALFWorld-Clarification +73% vs ReAct+UE, +36% vs UAM, averaged over 5 backbones. URL: https://arxiv.org/abs/2606.19559
- Kobalczyk, Astorga, Liu, van der Schaar, "Active Task Disambiguation with LLMs" (arXiv:2502.04485, Feb 2025): frames asking as Bayesian experimental design — choose the question with maximal expected information gain over the space of viable solutions. Abstract gives no headline number. URL: https://arxiv.org/abs/2502.04485
- Implication: escalate an item only when (a) a separate checker judges the specification itself to be missing or ambiguous (not merely that the agent is unsure how to act) and (b) the answer would change the chosen route (value of information); calibrate that trigger against logged outcomes, since asking only in calibrated cases cuts asks 10–66% in the controlled studies above without losing accuracy, and models left alone are poor at telling when information is missing.

### A6. Approval / alert fatigue — what happens to review quality when the queue is large
- van der Sijs, Aarts, Vulto, Berg, "Overriding of drug safety alerts in computerized physician order entry", JAMIA 2006;13(2):138-47, PMID 16357358 (review of 17 papers): "Drug safety alerts are overridden by clinicians in 49% to 96% of cases"; error-producing conditions = low specificity, low sensitivity, unclear content, needless workflow disruption.
- Isaac et al., "Overrides of medication alerts in ambulatory care", Arch Intern Med 2009;169(3):305-11, PMID 19204222: 233,537 alerts, 2,872 clinicians — accepted only 9.2% of drug-interaction alerts and 23.0% of allergy alerts; high-severity accepted 10.4%; if the patient had previously received the drug, OR for acceptance 0.03.
- Nanji et al., "Medication-related clinical decision support alert overrides in inpatients", JAMIA 2018;25(5):476-81, PMID 29092059: 73.3% overridden; ~60% of overrides appropriate — but renal (2.2% appropriate) and age-based (26.4%) overrides were mostly inappropriate: the important alerts drown with the noisy ones.
- Ancker et al., "Effects of workload, work complexity, and repeated alerts on alert fatigue in a clinical decision support system", BMC Med Inform Decis Mak 2017;17:36, PMID 28395667 (112 primary-care clinicians, 2010–2013): ~¼ of drug alerts and ⅓ of reminders were repeats for the same patient in the same year; "Likelihood of reminder acceptance dropped by 30% for each additional reminder received per encounter, and by 10% for each five percentage point increase in proportion of repeated reminders"; no effect of workload per se.
- Embi & Leonard, JAMIA 2012;19(e1):e145-8, PMID 22534081 (RCT, 178 physicians, 36 weeks, clinical-trial recruitment alerts): response fell 2.7% per time period; still 30–40% after 36 weeks.
- Akhawe & Felt, "Alice in Warningland" (USENIX Security 2013), >25 million warning impressions: users clicked through ~1/10 (Firefox) and ~1/4 (Chrome) of malware/phishing warnings, 1/3 of Firefox SSL warnings but 70.2% of Chrome SSL warnings — warning design and false-alarm history drive compliance. URL: https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe
- Alahmadi, Axon, Martinovic, "99% False Positives: A Qualitative Study of SOC Analysts' Perspectives on Security Alarms" (USENIX Security 2022; survey n=20, interviews n=21): practitioners confirm very high FP rates; most "FPs" are benign true triggers; asks for alarms that are Reliable, Explainable, Analytical, Contextual, Transferable. (Title's "99%" is a participant quote, not a measured rate.) URL: https://www.usenix.org/conference/usenixsecurity22/presentation/alahmadi
- Plus the Anthropic 1,053-tester probe (A4c): catch rate 17% → 5% after 50+ prompts in one session.
- Implication: every non-essential item in the daily digest lowers the chance the owner reads the essential one (−30% acceptance per extra alert in Ancker); the digest must be capped, deduplicated (no repeats of an item already defaulted), ranked by consequence, and each item must carry its context and recommended route so it can be judged in seconds.

### A7. "Silence means consent after a deadline" — engineering precedents
- Apache Software Foundation, lazy consensus.
  - Glossary (https://www.apache.org/foundation/glossary.html): "A decision-making policy which assumes general consent if no responses are posted within a defined period."
  - Community "Lazy Consensus" / "Decision Making" pages (https://community.apache.org/committers/lazyConsensus.html; .../decisionMaking.html), verbatim: "Lazy consensus means that you don't need to get explicit approval to proceed, but you need to be prepared to listen if someone objects." "Lazy consensus is achieved by stating your intent on a public email, and waiting an appropriate amount of time (usually 72 hours) for anyone to object." "Silence indicates consent, and after that time has passed, you can assume that nobody objects, and proceed with your plan." "Objections to the plan should be accompanied by a legitimate reason, and be open to discussing possible alternative approaches." Formal votes are kept for where a 'feel' for consensus is not enough (new committers, releases).
  - Voting page (https://www.apache.org/foundation/voting.html): "Voting periods should generally run for at least 72 hours to provide an opportunity for all concerned persons to participate, regardless of their geographic location." Example lazy-consensus mail: "if no-one objects within three days, I'll assume lazy consensus and commit it." Code-change vetoes need "a technical justification ... A veto without a justification is invalid and has no weight."
  - So the 72 h is a convention ("usually 72 hours"; votes "generally ... at least 72 hours"), motivated by time zones — not a hard bylaw.
- IETF. RFC 2026 (Bradner, Oct 1996) §6.1.2: Last Call by mail to IETF-Announce; "The Last-Call period shall be no shorter than two weeks except in those cases where the proposed standards action was not initiated by an IETF Working Group, in which case the Last-Call period shall be no shorter than four weeks." (https://www.rfc-editor.org/rfc/rfc2026.html). Counter-weight — RFC 7282 (Resnick, Jun 2014) "On Consensus and Humming in the IETF": "Lack of disagreement is more important than agreement"; "Rough consensus is achieved when all issues are addressed, but not necessarily accommodated" — silence is not consent; unaddressed objections block regardless of headcount. (https://www.rfc-editor.org/rfc/rfc7282.html)
- Rust RFC process (https://github.com/rust-lang/rfcs/blob/master/README.md): "The FCP lasts ten calendar days, so that it is open for at least 5 business days"; motion carries a disposition (merge/close/postpone); "Before actually entering FCP, all members of the subteam must sign off"; if "substantial new arguments or ideas are raised, the FCP is canceled".
- Amazon (Bezos). 2015 shareholder letter (8-K EX-99.1, filed 5 Apr 2016, https://www.sec.gov/Archives/edgar/data/1018724/000119312516530910/d168744dex991.htm): "Some decisions are consequential and irreversible or nearly irreversible – one-way doors – and these decisions must be made methodically, carefully, slowly, with great deliberation and consultation ... Type 1 ... But most decisions aren't like that – they are changeable, reversible – they're two-way doors ... Type 2 decisions can and should be made quickly by high judgment individuals or small groups." Large organisations wrongly apply the Type 1 process to Type 2 decisions → "slowness, unthoughtful risk aversion, failure to experiment sufficiently". 2016 letter (8-K EX-99.1, filed 12 Apr 2017, .../000119312517120198/d373368dex991.htm): "Many decisions are reversible, two-way doors. Those decisions can use a light-weight process"; decide "with somewhere around 70% of the information you wish you had. If you wait for 90%, in most cases, you're probably being slow"; "disagree and commit"; "Recognize true misalignment issues early and escalate them immediately."
- Architecture Decision Records — Michael Nygard, "Documenting Architecture Decisions", Cognitect blog, 15 Nov 2011 (https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions): short text file per decision with Title, Context ("the forces at play"), Decision ("We will…"), Status (proposed/accepted/deprecated/superseded), Consequences; old ADRs are never altered — a reversed decision is marked superseded. Motivation: without the rationale, newcomers "blindly accept" or "blindly change" decisions.
- Implication: our 24 h default is shorter than every precedent (ASF 72 h, Rust 10 days, IETF 2–4 weeks), and all of them (i) announce a concrete intended action with a deadline, (ii) allow any justified objection to stop it, and (iii) apply only to reversible matters (ASF uses formal votes for releases/people; Bezos reserves the slow path for one-way doors). So: auto-decide after 24 h only for two-way-door items, write each as an ADR-style record (context, options, chosen route, consequences, reversal path) marked "accepted-by-default", let a later owner objection supersede it, and keep one-way-door items (external publication, clinical-safety claims, spending, deletion of data) out of the silent-default path.

## B. Simulation-first method/tool validation

### B1. ADEMP — Morris TP, White IR, Crowther MJ, "Using simulation studies to evaluate statistical methods", Stat Med 2019;38(11):2074-2102, doi:10.1002/sim.8086, PMID 30652356, PMC6492164 (open access)
- Plan and report every simulation as Aims; Data-generating mechanisms (resample vs parametric; based on real data or not; factors and levels; factorial vs one-at-a-time); Estimands/targets; Methods; Performance measures ("List all performance measures to be estimated, justifying their relevance", explicit formulae for less-used ones).
- Choose nsim to reach an acceptable Monte Carlo SE for the key measures and report MCSE with every performance estimate. E.g. MCSE(coverage) = √(C(1−C)/nsim); keeping it ≤0.5% in the worst case (C=50%) needs nsim = 10,000; their worked example needed 1,600 repetitions for MCSE(bias) < 0.005. Results should not be shown more precisely than the MCSE supports.
- Coding rules: separate scripts for simulating/analysing data vs analysing the estimates; set the RNG seed once per repetition and store RNG states; separate streams when parallel; publish code.
- Review of Stat Med vol 34 (2015): 199/264 (75%) research articles included a simulation; of 100 sampled, 93 did not mention Monte Carlo SEs (only 7 presented them).
- They recommend writing a detailed simulation protocol before coding, to prevent selective reporting and force ADEMP to be explicit. Template follow-up: Siepe, Bartoš, Morris, Boulesteix, Heck, Pawel, "ADEMP-PreReg" (Psychol Methods, online 14 Nov 2024, doi:10.1037/met0000695, PMID 39541533) — in 100 simulation papers (2021–22) many omitted nsim justification, MCSE or code.
- Implication: every engine-built tool should ship an ADEMP protocol (written and hashed before the simulation runs) plus a performance table with MCSEs; "validated on simulated data" means pre-specified bias/coverage/type-I error targets met within MCSE, not "the code ran".

### B2. Plasmode simulation
- Vaughan, Divers, Padilla, Redden, Tiwari, Pomp, Allison, "The use of plasmodes as a supplement to simulations", Comput Stat Data Anal 2009;53(5):1755-66, doi:10.1016/j.csda.2008.02.032, PMID 20161321: "Plasmodes are data sets that are generated by natural biologic processes, under experimental conditions that allow some aspect of the truth to be known"; simulations "are only as good as our understanding of the underlying mechanisms". Admixture methods that all did well on simple data diverged greatly on a three-founder plasmode.
- Franklin, Schneeweiss, Polinski, Rassen, "Plasmode simulation for the evaluation of pharmacoepidemiologic methods in complex healthcare databases", Comput Stat Data Anal 2014;72:219-26, doi:10.1016/j.csda.2013.10.018, PMID 24587587: "Ordinary simulation approaches ... do not capture important features of healthcare claims." Method: resample the observed covariate and exposure data "without modification ... to preserve the associations among these variables"; simulate outcomes from a true treatment effect chosen by the investigator and the baseline hazard estimated from the real data (Medicare + Caremark statin cohort). Lets high-dimensional PS variable selection be evaluated, which ordinary simulation could not.
- Applied example: Desai et al., Pharmacoepidemiol Drug Saf 2019;28(6):879-86, PMID 31020732 — plasmode, 500 cohorts × 10,000 patients: bootstrap CIs after 1:1 PS matching over-covered (98–100%) vs 95–96% for the standard approach.
- Guidance: Schreck, Slynko, Saadati, Benner, "Statistical plasmode simulations — Potentials, challenges and recommendations", Stat Med 2024;43(9):1804-25, doi:10.1002/sim.10012, PMID 38356231 — notes there were "no explicit guidelines" and gives a step-wise generation and reporting procedure.
- Implication: the order is synthetic first (unit and boundary tests), then plasmode on the first real dataset a user uploads (keep their covariates/exposure, inject a known effect) before any real-effect estimate is reported; this tests the tool on the real covariance structure without needing a known truth.

### B3. OHDSI negative controls, synthetic positive controls, empirical calibration
- Schuemie, Ryan, DuMouchel, Suchard, Madigan, "Interpreting observational studies: why empirical calibration is needed to correct p-values", Stat Med 2014;33(2):209-18, doi:10.1002/sim.5925, PMID 23900808. Negative controls = drugs not believed to cause the outcome; fit the empirical null of their estimates; calibrated p-values account for random + systematic error. Found "the majority of observational studies would declare statistical significance when no effect is present"; calibration reduced spurious results to the nominal 5%; "at least 54% of findings with p < 0.05 are not actually statistically significant".
- Schuemie, Hripcsak, Ryan, Madigan, Suchard, "Empirical confidence interval calibration for population-level effect estimation studies in observational healthcare data", PNAS 2018;115(11):2571-7, doi:10.1073/pnas.1708282114, PMID 29531023. "CIs require positive controls, which we synthesize by modifying negative controls"; CI calibration "restores nominal characteristics, such as 95% coverage" and reduced disagreement between conflicting replications (dabigatran/warfarin GI bleeding; SSRIs/upper GI bleeding). Systematic error does not shrink with sample size, so it grows in relative importance as databases get larger.
- Schuemie, Ryan, Hripcsak, Madigan, Suchard, "Improving reproducibility by using high-throughput observational studies with empirical calibration", Phil Trans R Soc A 2018;376:20170356, PMID 30082302: 17,718 hazard ratios for all depression treatments with control hypotheses; agreed with 4 of 5 trial findings; no p=0.05 cut-off artefact unlike the literature.
- OHDSI Methods Benchmark — Schuemie, Cepeda, Suchard, ... Hripcsak, "How Confident Are We about Observational Findings in Healthcare: A Benchmark Study", Harv Data Sci Rev 2020;2(1), doi:10.1162/99608f92.147cc28e, PMID 33367288, PMC7755157. Gold standard = 200 real negative controls (4 exposures × 4 outcomes, 8 strata) + 600 synthetic positive controls (outcomes injected into negative controls at true RR 1.5, 2, 4, keeping confounding via an L1-regularised outcome model; Book of OHDSI ch. 18); 28 variants of 5 designs × 4 databases → 179,200 estimates. "in most contexts, only half of the 95% confidence intervals we calculated contain the corresponding true effect size"; most methods reject the null "more often than not when the null hypothesis is in fact true"; calibration largely restores 95% coverage / 5% type-I error; calibrated SCCS best (coverage 94–95% after calibration, AUC 0.95–0.98). They "strongly recommend including negative and positive controls in each observational study". Book of OHDSI suggests 50–100 negative controls. URL: https://pmc.ncbi.nlm.nih.gov/articles/PMC7755157/
- EUMAEUS — Schuemie, Arshad, Pratt, ... ## C. Data requirement specifications and data availability

### C1. Which format for a machine-checkable "data requirement" (fields, types, units, codes, missingness)?
- Frictionless Data Package v2 / Table Schema v2 (Open Knowledge Foundation; "The Data Package (v2) standard has been released on June 26, 2024"; https://datapackage.org/standard/table-schema/). Field: name (required), type (string, number, integer, boolean, object, array, list, datetime, date, time, year, yearmonth, duration, geopoint, geojson, any), format, title, description, example, constraints (required, unique, minLength/maxLength, minimum/maximum, exclusiveMinimum/Maximum, pattern, enum, jsonSchema), categories (+ categoriesOrdered), field-level missingValues that override schema-level ones and may carry labels (value + label), rdfType (semantic URI); table-level primaryKey and foreignKeys. No dedicated unit property (units go in description/rdfType or a custom property). Validator: Frictionless Framework (`frictionless validate`, row/field-level error reports; https://framework.frictionlessdata.io/).
- MLCommons Croissant — Akhtar, Benjelloun, ... Zhang (31 authors), "Croissant: A Metadata Format for ML-Ready Datasets", NeurIPS 2024 Datasets & Benchmarks (arXiv:2403.19546, v1 28 Mar 2024). Spec 1.0 (2024-03-01): schema.org-based, four layers (dataset metadata, resources = FileObject/FileSet, RecordSets/Fields with dataType, source, references, semantics such as splits/labels). Croissant 1.1 (spec dated 2026-01-29; announced 12 Feb 2026, https://mlcommons.org/2026/02/croissant-1-1-standard/): PROV-O provenance at dataset/file/record level, links to external vocabularies, DUO/ODRL usage policies, multi-dimensional arrays; "700K datasets now carry Croissant metadata" (Hugging Face, Kaggle, OpenML embed it). Neither 1.0 nor 1.1 defines units, value constraints (min/max/enum/pattern), missing-value semantics or required/optional fields — it describes an existing dataset, not a requirement. Croissant-RAI — Jain, Akhtar, Giner-Miguelez et al., arXiv:2407.16883 (Jun 2024): RAI documentation extension (collection, annotation, intended use, limitations, biases).
- OMOP CDM (OHDSI; site states "The current OMOP CDM version is CDM v5.5"; https://ohdsi.github.io/CommonDataModel/): a full target data model with standardized vocabularies; units are mapped to Standard Concepts in the Unit domain (unit_concept_id), observation_period defines when absence of a record means absence of the event. Quality: Blacketer, DeFalco, Ryan, Rijnbeek, JAMIA 2021;28(10):2251-7, PMID 34313749 — Data Quality Dashboard runs "over 3300 configurable data quality checks" (conformance, completeness, plausibility). Right for EHR/claims tools (and makes OHDSI negative-control calibration possible); too heavy for a researcher uploading one trial or cohort spreadsheet.
- Fit judgement (mine): publish each tool's requirement as a Frictionless Table Schema v2 (one schema per table, plus Data Package for multi-table) — the only one of the three that expresses required/optional, types, ranges, enums/categories, labelled missing codes and keys, and has an off-the-shelf validator. Add custom properties for units (UCUM code) and code systems (e.g. LOINC/SNOMED/ICD/ATC value sets via rdfType or a "codelist" URI), plus tool-level rules a table schema cannot express (minimum N, events per arm, follow-up length, allowed % missing per field) in a small separate rules file. Emit Croissant 1.1 when a dataset is published or shared (discovery, provenance, usage policy); accept OMOP CDM v5.4/5.5 as an alternative input route for EHR/claims tools.
- Implication: the data-requirement spec is a Table Schema the upload is validated against byte-for-byte before the tool runs; the same schema drives the simulator that generates the stage-1 synthetic data, so simulated and real inputs cannot drift apart.

## A. Escalation and human-in-the-loop

**A1. Feng, McDonald, Zhang, "Levels of Autonomy for AI Agents"** (arXiv:2506.12469, 14 Jun 2025; Knight First Amendment Institute) https://arxiv.org/abs/2506.12469
- Autonomy is "a deliberate design decision, separate from its capability and operational environment". There are five levels, named for the user's role: L1 operator, L2 collaborator, L3 consultant, L4 approver, L5 observer. At L5 the user has only "an emergency off-switch".
- At L4 the user is contacted only for "a blocker it cannot resolve on its own": a failure state, missing credentials, or "signing off on consequential actions". The user decides in advance what needs approval, and the plan is shown "only … for transparency". Their example is a research-report agent that skips sources it cannot reach and re-plans when a key is missing.
- The paper names the risk directly: "meaningless rubber stamping". It proposes "assisted evaluation": add user involvement step by step until the agent meets a success threshold, and certify the agent at that level.
- **Implication:** the owner's policy is L4 for a declared list of decision classes and L5 everywhere else. Set each class's level from measured success, not by fiat.

**A2. Microsoft Magentic-UI** (Mozannar … Amershi, arXiv:2507.22358, 30 Jul 2025) https://arxiv.org/abs/2507.22358
- Mechanisms: co-planning, co-tasking, action guards, answer verification, memory, multi-tasking. Action guards sort actions three ways: "always irreversible" (upload) goes to the human, "never irreversible" (scroll) runs automatically, and "maybe" (click) goes to an LLM judge.
- On GAIA validation (162 tasks) the agent alone completed 30.3%. With a simulated user that had side information it reached 51.9% ("by 71%"), while asking for help in only 10% of tasks. With a smarter simulated user it reached 42.6%, asking in 4.3% of tasks.
- In a 12-user study, people wanted approval for payments but not for trivial steps, and asked for "a third option" beyond approve/reject. None of 24 adversarial scenarios succeeded with guards and sandbox on.
- **Implication:** a few targeted asks capture most of the gain. Tie approval to how reversible an action is. Each item should offer approve, reject, or "do X instead".

**A3. OpenAI, Shavit, Agarwal, Brundage et al., "Practices for Governing Agentic AI Systems"** (Dec 2023) https://cdn.openai.com/papers/practices-for-governing-agentic-ai-systems.pdf
- Approval breaks down "when the user must approve many decisions and thus must make each approval quickly". The paper asks how to keep approval from becoming a "rubber stamp", and allows agents to "time out" until a human reauthorises them.
- Defaults: "err toward actions that are the least disruptive". Ask for clarification "especially when it may change their actions", but not "too frequently".
- On legibility: "a ledger of actions taken by the agent" is "a lighter-touch method than requiring human approval", and "Actions that can only be reviewed after the fact should be more easily reversible than those that require approval." Graceful shutdown must always be available, including for sub-agents.
- **Implication:** the 24 h default is defensible only for reversible actions logged with their reasoning and a way to revert.

**A4. Anthropic: how much autonomy users grant in practice**
- (a) "Measuring AI agent autonomy in practice", 18 Feb 2026, https://www.anthropic.com/research/measuring-agent-autonomy
  - Full auto-approve is used in about 20% of sessions by new users and over 40% at 750+ sessions. Experienced users also interrupt more (5% → about 9% of turns), so oversight shifts from approving each action to monitoring.
  - "Claude Code pauses for clarification more often than humans interrupt it."
  - Why it stops itself: to offer a choice between approaches 35%, gather diagnostics 21%, clarify a vague request 13%, get missing credentials 12%, get approval before acting 11%.
  - Only 0.8% of API actions appear irreversible.
- (b) "Claude Code auto mode", 25 Mar 2026, https://www.anthropic.com/engineering/claude-code-auto-mode
  - "Claude Code users approve 93% of permission prompts."
  - A two-stage classifier has a 0.4% false-positive rate (n=10,000) and missed 17% of real over-eager actions (n=52).
  - Blocked actions go back to the agent, which must "find a safer path". The human is involved only after "3 consecutive denials or 20 total".
- (c) "Auto mode is now the default", 7 Aug 2026, https://claude.com/blog/auto-mode-default-in-claude-code

  - In a study of 1,053 paid testers, humans caught a swapped-in dangerous command 13.6% of the time (143); the classifier caught 89% (937). Human catch rates fell from about 17% early in a session to about 5% after 50+ prompts.
  - Unrequested harm at severity ≥7 appeared in 6.3% of manual-approval sessions versus 2.4% in auto mode.
- (d) Sandboxing cut permission prompts by 84% (Anthropic engineering blog, 20 Oct 2025).
- **Implication:** this is the strongest support for the owner's stance. People review plans well and individual actions badly. Let containment and classifiers carry routine safety, and spend owner attention on plan-level decisions.

**A5. When should an agent ask?**
- **KnowNo** (Ren et al., CoRL 2023, arXiv:2307.01928): asks only when conformal prediction leaves more than one plausible plan. It meets a target success level "while reducing human help by 10−24%" against baselines.
- **CoDoC** (Dvijotham et al., Nat Med 2023;29:1814-20, PMID 37460754): learns when to defer from AI to clinicians. In breast screening it cut false positives 25% at the same false-negative rate and clinician workload 66%.
- **Ambig-SWE** (Vijayvargiya et al., ICLR 2026, arXiv:2502.13069): models "struggle to distinguish between well-specified and underspecified instructions". Asking on underspecified tasks improves results by "up to 74%".
- **Ask or Assume?** (Edwards & Schuster, arXiv:2603.26233, 2026, preprint): a separate agent that decides whether information is missing lifted Claude Sonnet 4.5 from 54.8% (no asking) to 69.4%, close to the 70.8% it reached with full information.
- **Selective quitting** (Bonagiri et al., arXiv:2510.16492): an explicit quit option raised safety by 0.39 on a 0–3 scale, at a helpfulness cost of only 0.03.
- **Implication:** escalate only when a separate checker finds the specification itself missing or ambiguous, and the answer would change the chosen route. Calibrate that trigger against logged outcomes.

**A6. Approval and alert fatigue**
- Drug-safety alerts were overridden in 49–96% of cases (van der Sijs, JAMIA 2006, PMID 16357358).
- Only 9.2% of drug-interaction alerts were accepted (Isaac, Arch Intern Med 2009, PMID 19204222; 233,537 alerts).
- 73.3% of alerts were overridden, and only 2.2% of renal-dose overrides were appropriate (Nanji, JAMIA 2018, PMID 29092059).
- Ancker et al. (BMC Med Inform Decis Mak 2017, PMID 28395667): acceptance "dropped by 30% for each additional reminder received per encounter, and by 10% for each five percentage point increase in proportion of repeated reminders."
- Security: users clicked through 70.2% of Chrome SSL warnings (Akhawe & Felt, USENIX Security 2013).
- **Implication:** every extra or repeated digest item lowers the odds the critical one gets read. Cap and rank the digest, never repeat items, and attach the context each needs.

**A7. Precedents for "silence means consent"**
- **Apache Software Foundation.** "Lazy consensus is achieved by stating your intent on a public email, and waiting an appropriate amount of time (usually 72 hours) for anyone to object." "Silence indicates consent." Objections need "a legitimate reason". Votes "should generally run for at least 72 hours … regardless of their geographic location". Releases and new committers still need formal votes. (community.apache.org/committers/lazyConsensus.html; apache.org/foundation/voting.html) The 72 h is a convention, not a bylaw.
- **IETF.** RFC 2026 §6.1.2: Last Call lasts "no shorter than two weeks" (four weeks for non-working-group documents). RFC 7282: "Lack of disagreement is more important than agreement."
- **Rust RFCs.** The final comment period "lasts ten calendar days", and is cancelled if substantial new arguments appear.
- **Amazon.** 2015 shareholder letter (SEC 8-K EX-99.1, 5 Apr 2016): one-way doors "must be made methodically, carefully, slowly"; two-way doors "can and should be made quickly by high judgment individuals or small groups". 2016 letter: decide with "around 70% of the information you wish you had".
- **Architecture Decision Records** (Nygard, 15 Nov 2011): each record has Context, Decision, Status and Consequences. Records are superseded, never edited.
- **Implication:** 24 h is shorter than every precedent, and all of them restrict silent consent to reversible matters and let a reasoned objection reopen the decision. Default silently only on two-way doors, and record each as an ADR marked "accepted by default" that a later objection can supersede.

## B. Simulation-first validation

**B1. ADEMP** (Morris, White, Crowther, Stat Med 2019;38:2074-102, PMID 30652356)
- Pre-specify Aims, Data-generating mechanisms, Estimands, Methods and Performance measures, and write the protocol before coding.
- Choose the number of repetitions to hit a target Monte Carlo standard error (MCSE). For coverage, MCSE = √(C(1−C)/n), so staying ≤0.5% in the worst case needs n = 10,000. Report the MCSE with every estimate.
- In 100 Stat Med simulation papers, 93 did not mention MCSE. A preregistration template exists: ADEMP-PreReg (Psychol Methods 2024, PMID 39541533).
- **Implication:** "validated on simulated data" means a pre-registered protocol whose bias, coverage and type-I error targets were met within MCSE.

**B2. Plasmode simulation**
- Vaughan et al. (CSDA 2009, PMID 20161321): plasmodes are datasets "generated by natural biologic processes, under experimental conditions that allow some aspect of the truth to be known".
- Franklin et al. (CSDA 2014, PMID 24587587): resample real claims covariates and exposures "without modification", then simulate outcomes from a chosen true effect. "Ordinary simulation approaches … do not capture important features of healthcare claims." Guidance: Schreck et al., Stat Med 2024 (PMID 38356231).
- **Implication:** when a user uploads real data, run a plasmode check before reporting any real estimate.

**B3. OHDSI controls and calibration**
- Schuemie et al., Stat Med 2014 (PMID 23900808): with negative controls, most observational designs declared significance when there was no effect. "At least 54%" of published p<0.05 findings would not survive calibration.
- PNAS 2018;115:2571-7 (PMID 29531023): positive controls synthesised by injecting outcomes into negative controls enable confidence-interval calibration, restoring 95% coverage.
- OHDSI Methods Benchmark (Harvard Data Science Review 2020, PMC7755157): 200 negative and 600 synthetic positive controls (true effect 1.5, 2 or 4), 179,200 estimates. "Only half of the 95% confidence intervals … contain the corresponding true effect size." Calibration largely fixes this.
- EUMAEUS (Front Pharmacol 2022, PMID 35873596): "Most methods show large type 1 error."
- **Implication:** this gives a tool a measured error rate on the user's own real data without needing the true answer. The data spec should request negative-control outcomes.

**B4. Synthea and synthpop**
- Synthea (JAMIA 2018, PMID 29025144) generates synthetic records from disease modules; OHDSI's ETL-Synthea converts them to OMOP. Validation (Chen et al., BMC MIDM 2019, PMID 30871520) found demographics realistic but outcomes not: COPD 30-day mortality 0.7% versus 7–8% in real data, and 0% hip/knee complications versus 2.9%.
- synthpop (J Stat Softw 2016;74(11)) makes disclosure-safe copies of a real dataset. Its own guidance: "Final analyses have to be run on the original data."
- **Implication:** use Synthea only for format and plumbing tests; its outcomes are whatever the module author wrote. Test correctness on our own data-generating mechanisms. Never present synthetic results as evidence.

## C. Data requirements and availability

**C1. Format fit**
- **Frictionless Table Schema v2** (26 Jun 2024): types, required/unique, min/max, pattern, enum, categories, labelled missing values per field, keys and semantic types. It has a validator (`frictionless validate`) but no property for units.
- **MLCommons Croissant** (NeurIPS 2024, arXiv:2403.19546; v1.1 in 2026 adds provenance and usage policies; MLCommons reports 700K datasets) describes datasets that already exist. It has no constraints, units, missingness rules or required fields. Croissant-RAI (arXiv:2407.16883) adds responsible-AI documentation.
- **OMOP CDM** (v5.5) is a full target data model. OHDSI's Data Quality Dashboard runs more than 3,300 checks (JAMIA 2021, PMID 34313749).
- **Verdict:** publish each tool's requirement as a Table Schema v2, with custom properties for units (UCUM) and code lists and a small rules file for study-level minimums. Validate uploads against it, and generate stage-1 simulated data from the same schema. Emit Croissant when data is published, and accept OMOP for EHR and claims tools.

**C2. Does "available on request" produce data?**
- Gabelica, Bojčić, Puljak (J Clin Epidemiol 2022;150:33-41, PMID 35654271): of 1,792 authors who promised to share, 1,669 (93%) ignored or declined the request. Only 123 (6.8%) supplied data.
- Tedersoo et al. (Sci Data 2021;8:192): 39.4% of requests succeeded, 19.4% were declined and 41.3% went unanswered. Papers stating "upon request" delivered 42.3%, versus 38.3% for papers with no such statement.
- Vines et al. (Curr Biol 2014): the odds a dataset still exists fall 17% per year.
- **Implication:** never block on authors; treat data requests as background tasks with a deadline.

**C3. How often papers share data or code**
- Hamilton et al. (BMJ 2023;382:e075767; 2.1M articles): 8% declared public data but only 2% actually had it; public code was under 0.5%.
- Sofi-Mahmudi et al. (medRxiv 2024; 2.0M open-access medical articles): 7.6% shared data, 1.4% shared code.
- Lawrimore et al. (bioRxiv Jul 2026; 951,949 articles from 2024–25): 8.7% shared data openly.
- Sounack et al. (arXiv:2604.06212): 12.2% of prediction-model papers had a code statement.
- **Implication:** methods must be re-implemented from text and checked against the paper's numbers. Simulation-first followed by user upload is forced by the evidence, not optional.

## D. Taxonomies of AI-scientist autonomy
- Wei et al. (arXiv:2508.14111, Oct 2025): L1 computational oracle, L2 automated research assistant, L3 autonomous scientific partner (runs the full cycle), L4 generative architect.
- Ding et al. (arXiv:2608.05179, Jun 2026, preprint): L0 assistive through L4 closed-loop (split into L4-m, triggered by metrics, and L4-v, externally validated) and L5 open-ended. Of 24 systems, 83% release code but only 38% release traces and 38% verify novelty. Wet-lab work and prospective trials need "external oracles".
- What end-to-end systems achieve today:
  - Kosmos (arXiv:2511.02824), working on a supplied dataset: 79.4% of its statements were judged accurate.
  - otto-SR (medRxiv v4, 2026): screening sensitivity 96.7% versus 81.7% for humans; reproduced 12 Cochrane reviews.
  - AI co-scientist (arXiv:2502.18864): its hypotheses needed human in-vitro validation.
- **Implication:** synthesis, secondary analysis, methods work and tool building can run end to end. Anything needing new patient data stops at a protocol, a data spec and a simulated power analysis.

## Design conclusions
1. Classify items by reversibility, not uncertainty. Only two-way doors get the 24 h default. One-way doors (publication, clinical-safety claims, spending, deleting data) wait.
2. The digest should be short, ranked and free of repeats. Each item gives the context, options, recommended route, consequence and how to revert.
3. A decision made alone after 24 h is re-searched, then recorded as an ADR marked "accepted by default"; an owner objection supersedes it.
4. Spend owner attention on plans (39% rejected) rather than individual actions (3% rejected).
