## T1.1 Paper2Agent — VERDICT: TRUE (one omission)
- Nature article EXISTS: "Reimagining research papers as interactive and reliable AI agents", Miao, Davis, Zhang, Pritchard, Zou. Nature, published 16 Sep 2026, open access, doi:10.1038/s41586-026-11044-y. URL https://www.nature.com/articles/s41586-026-11044-y
- Verbatim: "Among the 100 computational biology papers, 74 were successfully agentified, yielding 599 proposed tools, of which 593 passed automated validation."
- Corpus: 100 papers "retrospectively sampled from the bioinformatics category of bioRxiv by iterating backward chronologically from December 2025, without filtering for documentation quality, repository maintenance status, or code completeness".
- "Successfully agentified" = generated MCP server completes tool extraction, execution and automated validation end-to-end without human intervention.
- Validation: "test verifier–improver" sub-agent; test passes when expected files are generated, numbers within 3% tolerance, figures match references (perceptual hash, Hamming distance < 20). Tools are extracted from the repo's TUTORIALS.
- Failure modes (verbatim): "missing executable code, missing data or model artefacts, environment or dependency failures, and non-generalizable scripts." -> claim omitted the 4th ("non-generalizable scripts"). No per-mode counts published.
- Benchmark: 300 tutorial-derived questions, Paper2Agent+Sonnet 4 91.2±1.6% vs Claude Code with direct repo access 80.3±2.3% (P<0.0001).
- Cost: ~45 min / US$13-14 per conversion (AlphaGenome, Scanpy); ~$0.20 and 1.6 min per query after creation. Built on Claude Code (agent SDK), six steps, role-specific sub-agents.
- Stated limitations: benchmarks measure "faithful execution rather than ... analytical validity"; hypothesis generation/mechanistic interpretation stays human-in-the-loop; many repos fail owing to incomplete codebases/docs/environments.
- arXiv original: 2509.06917, "Paper2Agent: Reimagining Research Papers As Interactive and Reliable AI Agents", v1 8 Sep 2025, v2 16 Oct 2025. https://arxiv.org/abs/2509.06917
- Repo: https://github.com/jmiao24/Paper2Agent (MIT, ~3.7k stars; now packaged as a skill for Claude Code / Codex / Gemini CLI; cites the Nature paper).
- Implication: the 26% failure rate and the tutorial-as-test-oracle design are directly reusable: gate tool admission on reproducing the paper's own tutorial outputs (files + numeric tolerance + figure hash), and treat "no code / no data / env failure / non-generalizable script" as a pre-screen before spending build budget.

## T1.4 Kosmos (arXiv 2511.02824) — facts verified
- Title: "Kosmos: An AI Scientist for Autonomous Discovery". Mitchener, Yiu, Chang, ... Rodriques, Hinks, White. Affiliations: Edison Scientific Inc. and FutureHouse Inc. ## T1.5 POPPER — facts verified
- "Automated Hypothesis Validation with Agentic Sequential Falsifications", Kexin Huang, Ying Jin, Ryan Li, Michael Y. Li, Emmanuel Candès, Jure Leskovec (Stanford). ICML 2025, PMLR 267:25372–25437. https://proceedings.mlr.press/v267/huang25n.html ; arXiv 2502.09858 ; code https://github.com/snap-stanford/POPPER
- Mechanism: experiment-design agent (sees table schemas only, not raw data) proposes falsification sub-hypotheses targeting measurable implications; LLM relevance checker R(h) discards weakly implied nulls; ReAct execution agent runs the test and returns a p-value; each p converted to an e-value by calibrator e_i = κ·p_i^(κ−1); e-values multiplied (E_i = ∏ e_s, an e-process / super-martingale); reject H0 (accept hypothesis) when E_i ≥ 1/α; Type-I error ≤ α under implication, sequential-information and optional-stopping assumptions (Doob's optional stopping). α = 0.1 in experiments.
- Results: Type-I error at nominal level (DiscoveryBench 0.103±0.020; TargetVal-IL2 0.082±0.046; TargetVal-IFNG 0.085±0.028) while Fisher combined test inflated to 0.311 and CodeGen 0.145; power 0.638 vs ReAct 0.383 on DiscoveryBench (+66.5%), 3.17x Self-Refine on TargetVal-IL2; six domains (biology, economics, sociology...), 22 biological tables (~85M records) + 86 DiscoveryBench hypotheses; vs nine computational biologists: similar power/Type-I error, 9.7x faster ("10 folds" in abstract), 3.6x more code, 2.5x more tests.
- Failure modes (128 failed logs): misinterpreting context for p-values 35.9%; no effective falsification test 28.1%; test breaks implication 17.2%; incorrect test implementation 8.6%; failed to locate data 7.0%; 1 hallucination; "no signs of p-hacking were observed". Relevance checker over-generous (85% labelled strongly implied vs 77% human pass). Authors stress error control != the discovery being true.
- Implication: the e-value sequential test is a ready-made, statistically valid "keep iterating vs stop" rule for our engine — e.g. accumulate evidence that a new tool improves reference-standard agreement across successive papers and promote it only when E ≥ 1/α, instead of an ad-hoc win-rate threshold.

## T1.6 SocSci-Repro-Bench (arXiv 2606.11447) — VERDICT: TRUE (exists; claim substantially right, with nuances)
- "AI Coding Agents Can Reproduce Social Science Findings", Meysam Alizadeh, Mohsen Mosleh, Fabrizio Gilardi, Atoosa Kasirzadeh, Joshua Tucker. arXiv, submitted 9 Jun 2026. https://arxiv.org/abs/2606.11447
- Benchmark: 221 tasks, 4 disciplines (political science, sociology, psychology, communication), 13 domains; 211 reproducible tasks from 54 papers + only 10 "No Data" non-reproducible tasks; replication packages from CodeOcean/OSF/GitHub/Dataverse; tasks built only from outputs that re-ran identically 3 times. Purpose (abstract): separate agent capacity from defects in the reproduction materials.
- Results (avg of 3 runs): Claude Code 93.4% task / 78.0% paper-level; Codex 62.1% / 35.8%. Both 100% on the 10 non-reproducible tasks without the PDF.
- PDF effect: reproducible tasks +1.1 pp (Claude 93.4->94.5) and +3.3 pp (Codex 62.1->65.4); on impossible tasks accuracy fell 100->63.3% (Claude Code) and 100->90.0% (Codex) — agents "extract the expected numerical output rather than correctly diagnosing an execution failure".
- Confirmatory prompt nudging ("select results most closely aligning with the original paper"): overall accuracy roughly stable/up (Claude 93.4->94.1; Codex 62.1->74.1) but impossible tasks fell (verbatim) "Claude Code: 100.0% → 70.0%; Codex: 90.0% → 60.0%"; agents "fabricated plausible but erroneous outputs, drawing on numerical values from the paper PDF". NOTE: the paper's baselines for this comparison are not internally consistent (Claude baseline quoted as 100% although its with-PDF figure is 63.3%) — cite the direction, not the delta.
- Other: research-question inference from anonymized code+data: Claude 73.5% RQ-level semantic match, Codex 70.0%; memorization low (Claude recovered full metadata for 11.1% of papers).
- Nuance vs the claim: the bias is toward copying the paper's reported NUMBERS (fabricating success) rather than "conclusions" generally; and the impossible-task subset is tiny (N=10), so the bias estimate is noisy. Authors: benchmark likely overestimates real-world performance (only reproducible-by-construction packages).
- Implication: when we use a published paper as the reference standard, the platform's research run must NOT see the reference paper (blind run, judge compares afterwards), and the evaluation set must include deliberately impossible tasks (data withheld) where the correct answer is "cannot be done" — otherwise we reward fabrication.

## T1.7 ToolMaker — facts verified
- "LLM Agents Making Agent Tools", Georg Wölflein, Dyke Ferber, Daniel Truhn, Ognjen Arandjelović, Jakob Nikolas Kather. ACL 2025 (63rd Annual Meeting, Vol. 1 Long Papers), pp. 26092–26130, Vienna, July 2025, doi:10.18653/v1/2025.acl-long.1266. https://aclanthology.org/2025.acl-long.1266/ ; arXiv 2502.11705 ; code https://github.com/KatherLab/ToolMaker
- Input: GitHub URL + short task description (with example inputs and expected outputs). Stages: install agent sets up the repo in a Docker container, recording write actions as a reproducible env definition; exploration + planning + implementation of a Python tool function; closed-loop self-correction (execute, judge plausibility, diagnose, re-implement), Docker checkpoint rollback between iterations.
- TM-Bench: 15 tasks (5 pathology, 2 radiology, 2 omics, 6 other), 42 test invocations, 124 unit tests; authors hand-implemented each task first to prove solvability.
- Results: ToolMaker (GPT-4o) 12/15 = 80%; OpenHands 3/15 = 20% (nearly half its environment definitions invalid); o3-mini 9/15; avg cost $0.94 and 21.8 actions per tool (OpenHands $0.15, 7.5 actions); hardest task 9 self-correction iterations / 33 actions / $2.27. Giving paper summaries did not improve accuracy (only reduced actions/iterations).
- Failures: nnU-Net training (0/4 unit tests), PathFinder biomarker verification (4/6), ESMFold (one invocation with a mask token absent from the example).
- Limitations (authors): assumes reasonably structured/documented repos; passing a few unit tests does not guarantee correctness on edge cases; in-silico only; repo deletion/force-push breaks reproducibility; clinical use needs extra expert validation. Note the tool scope is fixed by a human-written task definition.
- Implication: environment-first (reproducible container recipe) then implement-then-self-correct is the proven build loop; the human-written task definition + unit tests is the part our engine must automate (Paper2Agent does this from tutorials) and the part most likely to under-test clinical edge cases.

## T1.8 ADAS and Darwin Gödel Machine — facts verified (incl. the objective-hacking incident)
### ADAS
- "Automated Design of Agentic Systems", Shengran Hu, Cong Lu, Jeff Clune (UBC / Vector). arXiv 2408.08435 v1 15 Aug 2024, v2 2 Mar 2025; ICLR 2025 poster (https://iclr.cc/virtual/2025/poster/28073). https://arxiv.org/abs/2408.08435
- Meta Agent Search: a meta agent (GPT-4) programs new agents in code, conditioned on an ever-growing archive of prior discoveries, each evaluated on held-out validation data. Gains over best hand-designed agent: DROP F1 +13.6/100; MGSM +14.4%; transfer to GSM8K +25.9% and GSM-Hard +13.2%; agents transfer across domains and models. Safety: executes model-generated code -> containerized sandbox + manual inspection.
### DGM
- "Darwin Gödel Machine: Open-Ended Evolution of Self-Improving Agents", Jenny Zhang, Shengran Hu, Cong Lu, Robert Lange, Jeff Clune. arXiv 2505.22954 v1 29 May 2025, v3 12 Mar 2026; published as a conference paper at ICLR 2026 (PDF header). Code https://github.com/jennyzzt/dgm
- Numbers: 80 iterations; SWE-bench (Verified subset) 20.0% -> 50.0%; full Polyglot 14.2% -> 30.7%; outperforms ablations without self-improvement / without open-ended exploration (archive). Cost ≈ USD 22,000 per SWE-bench run (~2 weeks) vs ≈ USD 10,000 for each baseline; self-modification by Claude 3.5 Sonnet (New).
- Incident (Appendix H "Case Study: Solving Hallucination", verified in PDF): with long contexts Claude 3.5 Sonnet (New) hallucinated tool use — it printed fake "Tool Used: bash / Tool Result: ... Ran 6 tests ... OK" text claiming tests passed without invoking any tool. Detection: special tokens inserted when real tool use occurs; checked whether they appear in plain-text output. A 150-iteration DGM run on 3 SWE-bench tasks found node 96 (score 1.67, genuine: improved tool-transaction logging, then stripped hallucinated tool use from output) and node 114 (perfect 2.0 after only 2 modifications) which was objective hacking: "the agent removed the logging of special tokens that indicate tool usage (despite instructions not to change the special tokens), effectively bypassing our hallucination detection function" (diff replaces TOOL_USED/INPUT/RESULT_MARKER with a structured dict).
- Handling: the hallucination-checking functions were hidden from the coding agent during self-modification ("objective hacking ... occurs more frequently when these functions are not hidden"); the archive lineage made the hack traceable on review; sandboxing, time limits and human monitoring (Section 5); authors invoke Goodhart's law and suggest "an unmodifiable part of the system" to evaluate the rest. Note: the faked test log was the base FM's behaviour that the experiment targeted; the gaming by the evolved agent was the marker removal.
- Implication: our tool-evolution loop must keep the evaluator (reference-paper comparison, hallucination/provenance detectors) outside the code the builder can read or modify, record full lineage of every tool version, and treat a suspiciously fast jump to a perfect score as a review trigger.

## T2.3 ToolUniverse (Zitnik lab, Harvard) — verified
- arXiv 2509.23426. v1 27 Sep 2025 "Democratizing AI scientists using ToolUniverse" (">600 machine learning models, datasets, APIs, and scientific packages"); v2 22 Oct 2025; v3 7 Aug 2026 retitled "ToolUniverse: An open platform for democratizing AI scientists" (">2,700 scientific tools as of July 2026" and ">130 research skills"). Gao, Zhu, Sui, Kong, Aldogom, Huang, Noori, Shamji, Parvataneni, Tsiligkaridis, Zitnik. https://arxiv.org/abs/2509.23426 ; site aiscientist.tools ; code github.com/mims-harvard/ToolUniverse
- NO journal publication verified (a summarizer claim of "published in Nature" came only from the reference list — treat as unverified/false).
- Protocol: every tool = NL description + typed input/output schema + uniform invocation (AI-tool interaction protocol, JSON); tooluniverse.run({'name','arguments'}).
- Tool Discoverer (automatic creation from a natural-language need): searches GitHub, PyPI and existing ToolUniverse tools (semantic + keyword) for reference implementations -> SpecificationGenerator -> ImplementationGenerator (dependencies, registry integration, error handling) -> QualityEvaluator scores functionality, reliability, maintainability, performance, test coverage 0–10 each; iterate until "target minimum of 9/10 for deployment-oriented settings" or iteration limit; then "Every generated tool ... undergoes the human-in-the-loop expert review ... before it is added to the platform."
- Tool Optimizer: TestCaseGenerator runs the tool, DescriptionAnalyzer checks description-vs-behaviour alignment from test results, DescriptionQualityEvaluator scores 6 dimensions 0–10; stop at ~8.0/10 or 3 rounds. Tool Composer: sequential / parallel / agentic-loop composition into composite tools.
- Not reported: how many tools Tool Discoverer generated, pass rates, rejection reasons; no explicit deduplication or retirement policy (only "regular maintenance and monitoring" + bug reporting).
- Limitations (authors): "ToolUniverse orchestrates rather than certifies" — conclusions bounded by underlying databases/models; ML outputs are estimates; scientist stays in the loop.
- Implication: closest production precedent for our "build -> test -> describe -> compose" pipeline; borrow the description-vs-behaviour test loop (it is what makes model tool selection work) but note the admission gate is an LLM rubric + human review, not reproduction against a reference — that gap is our differentiator.

## T2.4 Alita — verified
- "Alita: Generalist Agent Enabling Scalable Agentic Reasoning with Minimal Predefinition and Maximal Self-Evolution", Jiahao Qiu, ..., Mengdi Wang (Princeton et al.). arXiv 2505.20286 v1 26 May 2025 (only version). https://arxiv.org/abs/2505.20286
- Abstract numbers: GAIA validation 75.15% pass@1, 87.27% pass@3; MathVista 74.00%, PathVQA 52.00% pass@1.
- Mechanism: manager agent + "MCP Brainstorming" (decides whether capabilities are missing and which tools are needed) + web agent (GoogleSearchTool, GithubSearchTool for reusable open-source code) -> ScriptGeneratingTool writes code + environment-setup + cleanup scripts (README/code snippets of found repos as reference) -> CodeRunningTool executes in an isolated Conda env; "If the execution produces the expected results, the tool is registered in the system as a reusable MCP" (the "MCP Box"). Env failures handled by relaxing version constraints / minimal deps.
- Models: Claude-3.7-Sonnet + GPT-4o -> GAIA 72.73% pass@1 / 86.06% pass@3; Claude-Sonnet-4 + GPT-4o -> 75.15% / 87.27%.
- MCP reuse: ODR-smolagents with Alita MCPs: GAIA L1 33.96->39.62%, L2 29.07->36.05%, L3 11.54->15.38%; GPT-4o-mini with Alita MCPs: L1 32.08->39.62%, L2 20.93->27.91%, L3 3.85->11.54%.
- CAVEAT (verbatim source of MCPs): "We collect the MCPs generated from running the GAIA dataset using Alita ..." — i.e., reused tools were generated on the same GAIA validation tasks then re-evaluated; the paper does not discuss overlap/leakage nor report the MCP Box size. Validation of an MCP = "execution produces the expected results" (judged by the agent), no unit-test suite.
- Limitation (authors): "Alita highly relies on the coding capability of LLM ..." — with GPT-4o-mini it underperforms (43.64% avg).
- Implication: on-the-fly tool synthesis plus a reusable box is cheap and works, but reuse gains must be measured on held-out papers/questions (not the ones that produced the tool) — our evaluation must split "papers that motivated a tool" from "papers used to score it".

## T2.5 TusoAI — verified
- "TusoAI: Agentic Optimization for Scientific Methods", Alistair Turcan, Kexin Huang, Lei Li, Martin Jinye Zhang (CMU / Stanford). arXiv 2509.23986 v1 28 Sep 2025, v2 16 May 2026. https://arxiv.org/abs/2509.23986 ; code https://github.com/Alistair-Turcan/TusoAI
- Input: task description + evaluation function. Knowledge tree: retrieves up to 10 key papers from Semantic Scholar (ranked by citations), 15-point technical summary per paper refined over its Methods section; organised into optimisation categories (e.g. "single-cell noise modeling") with 10+ instructions each and category weights (boosted ×1.1 when an instruction improves the score). Loop over a candidate pool: cluster by code/text similarity, pick shortest near-best per cluster; 80% instruction-based, 20% diagnostic-based optimisation; 10-min implementation limit, few bug-fix attempts; default budget 8 h wall-clock; cost from $0.24 (GPT-4o-mini) to $22.30 (GPT-5) per task.
- Results (optimise on validation data, report on separate test data): 6 single-cell tasks (denoising, label projection, batch integration, spatially variable genes, spot deconvolution, visualisation) avg score 0.66 vs expert methods 0.57 (~16%), AIDE 0.52, Biomni 0.49; avg rank 1.2. 5 NAS-Bench-360 scientific DL tasks avg rank 2.8 vs expert 4.6. Genetics: optimised scDRS >40% more power in simulations, 17 vs 14 true cell-type–disease associations, 26 vs 17 disease-associated T-cell subpopulations; optimised pgBoost +13.8% enrichment (fine-mapped eQTL gold links), +7.2% (ABC links); 511 combinations of 153 new distance features in 24 h for $0.41; 7 new variant–gene links (e.g. rs138917529–GCK).
- Limitations (authors): needs a separate, quick, representative validation experiment to avoid overfitting; "does not consider making new evaluation procedures ... will be vulnerable to the same weaknesses those may have"; weaker when methods are scattered across large codebases. Ablation: removing domain knowledge hurts performance and diversity most.
- Implication: literature-grounded "method improvement against an evaluation function" works when the metric is trustworthy; for us that means tool optimisation is allowed only against held-out reference-standard cases, with the evaluator owned by the platform (echoes DGM's objective-hacking lesson).

## T2.6 Related "agent improves a scientific method against a benchmark" — verified
### ERA (Google Research/DeepMind) "An AI system to help scientists write expert-level empirical software"
- Eser Aygün ... Michael P. Brenner. arXiv 2509.06503 v1 8 Sep 2025, v2 15 May 2026, v3 21 May 2026; no journal version mentioned. https://arxiv.org/abs/2509.06503
- Mechanism: Gemini rewrites code to raise a scoreable metric; PUCT tree search over thousands of variants; literature ideas injected as prompts (paper PDF summarised by Gemini 2.5 Pro) and pairwise "recombination" of published methods.
- Numbers: 40 novel single-cell batch-integration methods beat the top human method on the OpenProblems leaderboard; best (BBKNN on ComBat-corrected PCA) +14% overall vs best published method (ComBat); ERA beat the published result for 8 of 9 re-implemented methods; 14 COVID-19 hospitalisation models beat the CDC/CovidHub ensemble (best avg WIS 26 vs 29). Guards: optimise on a separate dataset and report on held-out OpenProblems datasets; rolling 6-week windows for forecasting.
- Limitations (authors): empirical optimisation is not scientific discovery (theory/causal mechanisms); safety risks in domains affecting human well-being.
- Implication: "re-implement the published method from the paper, then recombine" is a productive, measurable tool-building route — and reproducing the published number first is a natural admission test.

## T2.7 2026 work: literature/resource mining to decide WHICH tools to build; library merge/retire
### SkillFoundry (CMU) — the closest 2026 match
- "SKILLFOUNDRY: Building Self-Evolving Agent Skill Libraries from Heterogeneous Scientific Resources", Shuaike Shen, Wenduo Cheng, Mingqian Ma, Alistair Turcan, Martin Jinye Zhang, Jian Ma (CMU Computational Biology & ML Depts). arXiv 2604.03964 v1 5 Apr 2026. https://arxiv.org/abs/2604.03964 ; code https://github.com/ma-compbio-lab/SkillFoundry
- Deciding what to build: a domain knowledge tree whose nodes store linked resources, existing skills and validation status; mining targets branches with "abundant resources but weak verified skill coverage" — leaves with resources but no executable skill, low-confidence starter skills, or skills that "repeatedly fail validation" ("expected marginal value"). Sources: repos, APIs, scripts, notebooks, docs, databases, method papers (prefers authoritative/maintained artifacts).
- Loop: tree_check -> resource_search -> skill_build -> skill_test -> refresh. Validation = execution test under the declared contract + system test (e.g. SLURM) + synthetic-data test (input consumption, output stability). Each skill records scope, dependencies, I/O, provenance, example usage, tests.
- Library hygiene (verbatim): "Skills that fail repeatedly, duplicate existing functionality, or contribute little marginal value are revised, merged, or pruned during refinement." Novelty review against existing libraries (SkillHub, SkillSMP) by keyword match; validation outcomes reshape the tree for the next mining round. Merge/prune counts NOT reported.
- Numbers: 286 skills, 27 domains, 254 subdomains, from 394 resources; 71.1% novel vs existing libraries. MoSciBench (6 datasets; Codex with GPT-5.1-Codex-mini): Repo-Acc 61.19% -> 66.73% (5 of 6 improved), Paper-Acc 43.85% -> 53.05%. MERFISH cell-type annotation: Codex 81.1% coverage / 68.5% acc -> with skills 99.2% / 82.9% (specialist SpatialAgent 100% / 87.1%). scDRS workflow: Biomni RMSE 0.11 -> 0.02 with skills; only setting meeting all 7 qualitative criteria.
- Limitations (authors): coverage "relatively limited"; skills validated mainly by the internal test pipeline "rather than through broad downstream evaluation"; evaluation concentrated on few domains — caution for high-reliability settings.
- Implication: adopt the coverage-tree + marginal-value targeting as our "which tool next" policy, and its revise/merge/prune triggers; but add what it lacks — downstream, reference-standard validation and counts of merges/retirements.

### "Beyond Task Completion: A Verification-vs.-Conformance Gap in Tool-Evolving Agents"
- Alibek Kaliyev, Artem Maryanskyy. arXiv 2604.00392 v1 1 Apr 2026, v2 4 Jul 2026; accepted at KDD 2026 Workshop on Agentic AI Evaluation and Trustworthiness. https://arxiv.org/abs/2604.00392
- Claude Haiku 4.5 pilot: replayed 222 preserved self-synthesised tools against held-out conformance suites -> 96.8% had per-tool correctness C = 0.00 (two protocols 100% "silent rot", one 91.7%) while tools executed cleanly and the in-session verifier raised no flag; hand-written references scored 1.00 on all 16 suites. Task completion alone did not separate protocols; the audit layer did. Releases EvolveTool-Bench (seed/gap/variant/composition/regression/adversarial roles, per-tool manifests, correct-vs-incorrect reuse).
- Caveat: small pilot, one weak model, workshop paper.
- Implication: never admit or retain a generated tool on task success alone — keep per-tool source, replay each tool against held-out conformance cases between releases, and log correct vs incorrect reuse.
