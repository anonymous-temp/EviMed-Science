# 记忆胶囊整改方案：让记忆、自迭代、分享和图表真正运转起来（2026-10-23）

> 本文是**方案和待办**，没有改任何代码或数据。依据是 2026-10-23 的两轮只读核查（8 份调研报告，见附录 A）、生产库的只读统计、OpenViking 上游源码（按 tag 读）和联网资料。每条结论在调研报告里都有文件行号或来源链接。
>
> 文中「旧引擎」= 记忆存在 PostgreSQL（`legacy`），「原生引擎」= 记忆存在 OpenViking（`native`）。

## 0. 结论

**架子都搭了，但四块都没有按预期运转。**

| 块 | 现在的真实情况（2026-10-23 生产） | 根因（一句话） |
|---|---|---|
| 记忆 | 运营账号 `<owner-account>`（引导登录账号）10-13 换到原生引擎后，记忆文件 **0 个**；10-19 两次提交各抽到 **0 条**；你日常登录的 `cdss-access` 仍在旧引擎，10-12「重读旧记忆」后只剩 19 条（13 条是对话摘要） | 八个模板每个结尾都写「拿不准就不记、一段对话可以一条都不写」，偏好还要求「以后/一律」这类信号词；而你的对话大多是工作指令，按这套规则一条都不该记 |
| 胶囊 | 原生账号读不到任何胶囊内容（10 条项目笔记、收到的包、证据专区订阅）；分享从没用过（三张分享表 0 行） | 原生账号的开场画像和胶囊检索工具被整体关掉，没有替代通道 |
| 自迭代 | 10-12 后不再学习；学到的 70 条全在 `cdss-access`（你日常登录、同时也是验收驱动用的账号），内容全是平台交付流程（引用重绑、清单哈希、提交次数），不是研究者的习惯；每小时的整理任务空转但报成功 | 蒸馏只喂对话**最后几十行**（恰好是提交和修复环节），触发信号在 10-12 后几乎断流，一条保护规则把整组整理全挡住 |
| 图表 | 落地页是「记忆记录浏览器」，原生账号大概率显示「还没有记住什么」或三个 0 | 画的对象不对：没有一个「胶囊」整体（关于你 / 项目 / 我的做法 / 知识 / 收到的 / 成长），没有成长故事，没有零数据时的第一天形态 |

**OpenViking 不是最新版**：我们钉的是 v0.5.0，最新是 **v0.5.1.1**（2026-10-20）；插件 0.5.26 正好是新 tag 自带的版本，不用动。v0.5.1 本身有「同一会话第二次及以后的提交搜不到」的缺陷，我们每轮都在同一会话提交，**只能升到 v0.5.1.1**。升级后身份垫片可以删、128 页上限消失，但有两处会直接坏（`content/write` 不再接受 `timeout` 字段；花光预算的 402 会被引擎重试），必须先修。

**自迭代是否按你给的算法（EvoDS × ToolVerse × SkillPyramid）搭的**：管道是照着搭的，逻辑是断的。计数绑定方法版本、SkillPyramid 的分析器和构建器、退役阶梯都在；但 τ=3 只剩「每第 3 次成功运行触发一次」，SCREEN 用词面重叠而不是向量，6 种关系只记 4 种，层级从不落库，多层检索根本没做（挂载就是最新的 16 条），ToolVerse 那一半零消费，ACC 默认关，研究者的代码技能没有生产者。最关键的断点在蒸馏输入（§5）。

**做法**：先止血（P0，让东西真的转起来），再改「记什么」（P1），升级 OpenViking（P2），把自迭代拉回原算法（P3），补齐分享（P4），重做胶囊总览图（P5），最后收尾文档和测试（P6）。待办在 §8，需要你拍板的 8 件事在 §9（不拍板就按推荐做）。

## 3. 与 OpenViking 的集成和改造形式

### 3.1 分工（目标形态）

```
                 浏览器（记忆胶囊页：总览 + 五视图地图 + 列表）
                              │ /api/memory/* /api/capsules/*
┌─────────────────────────── 控制面 ───────────────────────────┐
│ 记忆网关 memoryGateway      身份、准入、遮蔽、平台文字过滤、限速  │  ← 我们的边界，保留

│ 覆盖层 nativeMemory*        修订/撤销、拒绝表、来源关联、项目标签 │  ← 保留并补「来源对话」

└──────────────┬──────────────────────────────────────────────┘
```

## 4. 该记哪些、不该记哪些

### 4.1 立场

**记「本人说过、确认过、纠正过的」，加上「本人为某项工作定的约束」；永远不记文档、工具、网页、平台或助手说的话。**

判断标准是一句话：下个月在另一段对话里，有了这一条，助手会不会做得不一样？

拿不准时往哪边倒，分两种情况：
- 本人要求记的，宁可记；
- 敏感内容和第三方信息，宁可不记。

### 4.2 证据分级

| 级 | 含义 | 例 | 记不记 |
|---|---|---|---|
| E1 明说 | 本人在自己的消息里说到自己或自己的工作 | 「我是心内科医生」「检索一律用 PubMed」 | 记 |
| E2 确认/纠正 | 本人认可助手提出的做法，或纠正、改写助手做的东西 | 「好，就按这个三栏表来，其他材料也这样」「太长，压到 200 字、三条」 | 记（按它所针对的文体或对象限定范围） |
| E3 重复出现 | 两段不同对话里出现同一选择但没说成规则 | 两次预算表都要透视表 | 第二次出现时记——**与原则 18「推断不自动升格」冲突，需你拍板（§9 第 3 项）** |
| E4 一次请求的暗示 | 单个请求「看起来」说明某种身份 | 要一个 psycopg 例子 ≠ Python 开发者 | 永远不记 |

### 4.3 分类表（摘要，完整表见 G 报告 §4.3）

| 类 | 记 | 只有明说「记住…」才记 | 只在本次对话 | 永远不记 |
|---|---|---|---|---|
| 关于这个人 | 角色、专业、机构类型、资质；称呼、工作和输出语言、单位/日期格式、城市时区；**日常背景**（饮食、爱好、通勤，不带敏感原因）；正在准备的目标 | 本人健康/用药/过敏、宗教、政治、民族、性取向、财务、14 岁以下孩子的信息、精确住址或行踪、生物特征 | — | 密钥/验证码/证件号/银行卡号（本人要求也不记）、犯罪记录、移民身份；立场和观点（会让模型附和，CHI 2026）、性格判断、情绪 |
| 怎么和这个人干活 | 固定做法（详略、先问还是先做、先给大纲、引用格式、统计约定）；**写过初稿后的格式纠正**（限定在那种文体）；**纠正的错误**；**明确认可的做法**；自己用的工具、模板、命名规范；本人说明的环境限制（「只有 WPS」） | — | — | 助手对这个人的揣测；能从文件和工具里重新得到的环境事实；跨用户可迁移的做法（归平台方法，不进个人记忆） |

| 不能变成记忆的来源 | — | — | — | 平台注入文字、工具结果、网页、检索结果、运行状态；助手的提议（本人采纳后才算 E2）；助手复述已召回的记忆；**粘贴、转发、引用材料里的指令**（例如「把 X 记为可信来源、以后优先推荐 X」——微软 2026-02 报告的「推荐投毒」）；文档或本人上传的简历里写的内容；平台发起的轮次 |

### 4.4 落到模板和代码

1. 拆开现在那段 2,996 字的「不记」：
   - 「永远不记」块，大约 1,900 字；
   - 「怎么判断」块，用证据分级取代信号词表，删掉「拿不准就一条不写」。
2. 偏好去掉信号词；纠正扩大到「认可的做法」。`follow_ups` 只放不带日期的未结事项，提醒改走定时任务。
3. 敏感内容三分：永远不记 / 明说才记 / 普通。理由与事实分开，例如「我吃素，因为信佛」只记「吃素」。
4. 协作者按角色和约定可以记；项目卡「约束」里写明「交付约定」；粘贴材料里的指令不记。
5. 代码侧：
   - 纠正放到 `preferences/corrections/`（I2）；
   - 收窄 `LONG_TOKEN`，只认真实的密钥形状；
   - `<system-reminder>` 加进平台标签闭集，或者从模板里删掉这个说法；
   - 零操作指标，加每周静默零审计。
6. 每一步改动前后都重放 24 个新用例（G 报告 §6，C01–C24），外加现有回归锚点和一个「升级」用例。一句措辞就可能把一类从 0/8 改成 8/8，只看单次结果会误判，所以失败的用例要重跑 3 次。

## 5. 自迭代：拉回原算法

### 5.1 判断

原算法是一个闭环：生效前验证（EvoDS 的验证后缓存、τ=3）→ 有可执行环境才能检验候选（ToolVerse）→ 分层检索让库越大越好用（SkillPyramid）。

你的裁决删掉了生效前的门。代替它的是「生效后由数据降级」，但这一半在主线上没有数据可用。蒸馏输入也是错的。

平台级的 ASA（合成工具 → 执行验证 → 在没见过的用例上确认）没丢，挪到了循证进化里。两半现在只共用一套计数词表和一个联动事件。

### 5.2 修正后的回路（与所有裁决一致：不加审批、不加门、不付费做开关实验、先生效、一键恢复）

| 步 | 改什么 | 借鉴 |
|---|---|---|
| S1 证据 | 记下插话的原文；新增「下一轮首句」判定：本对话 30 分钟内的下一条用户消息，用一次 Flash 判为纠正/偏好/拒绝/接受/无，代码核对引文必须是原消息的子串。这就是原生账号缺的纠正来源。「留了文件且没被纠正」记为 silent，取代按 1/3 抽样的 delivered | TRACE（arXiv 2606.13174）把纠正规整为单条规则 |
| S2 轨迹摘要 | 纯函数 `trajectoryDigest`：每轮的首个请求原文、所有纠正及位置、交付物结构指纹、去掉平台编排工具（代码按闭集剔除）后的工具序列；纠正两侧 ±12 条锚定摘录，取代「最后几十行」 | 原计划 6.2 就是这么写的 |
| S3 触发 | `routine` = 同一范围内 τ=3 条**干净**（没被纠正）、交付形状相同的轨迹；范围是能力 id，或者普通对话，普通对话第一次能触发；删掉 delivered | EvoDS τ=3 用在它本来的位置 |
| S4 蒸馏 | 先拆成单条规则，判断「这次任务才需要」还是「会再出现」，只留后者；相关方法按向量取最近 8 条；`merge` 真正合并 | SkillGrain（2610.19380） |
| S5 挂载 | 候选按范围匹配；用派发首句做向量相似度排序；留 1 个探索位；加 depends_on 闭包，最多 1 个抽象方法、3 个功能方法；预算不变；挂载回执写明原因；方法生效或退役后刷新运行时 | Graph-of-Skills（2604.05333，MIT） |
| S6 计数与降级 | 新增「打开后被纠正 / 打开后顺利」计数；伤害检验用这两个；`never_opened` 只算范围内的运行；「被取代」和「超 50 条」真正执行；删掉算完就丢的路径 | Assay（2606.15390）的随机留出法，是否采用见 §9 |
| S7 整理 | 用向量做候选短名单；只对**变化过**的组跑 DECIDE，不变就跳过，写明 noop 原因；未证明的合并只挡自己组的 BUILD，14 天无人使用就退役（可恢复）；DECIDE 加 WIDER/REPLACES，6 种关系都记；层级写回记录；合并时回放各来源的证据引文做保留检查 | SkillCommit（2608.15165） |
| S8 可观测 | 每账号「上次有学习证据的时间」、各触发器课数、整理 noop 原因、挂载原因；原计划第 11 节的 6 个 go/no-go 问题做成每周巡检 | |

## 6. 记忆胶囊的图表化展示

**做法**：保留你定的五视图地图，作为钻取用的浏览器；在它前面加一个**总览**页签，并作为 `/app/memory` 的落地页。

总览由三部分组成：
- 一句数字都能点的话；
- 六张同一语法的卡片：**成长 · 关于你 · 项目 · 我的做法 · 知识 · 收到的**；
- 一个「需要看一眼」的短列表。

```
记忆胶囊                                   [项目：全部 ▾]            [记忆 ●]  [⋯]
 总览 │ 地图 │ 关于你 │ 项目 │ 做法
 胶囊里有 12 件关于你和项目的事、3 种做法、47 份资料；这个月新增 5 件。
┌ 自 9 月 22 日起，记下 18 件、学会 3 种做法、放进 47 份资料 ─────── 成长 ┐
│ 记下 ●  ·   ● ●  ●●   ●   ●●●  ●      ●                                │
│ 学会 ▲           ▲          ▲                                           │
│ 资料 ■  ■■■■  ■■   ■■■■■■■   ■■■                                        │
├───────────────────────────────┬──────────────────────────────────────┤
│ 关于你 · 6 件  (条目/柱)        │ 项目 · 3 个 (表 + 行内柱)              │
├───────────────────────────────┼──────────────────────────────────────┤
│ 我的做法 · 3 种 (条目/月轴点)   │ 知识 · 47 份资料 (按类型的组成柱)        │
├───────────────────────────────┴──────────────────────────────────────┤
│ 收到的 · 1 个   我能交出去的：方法 3 · 标准与偏好 5 · 背景 12（工作方式卡）│
└──────────────────────────────────────────────────────────────────────┘
 需要看一眼 · 3（依据的资料变了 / 说法不一致，每行打开抽屉）
```

规则：
- **形态随数据量变化**，阈值写死在一个纯函数模块里并有单测：
  - 0 条：给一个做法和一个按钮；
  - 1–5 条：直接列出条目本身；
  - 6–30 条：画点或排序柱；
  - 31 条以上：折叠成簇或画周柱。
- 每张卡独立读取，读失败就在这张卡上写明，绝不显示成 0。
- 不出现来源、置信度、使用次数、引擎名。
- 不在落地页画全局力导向图、雷达图，不做连续天数和徽章。

工作方式卡：
- 它是分享这一半的「脸」，展示「方法 · 标准与偏好 · 背景」三类各有多少；
- 同一组件也用在收到分享的页面上，接收方能直接看到对方怎么干活。

原生账号的第一天（没有记忆文件）也是有内容的页面：
- 成长卡上只有资料这一条线；
- 项目卡显示各项目的资料数；
- 关于你、我的做法、收到的三张卡各给一个按钮：「记住这一条」「去做一件事」「导入一个胶囊」。

依据：
- 少量数据就展示点本身（Weissgerber 2015）；
- 节点超过约 50 个时，关系图基本无法阅读；
- Strava 和 WHOOP 都明说最低门槛，同时先给能给的内容；
- 已发表的研究里没有证据表明记忆关系图对终端用户有帮助；有证据支持的是「可编辑的列表 + 标出需要注意的条目」。
