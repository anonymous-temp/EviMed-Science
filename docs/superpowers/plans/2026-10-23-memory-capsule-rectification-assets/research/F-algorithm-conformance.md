## 1. Verdict

The loop is a faithful transcription of the owner's algorithm in its *plumbing* and an open loop in its *logic*. The plumbing is real and mostly live: transcript capture with a completeness receipt (`runTranscripts.mjs`), digest-keyed counters that reset when the body changes (`methodGraph.mjs:166`, `learningService.mjs:468`), deliverable-level attribution against the mounted digest (`methodObservations.mjs:300-355`), a distill capability with a contract validator, a SkillPyramid-style analyzer/builder pair with the paper's hard rules (`methodConsolidation.mjs:741,775`), and a retirement ladder. What the algorithm *is*, though, is a closed cycle in which every unit is verified before it is exposed and its use is measured after: EvoDS's verify-then-cache-after-tau=3, ToolVerse's executable environment as the thing that makes a candidate testable, SkillPyramid's level-aware retrieval as the thing that makes a growing library usable. After the rulings (effect first at n=0, paired evaluation deleted, repair lessons at 0) the gate in front of exposure is gone, and nothing was put in its place on the researcher's main line: the demotion detector reads only deliverable observations that opened the method (`methodGraph.mjs:388`), which the ordinary conversation never produces; the induction input is the *tail* of the transcript, not the researcher's deviation (`methodDistillationRuns.mjs:231`, `runTranscripts.mjs:706-707`); consolidation is inert; the mount is a flat recency list of 16 cards; level, relevance retrieval and code skills do not exist for the researcher; the ToolVerse half is scaffolding with zero consumers; ACC is built and switched off. The owner's *platform-level* ASA (synthesize tool, execute-verify, confirm on unseen cases) was not lost: it moved to 循证进化 (`tool-builder`, `evolutionVerification.mjs`), which is why the two halves of the algorithm now live in two systems that share one counter vocabulary and one coupling event. The break that explains the production corpus (all 70 documents about delivery bookkeeping) is not the consolidation stall B ranked first but one step earlier: what is fed to distillation (section 3, break 1).

## 3. Where the loop breaks (ranked)

Ranking is by what each break, fixed alone, would change about the production facts (70 documents all about delivery bookkeeping; last distill 2026-10-12; hourly `consolidate` returning `groups:1, builds:0, relations:0, screened:false`; learning spend zero since 10-12). Breaks 3 to 7 repeat B's findings only where my trace adds a mechanism or a discriminating check.

### Break 1. Distillation is fed the tail of the platform's own transcript, not the researcher's deviation (VERIFIED; new relative to B)

- `buildDistillationInput` cuts the evidence with `transcriptExcerpt(transcript.messages, { limit })` and never passes `fromSeq`/`toSeq` (the only three call sites are `methodDistillationRuns.mjs:194,232,311`; no caller anywhere supplies a range). `transcriptExcerpt` ends with `clean.slice(-limit)` (`runTranscripts.mjs:706-707`). The window is `delivered` 60, `repair_accepted` 80, `edit_diff` 60, `routine` 40 per run, `correction` 30 (`methodDistillationRuns.mjs:88`).
- The stored transcript is the root session's lines followed by each child session's lines (`serializeRunTranscript`, `runTranscripts.mjs:406-413`; `readRunTranscript` does not reorder, :593-618). So for a delegating capability run the last 60 lines are the *last child's* tail, and for an undelegated one the root's tail: submit, repair, present, the closing summary. The researcher's opening request is cut off whenever the run exceeds the window. The plan said the opposite (6.2: "只放与触发相关的 seq 区间: the writing interval of the deliverable, the repair rounds, N messages either side of a correction") and the range parameters it needed exist and are unused.
- `correction` lessons are better off: `steeredCorrections` reads the researcher's typed words from the run's own turns outside the window (`methodDistillationRuns.mjs:175-204`) and puts them first. But `routine` and `delivered` lessons (signal `run`, section "lessonSignal", :114-117) have no researcher words at all, and on capability runs what they see is choreography. SKILL.md asks the model to leave "the platform's own tool choreography of plan, delegate and submit" out (`SKILL.md:~160-173, 183-190`), which is the plan's own warning against doing a deterministic job in a prompt (principles 1, 5): the closed set of choreography tools is known to code (`toolNames.mjs`) and can be removed before the model sees anything.
- `routine` compounds it: "same routine" is the capability id, "success" is `status === "succeeded"` with a file left (`learningTriggers.mjs:174-178`), peers are the previous two such runs, and each peer contributes its own last 40 lines. A run the researcher corrected the next minute is still a "successful trajectory".
- Why this is the first break: it explains production fact 2 without any help from consolidation. The only learned methods that can exist are the ones the model could induce from submit/anchor/receipt tails. It also explains why B's defect 2 ("nothing stops stale lessons") produced handbooks that name deleted features: the evidence window is the part of the run where those features appear.
- Contradicts the algorithm at: ASA "synthesize" needs a trajectory of the *task*, AWM needs the state-action sequence that is shared; the plan's own go/no-go question 3 ("can a candidate beat the baseline on an unseen variant without touching a validator") is unanswerable when the candidate encodes the validator's choreography.
- Discriminating check (read-only, ops): for the 8 approved methods read `payload.provenance.{trigger, signal, capabilityId}`. `signal: "run"` with trigger `routine`/`delivered` on a capability confirms; `signal: "researcher"` would refute the "all bookkeeping" reading for that method.

### Break 2. After effect-first, nothing on the main line can demote a method, and `never_opened` measures question mix (VERIFIED mechanism; INFERRED production impact)

- Exposure is at n=0 (A4). The compensating control the rulings promised ("evaluation only demotes", spec 8.4) was the paired evaluation, deleted; its replacement is `methodHarmTest`, which reads only observations with `invoked === true` (`methodGraph.mjs:388`), and observations exist only for deliverables with a plan item (`methodObservations.mjs:300-355`). The ordinary conversation, which is most of the traffic and the line where the 10-13 ruling now lets lessons be learned, has no plan items: it yields `read` and `carried` and never a verdict. For it the only demotion is `never_opened` (>= 20 answered carries, zero opens), and a card is carried in *every* non-GEO runtime whatever the question is (`learnedMethodFamilyForRuntime`, `learnedMethodMount.mjs:74`), so a method for one kind of task is stopped by how often the researcher asks something else (B 3.2 notes the same).
- The contribution clause is blind for the same reason (denominator `loaded` is deliverable-level) and is discarded anyway (D4).
- Net effect: a wrong or irrelevant method learned from the ordinary line can ride in 8-16 cards of every prompt until 20 unrelated questions pass, and a right one for a rare task is stopped. The loop is open exactly where the owner's ruling needed it closed.
- Contradicts: ASA's "cache only what verified" was replaced by "demote what harms", which presupposes a harm signal everywhere the method is exposed.

### Break 3. The trigger supply after 2026-10-12 cannot produce lessons on the main line (VERIFIED code; mostly B 6.1)

B ranked the candidates; my additions: (a) `afterRun` is wrapped in `.catch(() => null)` at the call site (`server.mjs:4102`), so a throw there is invisible apart from the audits `afterRun` writes itself; (b) the clinical-context early return (`server.mjs:4096`, and :4010 for the edge/trace producers) removes every VCR-reading conversation from lessons, counters and tool-edge receipts at once; (c) the transcript-completeness gate (`learningTriggers.mjs:288`) turns any unreadable history into "no lesson, no error"; (d) `delivered` is sampled at 0.33 by hash of run id and `repair_accepted` at 0 (`learningTriggers.mjs:444-456`), `routine` never fires for the answer line (`:98,:174`). The one source of *researcher words* for a native account is a message typed into a running turn or a `result-corrected` event; a plain "no, shorter" is a new turn and is nowhere (B 6.1b). Nothing in the platform reports "no evidence in N days" (no gauge for it).

### Break 4. Consolidation is inert and reports success (VERIFIED code; production cause has two live hypotheses)

- B's mechanism (guard): `members.some(unprovenMerge)` skips DECIDE and BUILD for the whole group (`methodConsolidation.mjs:281,424`), the group still counts (`groups: groups.length`, :501), the job succeeds. `integrate` has no such guard and no build (:548-564), so the stall is specific to `sleep`.
- Hypothesis I add (INFERRED): DECIDE may have run once and be *adopted* every hour. The dispatch id is `method-relations-<sha256 of sorted id@digest>` and `learningRuntime.dispatch` adopts an existing dispatch rather than starting a second (`methodConsolidation.mjs:672-675`, `learningRuntime.mjs` header, `methodDistillationRuns.mjs:443-446`). An unchanged 8-method library therefore costs nothing per hour and returns the same stored answer; `relations: 0` is then "the stored answer contains only subset/supersedes assignments or none" (`applyRelations` skips those two types, :587) or `decideGroup` returned null for a failed run. Zero spend since 10-12 fits both the guard and this; the distinguishing facts are in the next bullet.
- Discriminating checks (read-only): (1) in the learning project's run ledger, any `dispatchId LIKE 'method-relations-%'` created after 2026-10-12 (none favours the guard, one with `status=succeeded` favours adoption); (2) among the 8 approved methods, any with `provenance.consolidatedBy LIKE 'consolidate:%'`, no `provenance.runId` and no clear harm test (that is the guard's precondition, `unprovenMerge`); (3) the stored DECIDE answer under the learning project's `learning-results/<dispatchId>` (`RESULT_ARCHIVE_DIR`) for its `assignments[].RELATION_TYPE`; (4) `payload.learning.relations` non-empty on any approved method.
- Whatever the cause, three defects stand regardless: the pass cannot say it did nothing (`groups` includes skipped groups; no `noop` reason in the result or the metrics); SCREEN is lexical because J1 is not composed (`screenPairs` returns the shortlist unchanged, :649); and 2 of the 6 relation types cannot be recorded (C5), which makes the `superseded` retirement clause unreachable.

### Break 5. The mount is flat, recency-ordered and dependency-blind, so SkillPyramid's multi-level retrieval never exists (VERIFIED)

`selectLearnedMethods` filters by family, sorts by approval time, takes 16, spends a byte budget on card size (`learnedMethodMount.mjs:217-299`). There is no relevance to the task, no use of `level` (never computed into the record, C8), no dependency closure (so a reuse reference can point at an unmounted method), no exploration slot for methods with no evidence (the 10-06 plan 11.3 asks for one). A method takes effect only at the next runtime launch (B 17). With 8 approved methods the cap does not bind today; it will the day the anchor is fixed and the library grows, and then the 17th-newest method is never carried, never opened and so can never be retired by `never_opened` either (B defect 5).

### Break 6. Related-method selection is recency, not relevance, and nothing retrieves by meaning (VERIFIED)

`listMethods(userId, { limit: 20 })` is ordered by `updated_at DESC`, then `.slice(0, 8)` (`methodDistillationRuns.mjs:409,267`; B defect 6). The distiller is told to amend rather than duplicate and is shown the 8 most recently written methods. The 2026-10-12 audit already found the cost: a run carried 8.6 cards on average and 22 of 35 methods on file were rewordings of two lessons (`constants.mjs` note on `METHOD_UNUSED_RETIRE_LOADS`, `packages/domain/src/constants.mjs:~94-100`). SkillPyramid's incremental update retrieves the *related* skills for a new one by embedding; here neither the distiller nor `integrate` has an embedding, and the distill-time `merge` operation's `mergedMethodIds` is validated and ignored (C10).

### Break 7. The two halves of the algorithm are not joined, and the pieces that would join them have no consumer (VERIFIED)

- The "verify" half lives in 循证进化 (tool synthesis, `verifyCodeSkill`, held-out confirmation cases), the "learn from a person" half lives in the learning loop. They share the six-counter vocabulary and one event (`handbook-gap`, `evolutionLearningCoupling.mjs`); nothing flows from the researcher's loop into tool synthesis except that, and nothing from verified tools into method text except `platformTools` handed to DECIDE (`methodConsolidation.mjs:251-259,680`).
- Built, producing, and unread: per-run golden traces (`tool-traces/`, `server.mjs:4025`; the 10-06 plan lists them as the input for AWM-style workflow induction), executed edges (collected only by a manual script never run; repo file 0 bytes), compaction receipts (read by `report.py`, unknown distribution), `experienceBullets.mjs`, `open-method-pr.mjs`, `toolGraphSampling.mjs`, `generate-briefs.mjs`, `codeSkillVerification.mjs` outside 循证进化. Each is a finished part of the owner's algorithm with no caller on the researcher path (A2, A10, B2 to B4, D5, D6).

### Not breaks, but looks like them

- The 70-document corpus belonging to one account is a consequence of who generates qualifying runs (the acceptance account runs real capability briefs not flagged `automated`), not of a tenancy bug (B 6.2).
- `tau` no longer gating promotion is a ruling, not a defect (A3, A5).

## 5. A corrected loop, consistent with the rulings

Design rule: keep every box of the owner's algorithm and every ruling, change only what enters a box, what is counted, and what is selected at mount. Nothing below is an approval step, a paid on/off study, a delivery gate, a user-facing notice, a per-account cap or a clinical template; effect stays at n=0 and every automatic act stays restorable with one click. Language judgement goes to a model and exact operations to code (principles 1, 5), and each judge answer that quotes the researcher is re-verified in code and dropped on failure. Everything reuses an existing module; the only new store keys live in the `learning` payload of a method document and in the existing feedback ledger (`feedbackEvents.mjs`). Numbers marked (provisional) are choices made before a distribution exists, in the repo's own manner (`constants.mjs`, `METHOD_SCIENTIFIC_HARM_TEST`).

How the boxes map after the change: synthesize = S2 to S4; verify = a *continuous* outcome test on the main line (S6) plus a preservation check at merge time (S7), because a pre-exposure gate is ruled out; cache = the method stays mounted while the S6 detector is quiet; expand = S5 retrieval with an exploration slot; tau = 3 is kept where it was meant, as the number of *clean, same-shape trajectories* that justify a routine (S3).

### S1. Evidence capture (fixes break 3; reuses `feedbackEvents.mjs`, `resultCorrection.mjs`)

Inputs and kinds, all stored as feedback events keyed by run id:

| Kind | Source | Exists |
|---|---|---|
| `steer` | a message typed into a running turn; store its verbatim text and seq (today only a count, `recordSteeredInput`) | count yes, text read later by `steeredCorrections` |
| `result-corrected` | select-and-correct in the result view | yes |
| `follow-up` | the first user message of the *next* turn of the same session, within 30 minutes (provisional): one Flash judge call returns `{kind: correction / preference / rejection / accept / none, rule: one sentence in the user's language, quote}`; code checks `quote` is a substring of the message and applies `hasSensitiveText`; `none` and `accept` write nothing but a counter | new, one judge site; this is the native-account correction source B asked for |
| `silent` | a succeeded, file-leaving run with no event above by the time the next turn arrives or 30 minutes pass; carries the artifact-shape fingerprint of S2 | new, replaces the sampled `delivered` lesson |

No sampling of corrections (unchanged). The `follow-up` judge adds one cheap call per follow-up turn; learning has no daily cap by ruling, so it is metered, not capped (`purpose: learning`).

### S2. Trajectory digest and anchored excerpts (fixes break 1; reuses `runTranscripts.mjs`, `toolNames.mjs`)

A pure function `trajectoryDigest(transcript, run)` in `@evimed/domain`, beside `runTranscript.mjs`, returns:

- `requests`: the verbatim first user message of each of the run's own turns (the part the tail window cuts today);
- `interventions`: every `steer`/`follow-up`/`result-corrected` with seq and verbatim text;
- `artifacts`: path, kind and a structural fingerprint (headings, slide titles, sheet names and header rows, top-level definitions), read with the readers the `file-deliverable` check already has (`runWorkspaceChanges.mjs`);
- `tools`: the ordered tool names with the platform's choreography removed in code: `SOCKET_TOOL_NAMES` (`evimed_plan`, `evimed_delegate`, `evimed_await`, `evimed_submit_deliverable`, `evimed_package_check`, `evimed_revise_deliverable`, `evimed_render_report`, ...) plus the kernel's `present`, `todo`, `ask-user` (closed lists, `toolNames.mjs:175-200`);
- `outcome`: `{status, repaired}`.

`buildDistillationInput` then hands the model the digest plus, for each intervention, an excerpt anchored on it (`transcriptExcerpt(messages, {sessionId, fromSeq: seq - 12, toSeq: seq + 12})`; the parameters exist and are unused today, `runTranscripts.mjs:692-708`), instead of the tail window. A `routine` lesson carries the digests of its members, not 40 raw lines each. The choreography rule in SKILL.md becomes a safety net instead of the only defence.

### S6. Counters and demotion (fixes break 2; reuses `methodGraph.mjs`)

Counters stay keyed to `(methodId, contentDigest)` and reset when the body changes (unchanged). Existing: `eligible, loaded, invoked, succeeded, read, carried`. Added, per run that *opened* the method and deduplicated by run id:

- `appliedCorrected`: an S1 event arrived in the same conversation within the window and the follow-up judge says it concerns the method's `applies_when`;
- `appliedClean`: the conversation moved on without such an event;
- optional (Q1) `withheldRuns`, `withheldCorrected`: when the method has `carried >= 10`, the card is withheld from 1 in 10 eligible runs, chosen by hash of run id and method id (the `sampledByHash` mechanism), and the same judge scores whether a correction concerned the method's scope anyway.

Rules (all act immediately for inferred methods and are restored in one click, as today):

| Rule | v2 |
|---|---|
| harm | `methodHarmTest` over `bad = appliedCorrected or a rejected deliverable`, `good = appliedClean or an accepted/repaired deliverable`, with the scientific axis's numbers (background 0.25, harm 0.6, alpha 0.05, beta 0.2, minRuns 4, maxRuns 40, `METHOD_SCIENTIFIC_HARM_TEST`; a correction is ordinary work, so the delivery axis's 0.10 background is wrong for it) |

### S7. Consolidation (fixes breaks 4 and 6; reuses `methodConsolidation.mjs`)

- Shortlist by embedding cosine (top 20 per method, provisional floor 0.80) instead of token overlap; J1 optional. `DEDUP_SEMANTIC_COSINE` (0.95) is for merge candidates only.
- DECIDE only for *changed* groups: store `learning.decided = {key: sha256(sorted id@digest), at}` per group member; `sleep` skips a group whose key is unchanged and returns `{decided, skippedUnchanged, blockedUnproven}` plus a metric `consolidate_noop_total{reason}`. A no-op becomes a stated reason, not `success`.
- `unprovenMerge` blocks only the BUILD of a group that contains it, never DECIDE or the relations of the others; and it expires: a merge-built method with `carried >= 10` and no opens, or 14 days old with no use, is retired (restorable). The verify step for a merge moves from "wait for production runs to clear a harm test" to a preservation check at build time: `preservedSectionsIntact` (exists) plus one internal run that checks the merged text against each source's stored evidence quotes (SkillCommit's replay-and-mechanism-check, language judgement to the model, quote presence to code).
- DECIDE schema gains `WIDER` (subset direction) and `REPLACES` (supersedes), so `applyRelations` records all six relation types and the `superseded` clause becomes reachable (`methodConsolidation.mjs:587`).
- Persist `learning.level` from `validateMethodGraph().levels` at the end of `sleep` (`methodConsolidation.mjs:439-441`).
- `integrate` builds `shared_part` and `subset` assignments under the same guard instead of recording relations only.

### S8. Observability (reuses `learningMetrics.mjs`)

Gauges: `learning_evidence_total{kind}` and `learning_evidence_last_at` per account (the "nothing learned in N days" signal), `learning_lessons_total{trigger}`, `consolidate_noop_total{reason}`, `mount_selected_total{reason}`; and the plan's six go/no-go questions (section 11) as a weekly walk under `scripts/ops/`, since none is asked today.

- Researcher code skills: a deterministic detector over a researcher's transcripts (AST-normalise Python in `bash`/python tool inputs; same hash >= 3 times in >= 2 runs) queues a `script` lesson; the distiller proposes `scripts/<n>.py`, `.tool.json` and a test; `verifyCodeSkill` through the existing disposable executor runs before the method is created (verification failure means no method, not a gate on the researcher's work). 4. S5: pass when a dispatch with a topical first message mounts the nearest method and its dependency, and the receipt says why.
