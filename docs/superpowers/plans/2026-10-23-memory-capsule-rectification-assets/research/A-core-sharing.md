# FINAL STRUCTURED REPORT (V = VERIFIED, I = INFERRED; paths relative to OpenScience/apps/server/src unless noted)

## 1. How the capsule works today (summary)
A capsule is still a `documents` row (evimed_product, kind='capsule') plus `kind='fact'` rows pointing at it (capsuleService.mjs); the spec's single `evimed_memory.records` table with `holder` was never built (no `holder` anywhere). A person has one 「我的记忆胶囊」 (`account-capsule:<hash>`) and one hidden 「项目笔记」 capsule per project (`runtime-notes:<hash>`) which only the runtime `evimed_capsule_note` tool writes (inferred, auto-effective). Activation is a preferences row `active-capsules:account|project:<id>` (max 8). Export (`CapsuleTransferService`) assembles a pack at request time from four stores (capsule facts the person touched, effective learned methods in documents kind='method', explicit/manual `evimed_memory.records` for legacy accounts, or the OpenViking engine's files for native accounts), seals it as a JSON `.evimedcap` envelope (AES-256-GCM, Merkle root, Ed25519 over RFC 8785 manifest, scrypt N=2^17 password wrap and/or X25519+HKDF recipient wraps), with a signed card (title/author/summary/changelog), a version chain (`prevManifestSha256`) and a revocable snapshot record. Import = verify -> text-only check -> decrypt -> closed-set + model scan (`capsuleScan.mjs`) -> new imported capsule whose facts are `approved/origin=system`, not enabled; then trial / enable (account or one project) / disable; take-down by author or operator; upgrade in place when the pack's chain names the held manifest. In-platform sharing (named delivery sealed to the recipient's key, share links, take-down notices, corroboration metrics, Agent Skills zip) sits behind OPEN_SCIENCE_CAPSULE_SHARE_ENABLED (default false). Reaching a conversation: methods (4 workstyle kinds) are mounted as SKILL.md at runtime launch (capsuleMethods.mjs); everything else is reached through the runtime recall tool `evimed_capsule_recall` and, for legacy accounts, the resident profile. Production: no pack has ever been imported, no share row exists (coordinator's facts) => the whole received-pack half is unexercised in production.

## 3. Defects (ranked)
S1 [HIGH, V] Native accounts get no capsule benefit from non-method pack content, and zone subscriptions are unreachable for them. Chain in §4. Docs (AGENTS.md "stand aside") state the tool halves stand aside but nothing says what replaces them for a received pack/zone, and nothing does. Also the capsuleGateway recall comment (capsuleGateway.mjs:~160: "On the native engine ... recalled through its tools") describes a branch that has no caller.
S2 [HIGH, V] A native account's 「分享我的做法」 is empty or near-empty for the typical case (no learned methods, migration-replayed preference files, inferred notes): capsule_export_empty (:571). Spec's one end-to-end promise (§15 step 6) is not met for the owner account. The write side of memory for native accounts never produces writing_style/tooling/method_preference/behavior/expertise kinds (nativeMemoryStore.mjs:36-45), so WORKSTYLE ∩ native = {preference}.
S3 [MED-HIGH, V] Migration-lineage exclusion (capsuleTransferService.mjs:372-382,430-432) permanently drops any file ever touched by the replay migration unless the person edited its exact body last; later conversation commits that extend the file do not rehabilitate it. Safe-by-default but silently shrinks every migrated account's pack; the preview does not say why.
S4 [MED, V] Export marks every native engine file `explicit`/`manual` (nativeMemoryStore.mjs:267) - spec rule 3 (only the person's own words ever leave) is delegated to the engine's extraction template and cannot be re-verified in code. The old guard (verbatim quote bond) does not exist for native. Accepted by the 10-12 owner decision, but the capsule code's comments still read as if the guard existed.
S5 [MED, V] Upgrade-in-place unreachable for deliveries and links: `deliver()`/`createLink()` call `export()` without `supersedes` (capsuleSharing.mjs), so `prevManifestSha256` is null and import mints a new capsule every time. The in-app share path (the one meant to be the common one) has no versioning; only the file path has.
S6 [MED, V] Enable/disable of a pack does not touch running runtimes: methods mount at launch only (runtimeManager.mjs:4382 via syncCapsuleMethods; releasePausedMethodRuntimes only on pause :3739). For native accounts (no recall tool) disable "takes effect" only at the next runtime start; for legacy the recall half stops at once but the mounted skills stay. Spec §9.4-7 says disable is immediate ("整包退出").
S7 [MED, V] Stale/contradictory comments and domain constants: capsuleMethods.mjs:50-60 says imports arrive `candidate` ("mounting a candidate...") but import writes `approved` (capsuleTransferService.mjs:1006) ; capsuleContainer.mjs:21 mentions a "reshare flag" that does not exist; domain `CAPSULE_SHARE_SCOPES` includes '+documents' and `SHARE_SCOPE_ENTRIES` allows claims.jsonl/exemplars//lessons.jsonl/timeline.jsonl/documents/ (packages/domain/src/capsule.mjs:64,123-137) though the transfer service refuses everything but 4 files + methods (`SHARE_FILES` :58) - the manifest validator is looser than the share rule (defence is the second check only); `CAPSULE_FACT_ORIGINS` has 3 values vs spec's 7; `CAPSULE_TIMELINE_EVENT_TYPES` has no consumer outside the domain index (V by grep).
S8 [LOW-MED, V] `CapsuleService.activate(mode:'own')` replaces the whole list with the one capsule (:325), silently disabling every enabled received pack in that scope; route `/:id/activate` is live, the web helper `activateCapsule` (productClient.ts:90) has no caller, so unreachable from the UI today but a footgun. Guests are appended last (:326) not first as spec §9.4-6 says.
S9 [LOW-MED, V] `received()` and `mine()` read `documents.list(userId,"capsule",{limit:100})` (:183,345) and filter client-side: capsules are one-per-project (+notes capsules) so an account with >100 capsules silently loses received packs/own capsules from the shelf.
