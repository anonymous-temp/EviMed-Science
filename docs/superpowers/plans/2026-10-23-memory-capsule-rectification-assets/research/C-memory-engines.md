Reviewer: read-only static review of the tree at `main` (2026-10-23), no network, no secrets read, no production access (the coordinator's production facts are taken as given). Paths are relative to `OpenScience/apps/server/src` unless they start with another top-level directory. Labels: LIVE / PARTIAL / DEAD / MISSING; VERIFIED = read in code, INFERRED = deduced from code + the coordinator's production facts.

## 1. Summary

1. **Which engine.** The engine is per account (`evimed_memory.settings.engine`, `researchMemoryPersistence.mjs:267-282`). `memoryEngine()` returns `native` only when the deployment flag is on AND the row says native (`researchMemory.mjs:1875-1881`); a row with no value is decided once by the deployment default and written (`researchMemory.mjs:1885-1904`). The default is `OPEN_SCIENCE_OV_NATIVE_MEMORY_ENABLED = engineSelected` = "an OpenViking URL + root key are configured and the index provider is unset/openviking" (`config.mjs:321-324,344`). So: **default config (no OpenViking URL) = every account legacy; production-like config = every NEW account native, every account that existed on 2026-10-13 stays legacy until `scripts/ops/memory-engine.mjs`** (the migration stamped all existing users `legacy`, `researchMemoryPersistence.mjs:279`).
2. **The two engines are two different products.** Legacy keeps the whole 2026-09-21 design (four-dimension fact, validity intervals, supersede, conflicts, 重读旧记忆, usage counts, identifier rejection in code, forget-by-conversation, rejection ledger, TTL on inferences, timeline). Native keeps *file-level* memory written by OpenViking's extraction under our templates; per-fact validity/supersede/conflict/evidence/usage are MISSING by design (`nativeMemoryStore.mjs:253-296`: `validFrom/invalidSince/supersededBy: null`, `evidence: []`, `conflicts: []`, `usage: {}`). The loss is documented in AGENTS.md; what is NOT documented is the fallout below.
3. **Owner's four criteria on a native account.** (a) *remembers stated preferences/background*: LIVE in principle (templates + per-turn commit), but **zero files exist for the owner in production** — see section 5 for the code-level reasons. (b) *connects to the project*: PARTIAL (project-context template + project tag via overlay; project card read from the file's headings). (c) *obeys edits and deletions*: LIVE and well built (CAS edit, forget/undo with rejection fingerprints, post-hoc checker `nativeMemoryWorker.mjs:49-60,#afterWrite`); only verbatim-line rejection, a paraphrase is re-learned (acknowledged limit). (d) *can show where a thing came from*: **MISSING for conversation provenance** — native records carry `evidence: []`, the profile endpoint returns `conversations: {}, usage: {}` (`nativeMemoryStore.mjs:281,335,385`), so the drawer's 「来源对话」 (`apps/web/src/components/memory/FactDrawer.tsx:348`) cannot render; the overlay *does* hold `engine_session`/`archive_uri` on every revision (`nativeMemoryOverlay.mjs:238-246`) but no route exposes it. Only source-document labels, an as-of date and revision history survive.
4. **Largest structural findings.**
   - **Capsule facts become unreachable the moment an account is native** (VERIFIED): the dispatch profile is withheld wholesale (`residentProfile.mjs:115` returns before `capsules.profileFacts`), the `evimed_capsule_recall`/`_note` tools are not registered (`packages/socket/plugins/capsule.mjs:78,118`, test `packages/socket/test/memoryEntrance.test.mjs:71`), and the OV tools hide the derived `memories/evimed` subtree (`memoryGateway.mjs:691-701`). The migration deliberately does not touch capsule facts (`nativeMemoryMigration.mjs:20`). So the owner's 10 「项目笔记」 `project_fact` documents are readable on the capsule page / growth line / pack export, and by **no conversation**.
   - **A runtime launched before the switch stays on its launch value** (`runtimeManager.mjs:3716-3735`): only idle runtimes are released; a held-open one has no `EVIMED_MEMORY_GATEWAY_URL`, so the OV plugin is off for it (no capture, no profile) while the control plane already treats the account as native (dispatch profile `none("native")`). That is the most plausible reason the owner has no commits on 10-14.
   - **The migration is optional and the owner skipped it** (`migrated_at` NULL): the one legacy `profile` record is now read by nothing (page, recall, dispatch, map all key on the engine).
   - Legacy-only machinery still in the tree for native accounts: `memory-record-index` jobs finish as `native_engine` (`memorySubstrate.mjs:525`), extraction/summary/review skip (`memoryIntelligence.mjs:1251`), so no double-write — verified, with one leak: the agent-memory API (off by default) has no engine check (section 4, D6).
5. **Timeline / 成长**: writer = none by design, reader = LIVE for both engines (`memoryTimeline.mjs:225,393`); on native it is thinner (no supersede events, `ended` always 0) and the growth line **still counts capsule notes** that native conversations can no longer read (`memoryTimeline.mjs:~440`).

## 4. Defects, ranked

**D1 (high, VERIFIED) — Capsule facts are orphaned for every native account.** Dispatch: `residentProfile.mjs:115` returns `none("native")` before `capsules.profileFacts`/`lookupCount` (`:119-121`). Recall: the capsule socket row's memory half is off when `EVIMED_MEMORY_GATEWAY_URL` is set (`packages/socket/plugins/capsule.mjs:78,118`; asserted by `packages/socket/test/memoryEntrance.test.mjs:69-74`), and the gateway hides `memories/evimed` (`memoryGateway.mjs:691-701`). The server-side half (`capsuleGateway.mjs:165-166`, "native → memorySubstrate null") is dead code for a fresh native runtime because nothing calls it. The migration leaves capsule facts alone on purpose (`nativeMemoryMigration.mjs:20`), and evidence-zone subscription recall rides the same capsule `recall` action (`capsuleGateway.mjs:174-177`) so **zone cards also cannot be recalled by a native account**. Effects: the owner's 10 project notes, any imported pack's facts (a received pack's `fact` entries), and zone-subscription reference context are silent for N. Fix class: a native-account read of capsule facts (profile kinds into the dispatch block or into the OV profile; the rest through the recall tool) or register the capsule recall tool read-only for native with `scope: capsule`.

**D2 (high, VERIFIED mechanism / INFERRED cause) — Stale launch value after the switch.** `memoryGatewayUrlFor` is evaluated at launch (`runtimeManager.mjs:3693-3698,4431`); `releaseMemoryEngineRuntimes` releases only runtimes that are idle (`:3716-3735`). A runtime held open by a tab/LoopX/long turn keeps no gateway URL: no plugin capture, no profile, while the control plane already skips legacy extraction (`memoryIntelligence.mjs:1251`) and the legacy resident profile (`residentProfile.mjs:115`). The account is then **learning from nobody and remembering for nobody**, silently. The worker even states it: "the gateway withholds from an account that is not native meanwhile" (`:3712`) — but the opposite case (native account, legacy-launched runtime) has no handling. No metric or readiness fact distinguishes it. Remedy: on switch (and on each `noteRunFinished` for a native account) compare `runtime.memoryGatewayUrl` with the account's engine and mark/restart; at minimum count `native_account_runtime_without_gateway`.

**D3 (high, VERIFIED) — Native "where did this come from" is missing.** `evidence: []`, `evidenceCount: 0`, `conversations: {}` (`nativeMemoryStore.mjs:281,335,385`). The overlay keeps `engine_session`, `archive_uri`, `project_id` per revision (`nativeMemoryOverlay.mjs:238-246`, `native_sessions` table) but `publicRevision` omits them from the record's `revisions` (`nativeMemoryStore.mjs:~283`) and there is no record-provenance route. The fourth owner criterion fails for N without any new storage; it needs a join (revision → `engine_session` → run/conversation title).

**D4 (medium, VERIFIED) — The switch can strand legacy rows with no reader.** `memory-engine.mjs:85-87` refuses a native move with records unless `--migrate` or `--leave-records` is given, so the owner's one legacy `profile` record was left on purpose (INFERRED: `--leave-records`, since `migrated_at` is set only by `runMigration`, `nativeMemoryMigration.mjs:~196`). After that, page/recall/dispatch/map all key on the engine (`memoryRoutes.mjs:83-85`, `memoryMap.mjs:524`), so the legacy row is visible nowhere except account export (`server.mjs:7422`). It also counts in `engineWalk`'s "legacy writes after move" check only if `updated_at` moves.

**D5 (medium, INFERRED from code) — Owner has no native files: what the code allows.** See section 5; the strongest code-level explanations are D2 (stale runtime until the 10-18 release) plus "attended turns only" (`nativeTurnCommit.mjs:124` skips every programme/autopilot/geo/vcr/platform/LoopX run), plus a conservative template ("A conversation with nothing of that kind produces no memory operations at all", `profile.yaml`), plus a `completed` commit being recorded even with zero operations.

**D6 (low-medium, VERIFIED) — Agent-memory API ignores the engine.** `agentMemoryRecall.mjs:172-178` calls `recallAcrossMemory({capsules, memorySubstrate})` with no engine check; for a native account it would read the stale PostgreSQL rows and the capsule facts. Its episode writes go to `recordRun`, which skips native accounts (`memoryIntelligence.mjs:1251`) → silently nowhere. Off by default (`config.mjs:3213`), so latent.

**D7 (low-medium, VERIFIED) — Native reset does not hold against in-flight work.** No reset instant on the native path (`grep resetInstant|endedBeforeReset` in `nativeMemory*.mjs`, `memoryAdmission.mjs`, `memoryGateway.mjs`, `nativeTurnCommit.mjs` is empty). A commit/extraction already accepted by the engine before `reset()` finishes (`nativeMemoryStore.mjs:737`) can write files afterwards; the plugin's offline queue (7-day replay, `memoryAdmission.mjs:~47` comment) can re-post earlier messages into a fresh session. Legacy has `endedBeforeReset`.

**D8 (low, VERIFIED) — Forget-and-don't-relearn on native is verbatim-only.** `lineFingerprint` = lower-case/whitespace/as-of normalised sha256 (`nativeMemoryOverlay.mjs:40-45`); a reworded line is accepted back (acknowledged in the file header, but the owner rule "obeys deletions" is only as strong as the engine's paraphrase habit). Compare legacy: blocks by (kind,key).

**D9 (low, VERIFIED) — 成长 line counts capsule notes for native accounts.** `memoryGrowth` reads the capsules' `fact` documents regardless of engine (`memoryTimeline.mjs:~436-446`), so the owner's growth chart can show 10 "memories" the conversation cannot see (D1) and omits legacy records.

**D10 (low, VERIFIED) — Conflict path never fired in production (0 rows).** Mechanism needs the model to emit `conflictsWith` (`memoryIntelligence.mjs:709,808,1536-1561`). Same-key changes are revised not flagged. Either the feature is effectively dead or the prompt never elicits it; add an eval case before anyone relies on `caveats: conflict`.

**D11 (info, VERIFIED) — Dead config/legacy weight.** `memoryContextLimit`/`MaxChars` only budget the tool arm; the dispatch recall path they were built for is dead by ruling. The recall-tool floor (`memorySearchMinScore` 0.75, `config.mjs:2780`) is calibrated on one measurement (comment `:2775-2778`).

## 5. Production facts explained (coordinator's 4 points)

**5.1 Engine assignment.** 4 native accounts: owner (`<owner-account>`) and `team-demo` switched 2026-10-13 12:49 UTC by `scripts/ops/memory-engine.mjs` (the only writer of an existing account's engine, `researchMemory.mjs:1911-1925`); two `qa-rectify` accounts are new accounts that took the production default (`engineSelected`, `config.mjs:344`) on 10-19. 5 legacy: accounts that predate the column (stamped `legacy` by the migration, `researchMemoryPersistence.mjs:279-280`) and never moved, plus platform/system accounts. `cdss-access` is legacy for that reason.

**5.2 `migrated_at` NULL for the owner.** `noteMigrated` is called only at the end of `runMigration` when no group failed (`nativeMemoryMigration.mjs:195-197`). `team-demo` therefore went through `--migrate`; the owner did not. With one active `profile` record in `records` (not sensitive, not system, `MIGRATED_KINDS` includes `profile`), `switchEngine` would have refused a plain move (`memory-engine.mjs:85-87`), so the owner was moved with `--leave-records` (INFERRED; the other way to get NULL is `plan.carried == 0`, which that record contradicts unless it is `origin: system`). Consequence: the engine has never been told what the owner said before 10-13, and the legacy `profile` row is orphaned (D4). The 10 capsule facts were never in scope of the migration (`nativeMemoryMigration.mjs:20`).

**5.3 Owner's user dir has only the derived index (10 files under `memories/evimed/capsule/<id>/project_fact`, last 10-08), zero native files.** Those 10 files are the capsule index (`memoryIndexing.mjs` publishes approved capsule facts under `memories/evimed/capsule/…`) written while the owner was still legacy; nothing rewrites or removes them for a native account and the gateway hides them (`memoryGateway.mjs:691`). Native files appear only after an engine extraction that produced an operation. For the owner none did: see 5.4.

**5.4 Commits and the missing files.**
- *What is committed:* only an **attended** turn of a native account (`nativeTurnCommit.mjs:117-130`): platform-started runs (`automated`, `autopilot:*`, `geo:`, `vcr:`, `platform-*`, LoopX continuation, `memoryDispatch.mjs:25-33`) are never armed; the project must not be internal; the admission must say native+learn (`:187-190`: pause, trial, clinical context, internal agent, subagent, engine-templates-unconfirmed all withhold); and the session must have pending tokens after two agreeing reads (`:196-215`). Nothing is committed unless the plugin first forwarded messages through the gateway (`messageWrite`, `memoryGateway.mjs:397-436`).
- *Was it live on 10-14?* The merge is dated 2026-10-14 04:30 (`PROGRESS.md:83`, commit `030f48d18`); whether the production release of that day contained it is not provable from the tree (INFERRED: not before R18.2/R19; the owner's two commits on 10-19, after the 10-18 R19 release, are the first evidence it ran).
- *Why zero commits on 10-14 despite 1,396 kernel calls:* three code-level explanations, all consistent with the facts: (1) **D2** — a runtime launched before 12:49 on 10-13 and held open has no gateway URL, so the plugin forwarded nothing and the engine's own idle commit (`session_auto_commit` enabled, 900 s idle, `scripts/ops/openviking-configuration.mjs:121,131`) had no session to commit; (2) the day's calls were mostly platform-started (programme/evidence/VCR/LoopX runs are excluded by design); (3) the per-turn commit may not yet have been deployed. - *Why two `completed` commits yield zero files:* `completeCommit` records `completed` as soon as the archive's `.done` exists, whatever the number of operations (`nativeMemoryWorker.mjs`, `ingest` returns the count; `completeCommit(…, {operations})`). The templates are deliberately conservative — "Keep only what the user would expect the assistant to still know next month… When that is doubtful, leave it out. A conversation with nothing of that kind produces no memory operations at all" (`profile.yaml`, `preferences.yaml`) — and an owner whose conversations are task briefs (scientific work orders, not statements about themselves) legitimately yields nothing. The other path to "zero files" is the post-hoc cleaner deleting a file whose every line is refused (`#afterWrite`: `identifier_shape`/`platform_text`/`rejected_line` → file removed, revision `actor: platform`); that would leave `native_revisions` rows with `actor='platform'` and `open_science_native_memory_checks_total` non-zero — a one-line SQL check discriminates. The engine failing silently is *not* possible without a trace: a failed extraction leaves `.failed.json`, state `failed`, and is replayed up to 5 times (`nativeMemoryWorker.mjs:255-310`, `config.mjs:2753`). The QA accounts' files (12 under `memories/projects`, 1 profile for team-demo) show the engine and templates work end to end.
- *`memory-extraction` 965 calls/14 d:* the purpose is shared by **legacy extraction, 重读旧记忆, the map's topic grouping and OpenViking's own extraction** (`openVikingModelCaller.mjs:48`, `memoryIntelligence.mjs`, `memoryReview.mjs:117`, `memoryTopics.mjs`), so the count does not say how many native extractions ran.

## 6. Answers to the other key questions

- **nativeTurnCommit:** after an attended turn, 8 s quiet (`OPEN_SCIENCE_NATIVE_MEMORY_TURN_COMMIT_DEBOUNCE_MS`, `config.mjs:2764`), two agreeing engine-session reads (2 s apart, 4 attempts), then `commitSession` through the gateway's own path (same admission, hourly bound 120, ledger row `origin: gateway`). Automated/scheduled/autopilot/geo/vcr/LoopX turns never arm; the gateway lets a commit pass while one runs (`nativeTurnCommit.mjs:30-40`). The platform's injected text is excluded one door earlier: a message carrying any platform tag is never forwarded to the session (`memoryGateway.mjs:165-185`), tool parts and `peer_id` are dropped; the replayed archive goes through the same filter (`nativeMemoryWorker.mjs:#replay`).
- **Double-write / stale Postgres reads:** none found for a native account in the main paths — legacy extraction, run summary, review, index jobs and sweep all return early (`memoryIntelligence.mjs:1251`, `memorySubstrate.mjs:525,672`), recall/profile/page/map key on the engine, and `engineWalk` asserts it (`researchMemory.mjs:1950-1980`, `/api/ready`). Exceptions: the agent-memory API (D6) and the capsule note gateway action, which has no engine check but is unreachable because the tool is absent. A deleted legacy record's index copy is not removed for a native account (`indexRecord` finishes `native_engine` before removing) — harmless since native recall never reads it.
- **Capsule facts/packs at recall and dispatch:** legacy = unioned with records in `recallAcrossMemory` and resident profile (profile kinds only: profile, expertise, preference, stance, writing_style, `capsuleProfile.mjs:31-37`); native = not read at all (D1); methods (skills) are engine-independent.
- **Timeline / 成长:** writer none (by design, §10.4), reader LIVE for both; thinner for native (D9, no supersede).
