# B. Learning loop and learned methods (review of 2026-10-23)

Scope: how EviMed learns a researcher's methods and puts them back into use. Read-only review of the working tree at `main` (HEAD d8be3abaf plus uncommitted frontier work, which does not touch this slice). Evidence tags: VERIFIED = read in code at the cited place; INFERRED = follows from code but needs production data to confirm. All paths are under `OpenScience/` unless absolute. Nothing under `.evimed-local/secrets/` was read; production facts come from the coordinator's message and are explained in section 6.

## 1. The loop as it runs today (defaults)

1. Trigger. When any run ends, `server.mjs` `onRunFinished` writes the transcript, then (after `if (!reusableClinicalContext) return;`, server.mjs:4096) runs memory extraction and calls `learningTriggers.afterRun(project, run, memoryResult)` (server.mjs:4101/4194; `learningTriggers.mjs:553`). `learningTriggersFor` (learningTriggers.mjs:273) refuses non-researcher work (`isResearcherOwnedWork`: evaluation/automated runs, verification runs, internal projects, internal capabilities), incomplete transcripts, paused accounts, trial sessions, clinical-context runs, runs before a memory reset. Then it produces up to four lessons:
   - `correction` when `run.corrections > 0` (a message typed into a running turn) or the extractor wrote a `correction` memory (legacy-engine accounts only); plus a separate path for `result-corrected` feedback events (`correctionLessonFor`, :378, `afterCorrection`, :620). Never sampled.
   - `delivered` when the run succeeded and left a file (`leftFiles`, :162: artifacts, unverifiedArtifacts or outputFiles). Sampled by hash of run id at `OPEN_SCIENCE_LEARNING_DISTILL_SAMPLE_SHARE` = 0.33 (config.mjs:3112).
   - `repair_accepted` when the same run also needed more than one submission. Sampled at `..._REPAIR_DISTILL_SAMPLE_SHARE` = 0 (config.mjs:3123), so on defaults it never queues.
   - `routine` on the 3rd, 6th, 9th... successful file-leaving run of one capability, counted across all the researcher's own non-archived projects in a fixed 90-day period (`routineFamily` :209). Never for `open-domain-answer` (:98, :174).
   - `edit_diff` is only produced by the click-driven `feedbackEvents.mjs:538` path (adopt-and-edit); no automatic producer.
2. Distil. `distill` job -> `MethodDistillationRuns.execute` (methodDistillationRuns.mjs:~400) builds a frozen `distillation-input.json` (researcher corrections first, last 20 listed methods then 8 as `relatedMethods`, up to 4 peer runs for `routine`) and dispatches the internal `method-distillation` capability (v1.3.0) as a bounded run in the learning project. The model may answer create / amend / merge / no_change.
3. Effect. `applyCandidate` (:~500) writes `provenance.origin = "inferred"` always. A lesson whose only evidence is the platform reviewer (`signal = reviewer`) becomes a handbook candidate, not a method. Otherwise `LearningService.createCandidate` computes `promotionVerdict`; the only blocker is an unresolved conflict with an approved method (methodGraph.mjs:574). A method is `approved` at birth (the 2026-09-20 "effect first, evaluate later" ruling), and the paired-evaluation stack no longer exists.
4. Integrate/consolidate. Each write queues `consolidate integrate` and `sleep` jobs; an hourly `sleep` pass per researcher also runs (config.mjs `learningConsolidationIntervalMs` = 3.6M ms): approve candidates, screen pairs (J1 judge), group, DECIDE (model), apply relations, BUILD merges (model), retirement proposals, apply the "immediate" ones, complete pending merges, give each method a Chinese title/steps (`describe`, max 10 per pass).
5. Mount. At runtime launch only, `RuntimeManager.syncCapsuleMethods` (runtimeManager.mjs:3787) rebuilds `capsule-methods/` (0444 files): own capsule entries, then up to 16 learned methods (most recently approved first, byte budget spent on the card size `learnedMethodCardBytes`, learnedMethodMount.mjs:167), then received packs. Family filter: GEO runtimes get GEO methods; every other non-internal project (including the ordinary conversation) gets "research" methods (`learnedMethodFamilyForRuntime`, :74). The model sees a card (name, when-to-use, file path) in the system prompt section `evimed:capsule-methods` (plugins/capsule.mjs:342, ceiling 12,000 chars) and in delegations; it opens the file when it judges the method applies.
6. Count. On run end `recordMethodUse` (server.mjs:1502; called at :4049, i.e. after the clinical-context early return at :4010) derives, per run: methods loaded (mount receipts), invoked (file opened via `read`, `grep` on the file, or a bash READING_PROGRAM naming `_lm<hex>/SKILL.md`; `methodObservations.mjs:115-205`), per-deliverable observations (accepted/repaired/rejected + invoked), `read` (opened but credited to nothing), `carried` (card in front of a model that answered), `eligible`. Written to the method's `learning.counts` and the run ledger's `methodsLoaded/methodsInvoked`.
7. Retire. `retirementProposal` (methodGraph.mjs:637): incident (immediate); scientific regression (immediate for inferred; rolls back to the previous body or stops); harm test over invoked runs (immediate); `never_opened` = carried >= 20 answered runs and zero opens (immediate, safety-related exempt); contribution <= -0.1 over >= 20 loaded (proposal only); superseded and unused (proposal only); library over 50 effective (proposal only). Only the immediate ones are acted on (methodConsolidation.mjs:461). A project's deletion retires methods learnt only there.
8. Observability. Positive counters exist (learningMetrics.mjs:105-263): `open_science_learning_{mounts,mounted_methods,mounted_bytes,runs_with_methods,delivery_lessons,repair_lessons,method_retirements,run_methods}_total` and gauges `methods` by status, `distill_jobs` by trigger and status, `distill_results`, `method_uses`, `spend_cny`. This closes appendix A row 7 of the build spec (VERIFIED).

Defaults that shape all of this (config.mjs:3064-3123): learning on, no window, no CNY caps, concurrency 2, consolidation hourly, unused-retire 20 loads. `OPEN_SCIENCE_LEARNING_PLATFORM_HANDBOOKS_ENABLED` and `..._EVIDENCE_OUTCOMES_ENABLED` are off (config.mjs:691-697). (`deploy/web/docker-compose.api-only.yml:109` defaults learning off for the api-only stack; `.env.example:398` sets it true.)

2. "Loaded 34, invoked 0" (2026-09-28). ## 4. Defects ranked

Severity 1 = breaks the loop's purpose now; 2 = significant quality or correctness; 3 = hygiene.

1. (Sev 1) The hourly consolidation pass is a no-op that reports success. `sleep` skips DECIDE and BUILD for any group containing an unproven merge (`unprovenMerge`, methodConsolidation.mjs:281, :424) but still counts the group (`groups: groups.length`, :501) and the job succeeds. An unproven merge can only clear through `methodHarmTest` returning `clear`, which needs >= 4 *invoked, accepted* runs of that body (methodGraph.mjs:381-420; goodStep -0.405 vs lower bound -1.558); with the library this size and near-zero usage it never clears, and groupPairs puts every overlapping method into the single group (max 8), so one stuck member freezes relations, merges, dedup and the "supersedes" path for the whole account. VERIFIED mechanism; production fit in section 6.
2. (Sev 1) Learning teaches the gate and the platform's choreography rather than the researcher's habits, and nothing stops stale lessons. `routine` (every 3rd run, unsampled, signal `run`) and `delivered` induce "what the run did"; for capability runs that is submit/anchor/receipt behaviour. SKILL.md asks the model to avoid it (v1.3.0) but there is no deterministic check (principle 5 says model-judge, but there is none either; platform-handbook judge J23 is off). Existing handbooks and methods are never swept when a ruling removes a feature (09-17 ruling, deleted package files). No retire path for handbooks other than the owner's click and the evolution harm test (off).
3. (Sev 1, INFERRED) Who is learned from: with the owner using the platform lightly, a native memory account and few file-leaving turns, the loop sees almost no signal, and the one account it learns from is the acceptance account `cdss-access` whose traffic is synthetic briefs not flagged `automated`. The ordinary conversation's most common correction ("no, redo / shorter") arrives as a new turn and is invisible to the trigger for native accounts (the extractor's `correction` source is skipped, memoryIntelligence.mjs:1251; the steer count only sees messages typed *during* a turn). Nothing in the platform tells the owner "nothing learned in 10 days".
4. (Sev 2) No guard that a learned method or handbook is consistent with platform rulings or current features (methodSkill.mjs). The only guard is a sentence in the card.
5. (Sev 2) Non-immediate retirement proposals (contribution <= -0.1 after 20 loads; superseded; library over 50) are computed every hour and then discarded (methodConsolidation.mjs:461; no consumer of `retirements`). Together with `applyRelations` skipping `supersedes` (:587) the "superseded" branch cannot occur at all. The 50-method library cap is unenforced; the mount takes the 16 newest approved, so methods 17+ are never mounted, never `carried`, and so can never be retired by `never_opened` either.
6. (Sev 2) Related-method selection for distillation is recency, not relevance: `listMethods(limit 20)` ordered by `updated_at DESC` (productStore.mjs:171) then `slice(0, 8)` (methodDistillationRuns.mjs). The SKILL tells the model to amend rather than duplicate, but it is shown the 8 most recently written methods, not the 8 related ones. Library > 100 is not seen at all by `listMethods(100)`/`approvedMethods`.
7. (Sev 2) A method takes effect "at once" but is mounted only at the next runtime launch; no refresh or release when a method is approved or retired (retire-by-pause only). A learned method can therefore wait hours for its first run, and a retired one stays in a live runtime's prompt.
8. (Sev 2) Counts: `recordMethodUse` runs only after `if (!reusableClinicalContext) return;` (server.mjs:4010), so every conversation that read clinical VCR data leaves no counters and no `carried`; `methodsLoaded` for the answer line depends on the run-state projection being written (evidence-store mirror), unverified for ordinary turns here. `eligible` counts approved-but-unmounted (beyond 16) methods as "passed over".
9. (Sev 3) Stale text: `capabilities/method-distillation/capability.yaml` persona still says "only an independent paired evaluation decides whether it takes effect" (deleted 2026-10-10); `SKILL.md` line "Every trigger is set by the platform" is right but the persona contradicts the ruling. `learning.evaluations` residue on old records. `edit_diff` (SKILL section 1) has no automatic producer.
10. (Sev 3) `invoked` detection by bash text requires the literal `_lm<32hex>/SKILL.md`; `cd dir && cat SKILL.md`, globbing, or `cat dir/*` are not counted (under-count only).
11. (Sev 3) `methodsSectionText` adds up to 12,000 chars of cards to the system prompt of every session, including the ordinary conversation whose own always-on text is about 4,000 characters (AGENTS.md). With 8 methods this is small, but the ceiling is three times the persona.

### 6.1 Why learning stopped on 10-12/13 (distill last 10-12; `learning` spend last call 10-12)

The worker is enabled (consolidate jobs succeed hourly, so `OPEN_SCIENCE_LEARNING_ENABLED` is on). The two halves stopped for different reasons, and both line up with 10-12:

a) Spend (`learning` purpose) stopped because the model steps of the consolidation pass stopped. The `unprovenMerge` guard landed on 10-12 night (commits 690bfac89 and the 9083f6c27 fix), together with `scripts/ops/retire-unproven-merges.mjs` (the 27 merge-built methods, which explain "29 retired"). VERIFIED mechanism, INFERRED that the group holds such a member (see 6.3). Also from 10-12 the repair lessons went to share 0 (466cb41b4/245d4794d) and the delivered sample is 0.33 (since 10-10): 21 of the 28 lessons read by 10-12 were `repair_accepted`, which now never queue.

b) Distillation stopped because the remaining triggers need things that did not happen. ### 6.2 All 70 method documents belong to cdss-access; they are about gate bookkeeping
