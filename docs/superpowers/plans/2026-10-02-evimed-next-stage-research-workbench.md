Status: revised product plan, 2026-10-03. **Section 11 is the current backlog and sequencing decision.** Sections 1–9 preserve the October 2 research baseline, and section 10 records subsequent implementation; neither an old missing-feature statement nor the original week estimate overrides section 11. Public leaderboard work is excluded. Implementation, release qualification and production activation remain separate actions. Discussion is in Chinese; repository documents are in English.

The next cycle strengthens scientific material accuracy, reproducible results, continuing research decisions and useful learning on the existing hosted SaaS, fixed DSH/model and deterministic engines. Immutable results, selected replay/export, anchored revision and evidence-change continuation now have implemented source paths. Extend their remaining coverage and verify complete research workflows rather than build them again. Finish independent development while the team completes its current acceptance; unified integration, release qualification and deployment follow both tracks.

This decision follows a second pass through Claude Science's official documentation and independent commentary, both Open Science repositories, their implementation and test files, and EviMed's actual code. A feature described in a README, a renderer with empty fields, a source-level test and a successful deployed workflow are different levels of evidence.

## 2. EviMed's actual starting point

The competitive comparison must extend these implementations rather than count them as missing:

| Capability | Already present | Actual gap or verification needed |
| --- | --- | --- |
| Research conversation and branching | Native DSH sessions, turn navigation and `session/fork`; fork relation is adopted into the control-plane run ledger. | Compare selected results across branches while retaining the exact original source/version. No second session framework. |
| Evidence reading | `ReportReader`, `ClaimCitation`, quoted source captures, claim findings and the single domain quality implementation. | Bind every displayed result version to its own claims, evidence and numerical records; distinguish an unavailable check from a clean result. |
| Artifact history | `record_provenance` / `list_provenance`, `ProvenancePanel` and a reproduction prompt. | Generic native DSH write-to-history coverage is **unproven**: the frontend derivation helper has no production caller found; the observed DSH event consumer updates run progress. History storage does not yet prove automatic capture. |
| Provenance contents | Current writer stores path, sequential version, time, tool and optional text/log/session/call/model. Accepted deliverables and specialist/VCR results have stronger, separate receipts and digests. | The writer does not persist the shared type's environment/run/diff fields. A log description is not an execution receipt; a current path is not an immutable old artifact. Reuse the stronger existing records first. |
| Multi-output writes | Tool events and file records exist. | Current writer deduplicates by call ID plus session ID, without path. A future fan-out producer must retain all outputs. Test this before adopting the upstream helper. |
| Scientific viewing | Existing PDF, document, table, plot and scientific-format viewers; report/file routes remain available beside the native workspace. | Prioritize medical tables, figures and source PDFs. Viewer existence does not establish durable annotations or complete scientific provenance. |
| Export | Account/project archive and Word/PDF document conversion. | A selected, version-bound research result with authorized evidence and an inspectable computation recipe; not another general account export. |
| Computation | Six specialist agents plus VCR's deterministic R methods; VCR lineage, result hashes and data-plane controls. | A shared view of existing computation facts and replay eligibility across ordinary outputs. A generic prose artifact is not automatically replayable. |
| Source freshness | `sourceUpdates.mjs` already looks up Crossref correction/retraction notices when a reader checks claims. Source intake, frontier and agendas exist. | Distinguish no updates found from lookup unknown/failed, then map an update to affected results. Do not build a second retraction service. |
| Memory and reusable methods | Owner-scoped research memory, capsules, learned methods/handbooks, revisions and application records. | Demonstrate actual use and outcomes on normal tasks; tie each result to the method revision used. No duplicate memory service or paid method on/off campaign. |
| Runtime and extensions | One DSH kernel, harness port, immutable extension generations and server-side gateways. | Finish actual serving qualification and current release evidence. Desktop runtimes, ACP and additional kernels are not integration targets. |

## 5. Final product scope and integration design

### 5.1 The first two result journeys

**Evidence report:** open a drug-evidence report, select a claim, see the preserved quotation and source status, inspect the finding for this report version, request a bounded revision, and compare the successor. A corrected source must not silently rewrite the original.

**Deterministic analysis:** open an existing statistical result or forest plot, inspect its machine values and producing engine job, rerun the selected calculation from frozen authorized inputs, compare values under declared tolerances, then export the selected result and its available evidence.

These journeys anchor the cycle. Generic artifact support expands from them only after capture is demonstrated. No new medical capability is being invented merely to expose these platform functions.

### 5.2 One result contract over existing authorities

Add a small versioned projection in `packages/domain`; retain current run/source/engine records as their authorities. Store any new immutable artifact bytes through the project's existing storage boundary and append only missing version/relationship records to the existing product persistence facilities. There is no second run ledger, provenance database or agent-authored bookkeeping package.

| Record group | Required meaning | Authoritative producer |
| --- | --- | --- |
| Identity and ownership | Project, run, native session/branch, artifact identity, version, relative path, digest and byte size. A path alone cannot identify old content. | Authenticated control plane; server-checked stored bytes. |
| Producing work | Tool call or deterministic engine job, observed execution status, command/code snapshot when available and timestamps. Separate observed from declared/inferred facts. | DSH observation through harness-port, existing engine/controller receipts. Never a browser-submitted claim of verified execution. |
| Inputs and dependencies | Exact preserved source/input versions and hashes; only dependencies of the selected target; whether bytes remain available/authorized. | Source service, accepted delivery records, engine inputs and VCR lineage. Filename/mtime proximity is insufficient evidence of dependency. |
| Computation | Method, parameters, seed where relevant, machine values and units. | Existing deterministic engines. Model-produced prose cannot replace numerical output. |
| Environment and method identity | Actual runtime image/engine version, available lock facts, capability/skill/extension/handbook revisions. Unknown values remain unknown. | Runtime and job receipts plus effective generation records. A reconstructed environment is labeled as such. |
| Review and source status | Claim finding and its exact source/output version; current/stale/unavailable state; update-check status/time. | Existing review, domain verification and source-update paths. No findings or failed reads must not be displayed as “verified.” |
| Reuse eligibility | Available, partial or unavailable recipe with specific reasons; included/omitted/restricted bytes in export. | Domain projection derived from the above records, scoped only to the requested reuse operation. |

Suggested placement is a focused domain module plus a server service/route and worker only where required by storage or long execution. Follow the existing module/feature-toggle conventions; do not scatter artifact policy across the browser, MCP and engine implementations. Every new DSH seam goes through `harness-port`, its manifest and a live probe.

### 5.3 Capture before presentation

1. Trace one ordinary native session and one specialist result from execution to stored artifact. If another authoritative capture already exists, reuse it; otherwise connect the missing producer path. Start with supported write/edit events, submitted deliverables and deterministic engine outputs.
2. Preserve actual completed output bytes and available code/input snapshots. An arbitrary shell command or opaque third-party tool may have unknown dependencies; do not infer complete provenance from a success title. Capture failure records a gap and leaves the research output available.
3. Make ingestion idempotent across event replay/reconnect and parent/child sessions. For multi-output calls, identity includes the owning session/run, event/call and normalized artifact path/version; a call-level deduplication key must not discard a second file.
4. Test overwrite, rename, binary output, two files from one call, child output, branch output, disconnect replay and concurrent writes. Snapshot publication must not bind a digest to bytes that changed during capture. Existing path guards, capacity limits and tenant checks apply.
5. Expose capture coverage honestly. Legacy capped text and absent environment/code facts are not retroactively converted into full execution records. Retention/deletion/access changes remain enforceable when inspecting historical versions.

### 5.4 Inspection, revision and branch comparison

Extend current report/file routes and the native right-hand workspace. Use `ReportReader`, `ClaimCitation`, `ProvenancePanel`, `RunFilePage` and supported native bridge extension points. Verify slot/event availability before adding an adapter; do not create a second composer or parallel workspace.

The minimal revision reference contains the artifact/version digest, claim or element identifier, selected text/region and the user's instruction. The server resolves and authorizes the target again before putting it into the existing native conversation. Persist the reference with that request so a later edit cannot retarget it silently.

Start with a report paragraph, an evidence-table row/cell and a plotted result backed by machine values. PDF anchors additionally require the source digest, page and parser/region identity; stale anchors are shown as stale rather than moved to a similar-looking passage. Reuse the in-house parsing service.

A cosmetic edit preserves numbers and citations. An analytic edit changes the generating calculation and enumerates affected claims/tables/figures; create a successor version, retain the original and show meaningful value/source differences. `revisionGateway.mjs` remains the narrow accepted-deliverable repair authorization; it is not a general editing API.

Comparison uses existing native branches and selected artifact versions. No automatic branch merge, conversation replay engine, whole-report regeneration requirement or collaborative comment threads are included.

### 5.5 Selected calculation replay

A replay is a new, owned job linked to a frozen target recipe. Initial eligibility is limited to declared deterministic engine adapters; a hash does not make an arbitrary imported script eligible. It is not a resubmitted LLM prompt labeled reproducible.

- Eligibility requires available authorized inputs, a supported deterministic method/code path and an identified compatible execution environment. Store why a recipe is incomplete rather than inventing a dependency.
- Reauthorize inputs at execution time. Imported scripts/manifests remain untrusted. Use existing isolated jobs, specialist adapters, controller and VCR engine; patient-level VCR data stays in its data plane.
- Execute into a new output location. Never install packages into a live immutable DSH profile, overwrite the original result or replay external mutations automatically.
- Preserve input/code/environment identities and actual completion/cancellation/cleanup observations. A connection timeout is not proof the process stopped. A retry must resolve the previous attempt's ownership to avoid duplicate computation.
- Compare machine values using the method's declared tolerance and units. Distinguish exact bytes, acceptable numerical agreement, differences, substituted methods and unavailable comparison. Scientific applicability remains a separate evaluation.
- Initial reference analyses: an existing meta-analysis fixture, a FAERS signal fixture, a bibliometric network fixture, an analytic VCR design fixture and a VCR comparator fixture. Use existing deterministic test data and name the exact method/fixture in implementation. Five workflows must pass their own criteria; five files from one run do not count as five analyses.

An ineligible or failed replay never withholds the original report or unrelated completed work. Source code and environment export alone do not promise cross-machine equivalence.

### 5.6 Selected research package

Extend current exports with one selected result/version, authorized source bytes where distributable, machine values, code if captured and the result projection. Each included object has size and digest; omitted inputs stay explicit references with a reason. The minimum package is useful for inspection even when replay is unavailable.

The first implementation is EviMed's small export contract. Map it to RO-Crate only after the pilot is stable; validate that mapping against a pinned specification and an independent reader before claiming interoperability. AIPOCH `.science` import/export compatibility, full account migration and whole-session execution replay are separate future work.

Import/inspection never executes code, resumes jobs, restores connection credentials or grants access to original tenants. Reuse current archive bounds, storage paths and account/project authorization. No new signing service is required.

### 5.7 Evidence reliability and continuous research

Measure existing high-use literature, guideline/label, trial-registry and drug-safety routes before adding providers. Record metadata/abstract/full-text availability, preserved digest, parse coverage, source date, access status, retries and named failure. Count a successful metadata response as metadata, not full text.

Use the AIPOCH deadline/cancellation fixtures to check current connectors: the total deadline covers attempts and streamed bodies; Retry-After respects remaining time; a mutating request is retried only with an appropriate idempotency contract. Keep robots handling, DNS-pinned fetches and keys in the existing gateways.

Extend current source-update results to distinguish checked/no update, changed, unknown and unavailable. Use versioned claim/input links to identify potentially affected results. An already authorized agenda can create a bounded successor analysis; otherwise surface the impact for the next user-directed continuation. Preserve the prior result and state what changed, what was recomputed and what remains uncertain.

Existing autonomous method distillation/application continues. Record the exact method/handbook revision used and observed outcome; test data supplements, changed subjects, source deletion and interrupted runs. Do not introduce a manual promotion ceremony, second memory store, paid method on/off evaluation or automatic global sharing.

## 7. Acceptance and success measures

Use the existing briefs/incidents to establish a baseline before claiming gains. Start with **12 ordinary workflows** across drug evidence/selection, evidence synthesis, user-data analysis and VCR, plus **12 follow-up or failure cases**. This is an offline evaluation cohort, not an extra requirement imposed on each user conversation; it supplements current capability and 22-case extension acceptance.

| Measure | Acceptance or measurement definition |
| --- | --- |
| Usable current-version delivery | Readable/downloadable supported work with named limitations. Report numerator, denominator, code/image/model identities and failure classes. |
| Capture and traceability | Every declared pilot artifact/claim resolves to its preserved evidence or numerical source, or exposes its gap. This does not claim that a quote logically supports the conclusion. Capture coverage is reported by supported producer class. |
| Numerical reproducibility | Five designated deterministic analyses meet their own tolerances. Report unavailable, failed, numerically changed and substituted-method results separately. |
| Revision integrity | Old versions remain identifiable; changed values propagate to their dependent claims/figures; unchanged sources keep their original references. Imported or revoked objects cannot regain authority. |
| Scientific quality | Offline examination of unsupported conclusions, method suitability, applicability, source omissions, duplicate observations and numerical consistency. AI judgments are labeled as such; no clinical-validation claim. |
| Researcher verification effort | Time/steps to find a supporting quote, inspect a figure's value and understand a changed conclusion. Proposed target: median time 30% below the same-task baseline without increased substantive errors. This is a target, not a measured improvement. |
| Reliability and cost | Completion-time/cost distributions per usable result, repeated calls, interrupted work retained, late cancellation and cleanup. Use normal authorized budgets; do not introduce new account spend caps. |
| Method usefulness | Exact revision used, successful reuse, corrections/regressions and continuity after supplements/restarts. Counts of skills, memories or subagents are not success metrics. |

Tests assert observable boundaries and outcomes, not a mandatory tool order or prose template. Engineering authorization, tenant isolation, path validity and valid compute inputs remain enforced on their specific operation. Advisory research findings do not become whole-answer vetoes.
