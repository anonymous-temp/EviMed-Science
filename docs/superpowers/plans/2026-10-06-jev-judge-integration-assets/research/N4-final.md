### C1. GEO probe-answer sanity: refusal / session / busy / chrome detection (STRONG)
- File: apps/server/src/geoSanity.mjs:82-110 (`classifyProbeAnswer`), markers in packages/domain/src/geo/sanity.json (session_invalid 9, service_unavailable 12, refusal 8, page_chrome 11; length caps 400 chars) ; `stripPageChrome` geoSanity.mjs:51; consumed by geoParse.mjs and `failureMode` (geoParse.mjs:343).
- Today: substring marker lists over the Chinese text a consumer AI engine returned decide valid / suspect / refusal / failed. Open vocabulary (every engine rewords its refusals: "抱歉，我无法…", "不能为您提供用药建议"); a miss turns a refusal into 漏提我方 ("omitted") and a login wall into a measured answer, so it distorts the owner's metrics. The module header itself says "deletable when the probe host reports state as statuses".
- Closed question: for answers <= 400 chars (the only ones the refusal/busy rules apply to) choice over {real answer, refusal to answer medical question, login/captcha wall, capacity/busy notice, page shell only}. Tail chrome stays code (format).
- Volume: one call per probe snapshot, only the short-answer subset (long answers skip the model): hundreds to low thousands per measurement round. Cheap.
- Fallback: keep the marker lists as the net (Jev unavailable or abstains = today's verdict). Labels: every stored snapshot has `status`/`reason`/`marker` from the regex, so agreement can be measured on production snapshots; disagreements are the review set (~100 hand labels would do).
- Note: sits next to the already-covered geoJudge split but is a different file and a different question (answer is usable vs not), not a statement judgement. Control-plane code, no key problem. Not security.

### C2. GEO media market: outlet remark / catalogue classification (STRONG)
- File: apps/server/src/geoMarket.mjs:170-193 (`MARKET_BLACKLIST_RULES`: refuses_medical, community_ranking_slot, contact_allowed; `REMARK_FLAGS`: silentEdits, indexingPromise/Disclaimed, weekendYes/No, linkMonth) applied in `catalogueVerdict` geoMarket.mjs:363-383 and `catalogueRow` :403.
- Today: regexes over the vendor's free-text `remarks` / title (e.g. 「医疗不发」, 「收录不包」, 「周末可发」, 「修改不通知」) decide whether an outlet is blacklisted for medical evidence orders and set the flags that feed the outlet score. The header calls them "closed patterns the vendor's boilerplate uses", but the vendor's remark text is free-form per outlet, negation and ordering variants (「不接医药类」「医疗类稿件谢绝」「药品勿投」) escape the patterns; the failure mode is spending money on an outlet that refuses medical content, or dropping a good one.
- Closed question: per remark (<= ~80 chars) one noul each for: refuses medical/drug content; invites contact details; edits without notice; promises indexing (vs disclaims); publishes on weekends; link lives ~30 days. Or one choice over a small set of exclusive reasons plus the independent flags.
- Volume: catalogue sync, thousands of outlets, judged once per distinct remark text (cache by hash of title+remarks, re-judge only on change). Tiny.
- Fallback: the existing regex verdict (union for the blacklist direction is safer: blacklist if either says refuses). Labels: stored catalogue rows hold regex flags; orders' later `problem` outcomes (domain_mismatch, text_changed, rejected) give some outcome labels.
- Caveat: a blacklist decision gates spending, not safety/authorization; keep code-side budget/reserve checks untouched. Jev only proposes flags.

### C3. stats-integrity "causal language over an association" check (POSSIBLE, advisory, run-side)
- File: runtime/skills/core/stats-integrity/stats_integrity_check.py:120-170 (`_CAUSAL`, `_STATS_SIGNAL`, `check_interpretation`).
- Today: an English-only open-vocabulary regex (cause, leads to, results in, due to, impact of, effect of, proves, "increase ... by <digit>") fires on any line of a report that also mentions regression/association/p-value. Output is a dismissible `warn` finding in the app's review contract; nothing blocks. Visible problems: "effect of" and "results in" fire on legitimate randomized-trial prose, and Chinese reports (the product default) get no check at all.
- Closed question: for each sentence of a report that contains a statistical result: noul "asserts a causal effect that the stated design does not support" (design string from the report/state), or choice {causal claim, associational, descriptive, hedged}.
- Volume: one report per run, sentences filtered by the signal regex (tens). Very cheap.
- Fallback: current regex (it is the script's only output today). Labels: none; the sentences it already flags are a ready negative/positive set.
- Blocker: the script runs in the runtime container, which holds no provider key; needs the control-plane judge route (a gateway call) or move the check into the `review` socket plugin / a notice. Advisory only, so a weak candidate on yield, but it is the clearest open-vocabulary prose regex left in the runtime skills (principle 5).

## Remaining yield

Honest assessment: this sweep is near the floor. Two real candidates (C1, C2), both GEO and both control-plane, both short Chinese closed classifications with an existing regex to fall back on and stored labels to measure agreement; they are worth doing together because they share one judge call shape and the same test set approach (regex verdict vs Jev verdict on stored rows, review the disagreements). Of the rest, C3 is the only clear open-vocabulary prose regex left in runtime skills but it is advisory, English-only and run-side. Everything else I read is identifier format, number handling, closed-vocabulary matching, structured-key dedupe or platform-owned templates, which should stay code under principles 1 and 5 (Jev is weak at numbers and counting, so frontierNumbers, numericTraceability and the metrics code are deliberately not proposed). I would expect a fourth sweep to find nothing above "possible-weak"; any further gain is more likely in extending already-covered sites (for example judging the answer-usable question in C1 with the same call that geoJudge already makes) than in new files.
