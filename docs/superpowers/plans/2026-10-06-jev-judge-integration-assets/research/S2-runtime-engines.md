## Part A — runtime sites

### A1. socket/plugins/screening.mjs (`evimed_screen_batch`)
- Today: ONE tool call; model supplies `criteria` (free text) + `records[]` (id/title/abstract/year/source). Code chunks records into batches of `batchSize` (default 50, `screening.mjs:40`), runs waves of `maxConcurrentChildren` (default 30) kernel SUBAGENTS via `startSubagent(ctx, {capability:'evimed-screening', tools:['read'], persona:'你是文献筛选员…', outputSchema: SCREEN_VERDICT_SCHEMA, maxDepth:1}, parent, signal)` (plugins/screening.mjs:119-129). Model = whatever the kernel runs (DeepSeek flash via the control-plane model gateway, the kernel's own provider; no separate model, no separate key). Batched: 50 records per child prompt, per-child structured output; written to `screening-ledger.csv` (CSV id,decision,criterion,reason), `ledgerPath` checked against `isProtectedWritePath`.
- Rule: `decision ∈ {include, exclude, unclear}` (`SCREEN_VERDICT_SCHEMA`, packages/socket/src/screening.mjs:8-28); prompt (src/screening.mjs:54-75) says `unclear` is first-class and "a wrongly guessed include is caught by later full-text check, a wrongly guessed exclude is not" (so the intended asymmetry is: uncertain -> unclear, never exclude). The tool returns counts `included` / `excluded = verdicts - included` (plugin:181-188) — NOTE `excluded` counts `unclear` as excluded (a latent counting wart, not a Jev matter).
- Closed vs mixed: decision is a closed 3-way choice per record; `reason` (one sentence) + `criterion` (which criterion violated) are generated text. Criteria are free-form prose from the model, so the "question" per record is open-vocabulary criteria text applied to a record: exactly Jev's `choice` over a text state, with criteria as the question text.
- Fallback: a batch whose child fails/does not complete is pushed to `failures[]` and reported (never dropped silently); no per-record retry; there is no non-model fallback. Cancel stops further waves. Config off switch `EVIMED_SCREENING_ENABLED=0` registers nothing.
- Tests: packages/socket/test/consistency.test.mjs:611-634 (tool registered), :2389-2435 (protected ledger path refused), :2644-2720 (children released, cancel starts no further wave); pluginSwitches.test.mjs:157 (switch). Domain: runPhases.test (`phaseOfToolCall`=screen), narration.mjs:191. NO test pins verdict quality / include-exclude-uncertain semantics (the schema is the only pin); and no eval. The tool is not named in any SKILL.md (only in the tool description) — only `scripts/dev/vendor-community-skills.mjs:40` lists it as a socket tool name, so how often runs actually call it is unmeasured here (check production ledgers).
- Verdict: **SPLIT OFF a sub-decision (strong candidate)**: replace only the per-record `decision` with a Jev `choice` (include/exclude/unclear) or `noul` per criterion; keep reason/criterion generation to a subagent only for records Jev returns low-confidence or `exclude` (or drop `reason` to a template "criterion k not met" when Jev answered per-criterion). Constraints: the call must be made server-side (runtime holds no key), so it can NOT be made inside this plugin directly — it would call a new gateway (Part B). Jev has ≤255 options per choice and 64k-token request cap with state+longest question ≤32k: a 50-record batch maps naturally to ONE request with state = criteria and 50 questions (one per record, state = record text) or state = record + 1 question per criterion; that is far cheaper than a child agent. The `unclear` option maps to either an explicit option or confidence below a threshold (Jev's `confidence` = (k·p_max − 1)/(k − 1)).

### A2. socket/plugins/compaction.mjs
- Today: provider swap only when `policy: 'structured'` (default `basic` => registers NOTHING but the request-size guard `guardRequestBytes` + the `evimed_compact_request` tool; plugins/compaction.mjs:105-110). Engine (`createEvimedCompactionEngine`, harness-port/src/compaction.mjs:600) wraps the kernel's `BasicCompactionEngine.summarize` hook: the summary is written by the KERNEL'S OWN model (DeepSeek via the model gateway) with a deterministic STATE HANDLES block prepended and a deterministic membership check (`missingHandles`, retry once naming what was lost, then fall back to the plain upstream summary + recorded degradation). So: one LLM free-text generation (not a closed decision); the only closed decision is "did the summary keep every handle" and that is already code (string membership).
- What compaction does with OLD TOOL OUTPUT: nothing itself. Old tool results are handled by the kernel package `@deepseek-ai/dsh-compaction-tool-result-pruner` (preset row `packages/socket/presets/evimed-universal.patch.yml:277-283` + `presets/evimed-universal/agent.cordis.yml:260`): model-free head/middle/tail pruning of any tool-result node over `thresholdChars: 8192` -> keeps `headChars: 4096` + marker + `tailChars: 1024` (the three numbers mirrored in `@evimed/domain` `TOOL_RESULT_PRUNER`, packages/domain/src/constants.mjs:198, held equal by socket.test.mjs:1144). Upstream description (read from the sibling checkout's v0.1.2-rc.1): "Replay-safe model-free head/middle/tail pruning for tool-result surface nodes". This is LOSSY (the middle is replaced by a marker), not exact-duplicate folding.
- Exact-duplicate folding of tool output today: NONE. grep for dedup/fold/collapse in packages/socket and packages/harness-port finds nothing for tool output (only STATE HANDLES de-duplication of handle ids, harness-port/src/compaction.mjs:271, and unrelated evidence-source dedup).
- Where deterministic duplicate-line folding fits (seams in packages/harness-port/seam-manifest.json `events`): 
  1. `tools/execute` (`events.toolWrap`; port wrapper `onToolWrap`, harness-port/index.mjs:542) — around-dispatch, the ONLY seam today that can change what the model sees; run-policy already uses it (plugins/run-policy.mjs:1064, the one-retry for recoverable MCP source failures). A fold = `const result = await proceed(); return foldDuplicateLines(result)`. Must be a NEW socket plugin row (or a function in an existing agent-scope plugin) so it is individually switchable (`EVIMED_<X>_ENABLED`) per Plugin-first rules.
  2. `tools/post-execute` (`events.toolPost`) exists in the manifest (seam-manifest.json:26) but has NO port export and no probe (grep: only the manifest row); using it would need the "new seam = manifest row + port export + probe" step.
  3. `tools/result` (`events.toolObserved`) is read-only by contract — unusable.
  4. Alternative with no kernel seam at all: fold inside the MCP server's result rendering (runtime/mcp/evimed-research/server.py) — covers only research tools, not `bash`/`read` outputs, which are where long repeated lines (logs, R/pip noise) come from.
  The folding is lossless only if it keeps a count marker ("<line> (×N)") and runs BEFORE the pruner's 8192 threshold is applied (the pruner sees the folded text) — ordering is a design point to verify live. No model, no Jev: this is principle 1 (deterministic -> code).
- Verdict (Jev): **NOT a fit** for the compaction summary (free-text generation; Jev generates no text). Jev could answer "is this region of the log worth keeping?" but that is a language-judgment on prose that principle 13/12 caution against and that the handle-membership design deliberately avoids. Duplicate folding is deterministic code, not Jev.
- Tests: packages/socket/test/socket.test.mjs:1144 (pruner constants), :1159 (exactly one engine), :1173 (request-size guard); packages/harness-port/test/compaction.test.mjs.

### A3. socket/plugins/run-policy.mjs (delegation / subagent messaging)
- There is NO inter-agent message routing. Three one-way channels exist and each is deterministic code: (1) parent -> child exactly once at spawn: `evimed_delegate` (plugins/run-policy.mjs:1463-1613) builds the child's whole prompt with `buildDelegation` (src/runPolicy.mjs:1000; skill bodies, task, `brief` excerpt the parent model supplied, memory block, tool filter) and calls `startSubagent(...)`; (2) child -> parent only as a settled outcome through `evimed_await` / `childReport` / `settleDelegation` (retry-once decision is code: `entry.redelegated`, runPolicy `settleDelegation`); (3) plugin -> agent via `injectContext` (rides the next request) / `steerContext` (wakes the agent) — fixed templates tagged `<evimed-run>`, `<evimed-budget>` (run-policy.mjs:957, 1264-1313, 1796). No mailbox, no agent-to-agent send tool, no peer messages, nothing to "gate".
- The decisions in that file are all engineering/closed: plan-item state machine (`canTransition`, `advancePlanItem`), concurrency/attempt limits (`delegation_concurrency_limit`, `submissionsSpent`), dependency order (`unmetDependencies`), tool restriction (`delegationToolFilter`), the tool-wrap one-retry for recoverable source failures (`onToolWrap`, run-policy.mjs:1064, `classifyEvidenceSourceError` closed vocabulary), the control-plane routing line parse (`routedCapabilityOf`, runPolicy.mjs:937 — a closed-id lookup, not language), `namedCapabilityIds` (closed catalogue ids, :953). The one language-ish check is `contentTriggerIssues` -> `matchedClinicalTriggers` (medicine-name scan; see Part D).
- Verdict: **NOT a fit.** The only free-text hand-off is the parent's `brief` excerpt to the child — a faithfulness question ("is this a fair excerpt of the question?") that is open-ended and, by principle 2/13, must not become a gate. Jev could answer `noul` "does this brief drop a constraint the question states?" but that is an input-side check on model behaviour (principle 2: contracts bind outputs, not inputs) — do not build.
- Tests: consistency.test.mjs (delegation, await, settle, concurrency; ~2380-2720 area), combinedPlan.test.mjs, pluginSwitches.test.mjs.

## Part B — how a runtime-side or engine-side caller reaches a judge without a key

### B1. The rule and what actually holds today
- Rule: provider keys live in the control plane's gateways, never in the runtime container (CLAUDE.md "Safety defaults"; layer 3 table: "one path constant + one handler + one allowlist; never routed around"). Jev's key is a HOST FILE read only by the control plane (`OPEN_SCIENCE_TYPESAFE_API_KEY_HOST_FILE`, `config.typesafeApiKey` -> `callJev`, apps/server/src/jevModel.mjs:163-168); the pinned model is `config.reviewJevModel`, base `config.reviewJevApiBase` (deps-version.json `typesafe.review.model`).
- Engines do NOT call api.deepseek.com with a real key in the hosted deployment: `OPEN_SCIENCE_ENGINE_MODEL_GATEWAY_ENABLED` defaults true (apps/server/src/config.mjs:1835-1836; deploy/web/docker-compose.yml:1154,1405,1574,1638,1692,1751 `:-true`; deploy/web/.env.example:405), and `scripts/ops/host-release-switch.sh:227-229` appends `docker-compose.engine-keyless.yml` whenever the lever is on, which bind-mounts `/dev/null` over `/run/secrets/deepseek-api-key` in all six engine containers. The base compose still mounts the key (`LLM_API_KEY_FILE: /run/secrets/deepseek-api-key`, docker-compose.yml:1156,1398,1571,1635,1689,1748) and the adapter's DIRECT path survives when the lever is off: `service.py:_child_environment` falls back to `_read_secret(LLM_API_KEY_FILE)` and `LLM_BASE_URL` default `https://api.deepseek.com` (deploy/specialist-adapter/evimed_specialist_adapter/service.py:1262-1268; `_model_ready` at :646-654). Engine code run as a bare CLI/`start.py` (laptop, not hosted) still talks to api.deepseek.com with its own `.env` key — that is outside the SaaS.
- So the two caller populations and their credentials:
  1. Runtime-side (socket JS, MCP Python, the in-container MetaAgent subprocess): the runtime's own short-lived tokens. Two flavours: the MODEL-GATEWAY token (file `EVIMED_MODEL_GATEWAY_TOKEN_FILE`; verified by `runtimeManager.assertActiveModelGatewayToken`, runtimeManager.mjs:3545; used by frontier/kb/geo/vcr/semantics/sources/search/results gateways) and the WORKLOAD token (file `EVIMED_WORKLOAD_TOKEN_FILE`, rotated every 150 s; `assertActiveEviMedWorkloadToken`, runtimeManager.mjs:3576; used by revision/review/capsule/extensions/tooluniverse/engine-token-mint). Socket plugins get `tokenFile` + a gateway URL via preset `!!js process.env.*` (packages/socket/presets/evimed-universal.patch.yml:120-121,147,172-173,319-320).
  2. Specialist engines (separate containers): a per-JOB credential minted at admission (B3).

### B3. Engine-side: HMAC short-lived per-job credentials
- `apps/server/src/modelGatewayEngineTokens.mjs`: path `ENGINE_MODEL_TOKEN_PATH = /internal/engines/v1/model-token` (:37); `createEngineModelTokenHandler` (:187-263). Two proofs: (a) Bearer = the runtime's own workload token (`assertActiveEviMedWorkloadToken`; names account+project, proves a live runtime), (b) `x-evimed-engine-signature: v1=<hex>` = HMAC-SHA256 of the body under a key derived from the WORKLOAD signing secret (`engineModelRequestSignature`, :51-54, key domain `evimed/engine-model-token/key/v1`) — a secret specialist services hold and a runtime never does (so a runtime that prints its token cannot mint itself credentials). Body `{v:1, kind, jobId, executionContext?}` (<=4 KiB). Answer `{token, baseUrl, model, modelPolicy, expiresAt, runId}`.
- The credential (`issueEngineModelToken`, :75-108): HS256 JWT signed with `config.modelGatewaySigningSecret`, claims `v, aud:"evimed-engine-model", userId, projectId, kind (one of ENGINE_KINDS), jobId, runId?, sessionId?, reasoningEffort?, dailyLimit/weeklyLimit/runLimit?, iat, exp, jti`; TTL `engineModelTokenTtlSeconds` bounded 300 s..24 h; STATELESS on purpose (a job runs tens of minutes to hours and must survive a control-plane restart); every unknown claim rejected by `verifyEngineModelToken` (:118-161).
- Adapter side: deploy/specialist-adapter/evimed_specialist_adapter/engine_model.py (`signature`, `request_credential` — one 5 s attempt, any failure refuses the job rather than falling back to a provider key; `child_environment` hands the engine `DEEPSEEK_API_KEY`/`LLM_API_KEY` = the job token and `*_BASE_URL` = gateway, plus `LLM_ENABLE_THINKING` / `LLM_REASONING_EFFORT`); wired in service.py:859-870 (admission), :1248-1268 (`_child_environment`). Pinned HMAC vector test in both suites (`test_engine_model.py`).
- How the gateway uses it: `modelGateway.mjs:991-995` tries the runtime-token check first, then `engineCaller` (:203-212) which ONLY accepts an engine credential when `config.engineModelGatewayEnabled === true` AND `route.protocol === "chat"` — i.e. engines can reach `/internal/model/v1/chat/completions` and nothing else; purpose is stamped from the token (`caller.engine ? ... "engine"`, :1047), never from the request body. Engines speak the OpenAI-compatible chat protocol and append `/chat/completions` to whichever base URL they read (engine_model.py `child_environment` docstring).
- The in-container MetaAgent path (MCP `meta_agent.py:_model_environment`) is the runtime's own gateway token as `LLM_API_KEY` (no engine credential).
- Therefore, for a Jev "judge" an engine would call, the existing engine credential is NOT enough as is: it is accepted only on the chat route. A judge route needs its own caller check mirroring `engineCaller`/`createEngineModelTokenHandler`: accept `verifyEngineModelToken(token, {secret: config.modelGatewaySigningSecret})` (+ `config.engineModelGatewayEnabled`) in addition to the runtime-token check, and take userId/projectId/runId/limits from the credential claims (never the body), `purpose` from the claims/`engine` — exactly what `modelGateway.mjs:1031-1060` does for chat.
