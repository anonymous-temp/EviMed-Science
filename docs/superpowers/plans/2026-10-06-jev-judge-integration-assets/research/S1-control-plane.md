# Notes on the existing client that any new site would meet

- `callJev` takes `purpose` (default `review`) but no `limits`; `reserveModel` is called with `dailyLimit = config.userDailySpendLimit`, `weeklyLimit = config.userWeeklySpendLimit`, `runLimit: 0` (jevModel.mjs:214-216). The module-budgeted callers (frontier, geo, evolution) pass `limits:{daily:0,weekly:0}` to their own gateway call and are governed by their module budget read from the ledger by purpose (e.g. frontierPipeline.mjs:610, geoJudge.mjs:440). A Jev call for those modules would book `purpose: "frontier"|"geo"|"evolution"` (valid, in the closed vocabulary, and in `UNCAPPED_USAGE_PURPOSES`, usageLedger.mjs:31) so its cost would automatically count toward the module budget, but the per-call `limits` pass-through does not exist yet. With production spend limits at zero (memory: spend-limits-are-zero-in-production) this has no effect today.
- `callJev` has no `thinking`/`temperature` to set and generates no text, so every output must be a typed answer. Confidence is per question; the only calibrated gate in the repo is `typesafe.review.supportConfidence = 0.8` for the SUPPORTS choice of the reply check (deps-version.json:102). Each new site needs its own threshold measured on its own corpus (jevModel.mjs header: "confidence thresholds are calibrated per version").
- Limits: 64k tokens per request, 32k state + longest question (jevModel.mjs:96-99); a request over either is refused before it is sent (`jev_request_too_large`). Batches of many items in one state worked for the reply check (about fifty sentences per request) but "accuracy falls as the state fills with material a question does not need" (replyCheckJev.mjs:40-43).
- Documented weak spots (replyCheckJev.mjs:33-36, deps-version.json notes): counting, numeric closeness, dates, a state full of unneeded material, a state that addresses the checker. Sites whose state is adversarial (capsule scan) or numeric (VCR criteria, GEO number checks) are the wrong place.
- Data egress: Jev is a third-party endpoint (api.typesafe.ai) and a NEW recipient. What it receives today is the assistant's cited reply sentences plus public source abstracts (replyCheckJev.mjs:83-109). Sites whose state is public literature (frontier screening, same-event, evidence-zone target) or platform metadata (method names/descriptions, capability catalogue, tool names) raise no confidentiality question. Sites whose state is a researcher's own words (routing and Feishu intent: the raw question or chat message; memory: conversation text; source text) would send content that DeepSeek already receives to a second third party, which the existing reply-check use does not set a precedent for (that sends model output, not the researcher's question). Patient-level clinical text (VCR) must not go there without an owner ruling.
- Failure model already in place and reusable: `JevError` codes, one retry for 429/5xx, `jev_model_mismatch` discard, ledger reserve/settle/release. Every candidate site below already has a fail-safe that is model-agnostic (rotation, shortlist unchanged, stay-in-project, treat-as-not-same, no route -> net -> answer line), so a Jev failure can fall back to the existing path or to the incumbent Flash call.

## Ranking by fit x value (my reading of the above, factual basis cited in each section)

1. Frontier screening (1): closed, high volume (every ingested entry), already a dedicated budget; weak calibration set but it can be built cheaply from entries + operator review.
