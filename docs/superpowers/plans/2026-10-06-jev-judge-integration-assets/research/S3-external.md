### 1.4 Request limits
- Context: "64k tokens per request; 32k tokens for `state` plus the longest question". The 64k budget covers the state plus all questions combined. https://docs.typesafe.ai/models.md (read 2026-10-06). (InfoQ and Wikipedia repeat these numbers, one of them as "32,000 tokens" only.)
- Choice: max 255 options. Score: at least 2 levels, "the API accepts up to 10". Noul: yes/no probability. https://docs.typesafe.ai/api.md (read 2026-10-06). The blog adds that for high-cardinality choices TypeSafe itself "do[es] a 2 stage-system of scoring independently then making an explicit choice".
- Input is text only: string, JSON object, or array of text values. https://docs.typesafe.ai/models.md.
- Response: Choice and Score answers carry `probabilities` and `confidence` (0 to 1); Noul carries only the 0-1 value and no `confidence`. https://docs.typesafe.ai/api.md and https://docs.typesafe.ai/confidence.md (read 2026-10-06).
- Errors: 401, 422, 429 (rate limit), 529 (overloaded); use exponential backoff. https://docs.typesafe.ai/api.md.

### 1.5 Rate limits
- Stated: "100K tokens per second / 80 requests per second" for `jev-1.13.0`, with the warning "Rate limits are adjusting dynamically ... the limits above can change without notice" as GPU capacity lands; higher limits on custom/enterprise plans. https://docs.typesafe.ai/models.md (read 2026-10-06). The limits are per-account tokens/s and requests/s; the docs do not say whether they are per key, per organisation or global.

### 1.6 Batching many questions in one request
- Yes, and it is the core design: `questions` is a map; Jev "ingests the `state` once and evaluates every question against it in parallel". https://docs.typesafe.ai/models.md; pattern page https://docs.typesafe.ai/patterns/fan-out.md ("Speculative fan-out", read 2026-10-06).
- Limits: 64k tokens total (state + all questions), 32k for state + longest single question. The API reference lists no explicit maximum count of questions per request. https://docs.typesafe.ai/api.md.
- Cookbook claim: batching 13 questions over a ~54,000-character article was "12.2x cheaper and 10.0x faster with no change in answers", with five runs averaged. The "10.0x faster" number sums 13 single-call latencies as if sequential (0.27 s batched vs 2.71 s); the cookbook itself says "Fire them concurrently and the gap shrinks, but the 13x token cost stays." https://docs.typesafe.ai/cookbooks/parallel_questions.md (read 2026-10-06). The cost part is the robust claim.

## 2. Jev weaknesses, confidence definition, language, prompt-injection posture (read 2026-10-06)

### 2.1 Documented weaknesses ("jaggedness") of jev-1.13
Source: https://docs.typesafe.ai/model-jaggedness/jev-1.13.md ("Applies to `jev-1.13`. Last reviewed 2026-10-02."). There is no jaggedness page for any other version (the llms.txt index lists only this one). The page is a table of nine failure modes plus a closing reminder:
1. Literal reading: answers the question as written, reads scoping words and negations at face value; fix is to write exact conditions and boundary cases.
2. Math and numbers: cannot count reliably (characters, term occurrences, list items; "the error grows with the size of the thing being counted"); worse on numeric representations than semantic ones (hex vs colour names; assembly vs high-level code); Score outputs must not be interpolated to recover an exact magnitude ("score levels are weak in numerical calibration"), only thresholded.
3. Date and time comparison: reads dates as text; ordering, gaps and window membership are unreliable, worse with mixed formats, relative references, quarters, settlement or accrual periods. Fix: extract date parts with a Choice, compare in code.
4. Indirection: double negatives or multi-hop questions cost accuracy.
5. Large state full of irrelevant detail: "Accuracy falls as the state grows with content unrelated to the decision"; the closing box says "Jev suffers from context rot". Fix: filter in code first.
6. Adversarial content: "State is data, and `jev-1.13` does not treat it as hostile by default. Content written to adversarially steer the model, whether that is an injected instruction, a deliberately misleading framing, or text that argues for its own classification, can move the answer. We expect to improve on this in the future." Fix offered: "be explicit in the criteria. Test your integration thoroughly before deploying it to many users." No mitigation is offered beyond that.
7. Contradictory instructions and criteria (for example a Noul where `true` maps to no).
8. Choice option order: "leans toward the option that comes first" in some cases; fix is to reorder options and check consistency.
9. Generation: not trained to generate text.
Closing "avoid" list: asking what code can compute exactly; hiding several judgments in one question; System Two tasks with more layers of indirection; more context in `state` than the question needs.

### 2.2 How `confidence` is defined
Source: https://docs.typesafe.ai/confidence.md (read 2026-10-06).
- It is NOT a measured accuracy. It is "a statistic computed from the probability distribution the answer already gives you"; "TypeSafe's `confidence` is one reasonable way to summarize a distribution, not the only one".
- Choice, n options, top probability p_max: confidence = (p_max - 1/n) / (1 - 1/n). 1.0 when all mass is on one option, 0 when uniform. Only p_max counts: (0.6, 0.3, 0.1) and (0.6, 0.2, 0.2) both give 0.4. The page suggests also trying top probability and the top-to-second ratio.
- Score, n ordered levels, m the most likely level: confidence = max(0, 1 - sum_i p_i |i - m| / MAD_unif), MAD_unif = (1/n) sum_i |i - (n-1)/2|. Probability on a neighbouring level lowers confidence less than probability on a distant level.
- Noul: no `confidence` field is returned; the page says to use the distance from 0.5, |2p - 1|, if a confidence-style number is wanted. The answer is a single P(true).
- The guidance pattern is three bands (high: act; medium: confirm or review; low: route to a human) with thresholds scaled to risk; the example uses 0.5 as a floor and 0.9 for a high-stakes action, and says "The correct threshold values depend on your domain ... Start with conservative thresholds, test with your own data".
- Calibration claim: the AI primer says RLCD is trained so that outcomes given probability 0.8 occur about 80% of the time, "These rates describe groups of predictions, not a guarantee about any single answer." https://docs.typesafe.ai/introduction/machine-learning-primer.md (read 2026-10-06). No calibration curve, ECE or per-domain calibration data is published in the docs I read; the vendor says it deliberately does not publish public-benchmark numbers ("Put no weight on public benchmarks", launch blog FAQ, https://typesafe.ai/blog/introducing-system-one-models-and-jev, read 2026-10-06).
- Only vendor-side evidence of confidence gating I found: a cookbook on 60 SEC 10-K filings, 75-way Choice: "a confidence cutoff of 0.9 splits them in half. The confident half is right 90% of the time; the other half, 40%" (27/30 vs 12/30; n = 60, English, self-reported labels). https://docs.typesafe.ai/cookbooks/classification_using_confidence.md (read 2026-10-06). It is a demonstration, not a validation; and 90% accuracy in the confident half still means 1 in 10 confident answers is wrong.
- Another vendor cookbook (insurance claim rubric, 14 Noul questions, 15 repeats per condition) tests answer stability across repeats against other LLMs; I did not extract its numbers. https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook.md.

### 2.3 Language support
- "English is the primary training language and where accuracy is currently best. Other languages, including CJK scripts, are handled but not equally well; test on your own content before relying on Jev for a non-English workload, and pay close attention to Confidence when routing." https://docs.typesafe.ai/models.md (read 2026-10-06).
- No Chinese-specific accuracy figure is published anywhere I found. So Chinese medical text is explicitly "handled but not equally well".

### 2.4 Prompt-injection posture
- Declared weak: see 2.1 item 6. The judged text ("state") is not treated as hostile; an instruction inside it, a misleading frame, or text arguing for its own label can move the answer. Also the choice-order bias (item 8) and the literal-reading trait (item 1) are exploitable levers.
- Vendor usage as a defence: the guardrails cookbook (Noul per hazard: jailbreak, harm, "a diagnosis or a dosage?", self-harm) scores public in-the-wild jailbreak prompts; a "jailbreak dressed as a medical accommodation" scored 0.74 (borderline), the DAN prompt 0.98. https://docs.typesafe.ai/cookbooks/llm_guardrails.md (read 2026-10-06). The RAG-passage cookbook uses a `contains_prompt_injection` Noul with a 0.70 cut on a single hand-written forum post (score 0.99). https://docs.typesafe.ai/cookbooks/classifying_rag_passages.md (read 2026-10-06). These are single-case demonstrations, not an adversarial evaluation (no adaptive attacker, no attack that targets the judge itself).
- Pattern worth noting for evidence work: the citation-check cookbook first does an exact string match for the quote and only then asks a Choice whether the surrounding context supports the claim; eight citations, four planted failures all caught. https://docs.typesafe.ai/cookbooks/citation_check.md (read 2026-10-06). That is the same "code decides what code can decide" split as our domain gate.
- Independent commentary quoted by InfoQ (2026-10-01): "it cannot emit an invalid type but can still emit a completely wrong valid value" (Hacker News commenter), and a tool-vendor CTO saying the design "delegates the hallucination problem a little bit to the user", who must decide whether 50% is worth acting on. https://www.infoq.com/news/2026/10/typesafe-ai-jev-released/ (read 2026-10-06). The vendor's "0% hallucination" claim is about schema validity only; the blog states "Our number is not empirical. Schema matching is guaranteed".
- Ecosystem: per InfoQ, LangChain shipped a `TypeSafeClassifier` integration with an AutoMode middleware that screens tool calls before they run, and Vercel put Jev on its AI Gateway on day two. Both would be places to look for a worked example of a judge on tool calls. https://www.infoq.com/news/2026/10/typesafe-ai-jev-released/.

### 3.2 The decision points: 35 became 38 on 2026-10-05
- The "35 decision points" wording is the README of 2026-09-23 (commit d52927ae0, "the README as a technical document: the turn, all 35 decision points ..."). HelloGitHub and awesome-list submissions of 2026-10-05 also say 38.
- The 35 of 2026-09-23 by the README's own grouping (I counted the table rows in `git show d52927ae0:README.md`):
  - Input (3): `input.preflight` (message kind, thinking level), `task.frame` (new task / hard constraint / correction / subgoal / no change), `input.interjection` (interrupt now or after this step).
  - Context (13): `skills.disclosure`, `capability.disclosure`, `tool.admission` (per chunk of long tool output), `tool.admission.test-log`, `context.forget` (stale tool results become tombstones), `context.compact` (keep/prune a passage, no summary), `memory.recall`, `memory.capture`, `memory.outcome`, `memory.worth`, `memory.merge`, `memory.applied`, `cache.warming`.
  - Tools and safety (7 then, 9 now): `tool.risk`, `tool.approval`, `tool.constraint`, `files.locate`, `browser.step`, `review.triage`, `diagnostics.delivery`; added later: `tool.injection`, `judge.items`.
  - Turn (7 then, 8 now): `turn.drift`, `turn.rewind`, `turn.completion`, `output.drift`, `goal.met`, `board.read`, `notify.routing`; added later: `turn.continue`.
  - Teamwork (5): `swarm.routing`, `swarm.patch`, `hive.publish`, `hive.deliver`, `hive.relate`.
  Mapping to the task's five categories: user input = Input group; tool calls = Tools and safety (plus `tool.admission` in Context); context management = Context; completion check = `turn.completion`, `turn.continue`, `goal.met`; multi-agent communication = Teamwork. Sources: README at the pinned commit and https://github.com/qybaihe/mu/blob/47c51b0c68f622e9953b7f501d165fe474eec588/docs/reference/decision-points.md.
- Several of the 38 are not judge-first: `tool.risk` ("rules flag dangerous-looking commands; the judge only vouches that you asked for it. Unsure means asking you"), `turn.completion` (code counts edited files and whether a command ran after the last edit; the judge only reads the closing message; fail-open to "done", `packages/kyrn-judge/src/decisions/turn-completion.ts`), `hive.deliver` (a "decision" note is delivered to everyone by rule, no judge). That split matches "code decides what code can decide".

### 3.3 Shadow mode and the default flip
- Each point is `active`, `shadow` (asked and logged, changes nothing) or `off`, and can name its own judge or a cascade such as `laya,jev`. README at the pinned commit; `docs/judges.md`.
- The default WAS shadow until 2026-10-06 07:21 +08: commit ff7ac2816 "decision points are active by default" says "A fresh install recorded every verdict in shadow and acted on none ... modes.default is now 'active'". So everything written about mu's behaviour before that date (including the "35 points") describes a harness that mostly only logged. Today every point acts out of the box, including `tool.admission` (dropping tool output) and `tool.injection` (withholding passages). `packages/kyrn-judge/src/config.ts` line ~112; CHANGELOG [Unreleased] "Decisions act by default".
- Verdict ledger: every verdict is logged locally (`mu ledger`); `recordState: true` also keeps the judged state, off by default "because the states hold your content". `docs/judges.md`.

### 3.4 Judges
- Jev (hosted): reached via TypeSafe, OpenRouter, Vercel AI Gateway, OpenCode Zen, or Cloudflare Workers AI, by first key found. With NO key set, mu silently uses "Jev 1.13 on OpenCode Zen, free for a limited time: what it judges goes to OpenCode, which does not train on it; mu says so once a day". So the default configuration sends tool output, user messages and web content to a third-party relay. `docs/judges.md`, README "Privacy" (read 2026-10-06).
- Laya (local): a 322M-parameter judge, not made by TypeSafe: Convai Innovations' open-weights model (mmBERT-base multilingual, Core ML port, 1,024-token window shared by question, options and state, batch 1, max 32 options, state silently truncated at the end). `kyrn/docs/03-local-judge.md` (2026-09-20). The authors' own check on 37 hand-labelled scenarios (half Chinese, half English): "Reliable on simple predicates, weaker on meta-judgments"; the prompt wording moved one yes/no accuracy from 42% to 74%; some fields "unusable" (needsClarification 2 right / 4 wrong; complexity scores AUC 0.46-0.77); on 25 chat/not-chat yes/no questions it got 11-19 right "with many high-confidence wrong answers". The doc says "this is a wiring and wording check, not a serious evaluation".
- Plain LLM: `llm:<provider>/<model>`, "prompted to answer as JSON"; its probabilities are verbalised, not read from logits (comment in `packages/kyrn-judge/src/providers/llm.ts`). Also `classifier:<provider>/<model>` (Cloudflare Clef, System One models on OpenRouter/Vercel), `clm` (CLM-8B, "not measured on mu's questions yet"), and custom HTTP judges.
- Cascades: "Each later judge only sees the questions the earlier ones left uncertain" (`tiers: ["laya","jev"]`), per-point routes. `docs/judges.md`.
- Planned but not built: a distillation route (Jev as teacher, ledger as training set, fine-tune a local Laya), described in `kyrn/docs/03-local-judge.md` section 4.3. This would collide with TypeSafe's MCA clause 2.3(b) (no using Output to train a model to imitate the Services) for anyone on a TypeSafe contract; see section 1.9.

### 3.5 The `kyrn` judge package

### 3.6 The 51% claim (deterministic exact-duplicate folding)
- Confirmed: no model call. README: "No model is called. The markers expand to the original byte for byte, and the full log stays on disk, behind a pointer at the end of the output." The 8 short logs are not processed. The README's own caveats: "Other runners are not measured"; "There is no end-to-end comparison with pi, Claude Code or Codex on the same tasks yet"; it measures what reaches the model, "not whether the model then finishes the task". Pinned README, "Measured" section; `kyrn/docs/09-test-log-admission.md` section 4 and 6.

The doc notes Jev is not bit-deterministic (27 of 72 probabilities differed by 0.01-0.04 between two identical runs) and "unclear was never chosen". ### 3.7 Latency claims (0.3 s, 0.44 s)
- 0.3 s: one WARM question over HTTP/2 (measured 2026-09-23 by the authors from their own network to api.typesafe.ai: HTTP/1.1 0.52 s, HTTP/2 0.31 s). 0.44 s: 16 chunks of tool output in ONE request (63 chunks / 72 KB of npm output; 16 requests of one chunk took 1.43 s and 11.6k input tokens, one request 0.44 s and 7.6k tokens, verdicts identical). Source: `kyrn/docs/04-injection-points.md` section 10.7 and the comment in `packages/kyrn-judge/src/extension/judge-fetch.ts`.
- What the README leaves out, from the same documents: cold connection with five concurrent questions took 3.9 s on HTTP/1.1 and 1.7 s on HTTP/2; curl's TLS handshake alone took 1.4 s from the author's network; the server drops an idle connection after about 90 s (alive at 90 s, dead at 150 s), so mu sends a throw-away question every 50 s to keep it warm (281 input tokens each); across 39 real sessions the per-decision-point latency (p50 / p90 / max) was preflight 1.2 / 5.0 / 9.1 s with 4 timeouts, skill disclosure 1.2 / 7.7 / 9.5 s, tool admission 1.7 / 20 / 30 s (before batching), Jev approval 1.2 / 3.8 / 8.9 s, completion check 3.5 / 5.2 s. So a usable design needs warm connections, timeouts and a fail-open default.
- These are the authors' sessions on their own network; the repository does not claim a China-to-US number separately, but its measured cold handshake of 1.4 s (TLS) suggests a long route.

### 3.8 The hive (multi-agent delivery gate)
- README "The hive": two to six "bees" with their own focus (they read, run commands and browse, never edit); "Each time a bee finishes saying something, `hive.publish` asks once: is there a finding, a dead end, a decision or a blocker here worth sharing?"; what passes goes on a shared append-only board; for each new note `hive.deliver` asks once per OTHER bee whether it touches that bee's focus, and delivers it marked "a finding, not an instruction"; `hive.relate` reads the relation of a new note to earlier ones (supersedes / contradicts / supports / none); a superseded note becomes a correction delivered to the bees that hold the old one; contradicting notes both stay, marked as a dispute, and "if nobody settles it within a minute, a verifying bee is sent". Specs in `packages/kyrn-judge/src/decisions/hive.ts`.
- Rules around the judge: publish needs `share_worthy` three-zone "yes" (P at least 0.8) AND a non-"other" kind; a "decision" note is delivered to everyone without asking; and the cross-bee "supersedes" call needs P at least 0.9. That last bar exists because the authors calibrated on 153 hand-labelled note pairs from 11 real hives (2026-09-24): "across investigators no 'supersedes' reading was right (0 of 6 at the 0.6 bar, the highest at 0.87 ...)", and a bee revising its own note was right 5 of 12 times. This is direct evidence that a judge's relation call between two findings is unreliable. Comment in `hive.ts`.
- The authors' own retrospective (`kyrn/docs/08-jev-retrospective.md`, 2026-09-21, 6 real hives): publish passed 89 of 662 candidates (13.4%); deliver passed 64 of 140 pairs (16 of them by the forced "decision" rule); 89 board notes, 40 reached at least one bee; board-to-pickup delay median 27.2 s, p95 76.2 s; "no strong evidence that any delivery immediately changed an investigation or solved the task". README's "A real run: three bees, nine minutes, 117 candidates judged, 27 on the board, 16 delivered" is a throughput number, not a quality number.

### 3.9 Work vs report split (the board)
- README "The plain-language board": "mu does not ask the working model to narrate itself." With `/board` on, each step the agent takes becomes one plain line on a board as soon as it ends (code, not model: a file changed, a check passed or failed, a command run); when the agent says something, `board.read` asks the judge (multiple choice: phase, which acceptance item, whether it waits for you, news vs routine); only news makes a separate "plain-speaking" writer model retell it for a person and keep the state current ("what is happening now, how many items of the checklist are done, what waits on you"); a finished run gets a closing summary with the account kept. The board is "For you only, never in the model's context", and "The working model keeps its own language for the work". Off by default (`defaultOn: false`: "each update of the board costs a model call"). `docs/reference/features.md` section "board".
- Relevance: it is a channel-separation design (work artefacts vs a reader-facing report written by a different model), the same as our principle 10(a); but it is a progress display, not a deliverable-quality gate.

### 3.11 Tool-output admission policy: what is unsafe for medical or scientific data
Read at the pinned commit: `packages/kyrn-judge/src/decisions/tool-admission.ts` and `extension/features/admission.ts`.
- General path (not the test-log path), active by default since 2026-10-06: tool output of at least 6,000 characters, cut into 1,200-character chunks (3 to 48 chunks); each middle chunk is classified by a Choice question into `error`, `result` ("Search results, file contents or data"), `progress`, `warning` ("Repeated warnings or deprecation notices"), `passing` ("Tests or checks that passed") or `other`. Any chunk whose top class is `progress`, `warning` or `passing` is DROPPED and replaced by a line like `[mu: N lines (M chars) of warning/progress output omitted; full output: /tmp/.../x.txt]`. The threshold is only `pickChoice`'s default 0.6 top probability (the file comment says "only a confident noise class drops a chunk", but 0.6 is the floor; the stricter 0.9 bar is the test-log path only), and `pickChoice` ignores the threshold entirely when the provider returns no probability distribution. First and last chunks always stay; `isError` results, `read`/`edit`/`write`/`delegate`/`hive` tools and non-text content are never judged; a verdict later than 4 s is ignored (output goes in whole). The dropped text is archived under the OS temp dir (volatile) and the model must choose to open it.
- Unsafe for scientific/medical data, in my reading:
  1. "Repeated warnings" are classed as noise. In statistical or data-pipeline output a repeated warning is often the finding (non-convergence, singular matrix, NAs introduced, imputed values, dropped rows, unit or encoding fallbacks). A chunk saying that 40 patients were excluded for missing data is a "warning" to the classifier.
  2. "Passing" checks are classed as noise. Validation output (QC checks, schema checks, assertions that a cohort count equals the expected count) is audit evidence of what was verified, not clutter.
  3. A table chunk the classifier calls `progress` (row-by-row log, per-sample status) would be dropped even if it holds the one anomalous row.
  4. Classes are decided on a 1,200-character window with no knowledge of the user's goal (unlike the test-log path, which takes the goal and protects lines that mention identifiers from it); the 0.6 floor with a Choice whose first-listed option bias is documented by TypeSafe (choice-order bias, section 2.1 item 8) can flip close calls.
  5. In the test-log fold, exact repeats of a 6-line, 200-character block are folded after the first copy. That is lossless for test failures, but a fold is wrong for data whose repetition is the signal (duplicate patient rows, repeated measurements, an identical record emitted twice); the fold only applies to output recognised as a test runner's, so it would not touch a data dump, but the pattern must not be copied to data output.
  6. The authors' own retrospective measured the general path on 194 batches / 2,412 chunks: zero chunks dropped, 54% of all Jev input tokens spent, and states (my translation from Chinese): "a filter rate is not a filter accuracy; the information that was blocked may contain key evidence". So the benefit was never shown, only the risk surface. `kyrn/docs/08-jev-retrospective.md` (2026-09-21).
- Other points relevant to a medical use: `tool.injection` withholds passages of web pages, search results and MCP output that Jev scores above 0.5 as instructions aimed at an AI; a passage in a clinical document that reads like an instruction (a dosing instruction in imperative form, a protocol step "do not discontinue") is exactly what a "contains instructions" detector may flag, and a withheld passage is replaced by a one-line note. The question text itself was tuned on prompt-injection examples, not on clinical text.

### 4.1 arXiv 2609.37647 "Evaluating and Benchmarking the System One Model Jev"
- URL: https://arxiv.org/abs/2609.37647 (v1 only, submitted 2026-09-29, cs.CL and cs.AI; read 2026-10-06). Organisations (from the PDF title block; the arXiv metadata carries no affiliation field): University of Bonn; Lamarr Institute for Machine Learning and Artificial Intelligence (Bonn); Fraunhofer IAIS (Sankt Augustin). - What it claims: zero-shot evaluation of `jev-1.13.0` on 37 public datasets, 346,009 requests, US$9.40 in total, one frozen prompt template per dataset (tested on 20 training/validation examples, never tuned on evaluation data), compared with two open-weight LLMs scored on identical requests through exact option probabilities (Qwen3.8-27B and Gemma-4-E4B). The authors state "All three models degrade on low-resource languages, fine-grained or noisy labels, and rubric-based quality judgments."

So the default 0.5 cut misses half of the injections on that set while the ranking is excellent; threshold tuning matters more than the model.

Mean client-side latency 0.36 s per request at 32 concurrent requests (client location not stated, includes network); throughput was limited by the rate limit; US$9.15 for 217.9 M input tokens (630 tokens per request on average).

### 4.2 arXiv 2609.26550 "JEV-as-a-Judge: Accept When Confident, Escalate When Unsure"
- URL: https://arxiv.org/abs/2609.26550 (v1 2026-09-22, v2 2026-09-27, v3 2026-09-29; I read v3, the latest; read 2026-10-06; cs.AI). Organisation: Carnegie Mellon University (four authors); acknowledgements name a US federal measurement-science award (NIST) and an AI measurement centre at the university, and OpenAI's researcher-access credits. Independent of TypeSafe. Preprint, not peer reviewed. The arXiv comment says v3 "Expanded the dataset, updated the results and figures, and added new analyses. The previous result reporting 99% of GPT performance at 57% of the cost is retained in the appendix", so any earlier quote of "99% at 57%" is the v1 result, superseded.
- What it claims (v3 abstract and body): against sixteen generative and reward-model judges, with blinded human adjudication of disputed items, Jev is within three points of GPT-6 "wherever a verdict can be read off the text" at 0.36% of its fee ($0.044 vs $12.182 per 1,000 judgments, 277 times cheaper) and 0.15 s median latency (p95 0.24 s, against 1.89 s median and 3.86 s p95 for GPT-6); it ranks eighth of fifteen LLM judges on 4,850 pooled public judgments (1.7 points behind GPT-6); it trails by 7 to 28 points on expert knowledge, code, math and logic, and by 13.5 on style-adversarial RM-Bench pairs (a wrong answer written more elaborately). A cascade with a threshold frozen in advance (average both presentation orders, accept if confidence q >= tau, else escalate to the stronger judge, which judges independently) escalates 31% of 1,610 held-out pairs and is 0.9 points more accurate than GPT-6 alone at 41% of its fee; in a pre-specified live test on two new workloads where Jev alone trails GPT-6 by about 14 points (PPE correctness pairs and a second set of JudgeBench pairs; 570 held-out pairs in total) the cascade matches GPT-6's accuracy exactly, with a smaller saving; a separate live replication of the frozen policy on 510 of the 1,610 held-out pairs answered in 0.27 s median against 2.10 s for GPT-6 alone. Verified against the PDF text: the numbers in the arXiv abstract match.
- Details that change how the "cheap judge first" pattern should be built: (1) the paper's confidence q is the largest label probability, not TypeSafe's `confidence` formula; (2) averaging both presentation orders is part of the recipe because reversing a pair changes Jev's verdict on 3.7% of RewardBench pairs and 11.1% of JudgeBench pairs (GPT-6: 1.5% and 0.9%); (3) equivalent output types disagree: the same binary question asked as Choice, Noul or two-level Score gave probabilities differing by 0.055 (Choice vs Noul) on average and one close decision flipped, so a threshold must be tuned for one fixed output type; (4) where Jev's confidence is at least 0.9 it is nearly tied with GPT-6 (94.7% vs 94.4% on 3,744 items), but on HaluEval/JudgeBench its error rate at q >= 0.9 is 2.1% (RewardBench) to 6.5% (JudgeBench), and 7.9% on hard style-adversarial pairs; (5) on reference-free prose (200 general responses with human hallucination labels) every tested judge was near chance (Jev 53.5%) yet confident (mean max probability 0.91 to 0.96; Jev Brier 0.821, AUROC for detecting its own errors 0.498): confidence carries no information there; (6) the threshold recipe: about 100 local labels, choose the threshold by the one-sided 95% lower confidence bound of the accuracy loss rather than the point estimate (cuts the chance of losing more than two points from about 45% to about 5%); (7) two Laya checkpoints (zero-shot) were near chance on preference pairs.
- Stated limitations: one proprietary version; "specialized professional domains are untested"; latency "from one client location and collection period"; the human adjudication is one team member over 183 items chosen by disagreement; no medical or Chinese-language task. Its ethics section says confident errors "argue against using any automated judge as the sole arbiter of consequential decisions."
- Is the user's description right? Yes: it is a "cheap judge first, escalate when uncertain" study; the claim holds on general preference/factuality/correctness benchmarks, not on medical or Chinese data.

## 5. Cheap-judge cascades and confidence-gated escalation: the literature that matters (max 10 bullets; each read 2026-10-06 via the arXiv abstract page unless stated)
1. Foundations: FrugalGPT (arXiv 2305.05176, Stanford; "up to 98% cost reduction" at GPT-4 parity or +4% accuracy at equal cost, on its tasks); "Language Model Cascades: Token-level uncertainty and beyond" (ICLR 2024; deferral on class uncertainty is the established approach for classification and needs learned rules for generation); "A Unified Approach to Routing and Cascading for LLMs" (arXiv 2410.10347, ETH Zurich; proves the optimal cascade rule and combines routing with cascading). Read via search summaries, not the PDFs. The 2026 survey "Dynamic Model Routing and Cascading for Efficient LLM Inference" (arXiv 2603.04445, TMLR 2026) concludes that practical systems "are often compositional" and the best routing depends on deployment constraints.
2. "Trust or Escalate: LLM Judges with Provable Guarantees for Human Agreement" (arXiv 2407.18370, ICLR 2025 oral; University of Washington and Allen Institute for AI): cascaded selective evaluation, a cheap judge first (Mistral-7B in their runs), a confidence estimate from simulated annotators, escalation to stronger judges, and a provable human-agreement guarantee (over 80% agreement at about 80% coverage on a Chatbot Arena subset where GPT-4 alone does not reach 80%). The guarantee needs a labelled calibration set from the target distribution. Read via search summary.
3. The Jev-specific cascade evidence is the CMU preprint (section 4.2) plus the Bonn benchmark (4.1); both are English, general-domain, one vendor model, one proprietary version, none is peer reviewed yet. Its recipe (about 100 local labels, lower-confidence-bound threshold, both presentation orders averaged, one fixed output type) is the transferable part.
4. Conformal Cascade: "Distribution-Free Accuracy Guarantees for Multi-Tier LLM Inference" (arXiv 2607.25018, submitted 2026-07-27): 18 multiple-choice benchmarks "spanning science, medicine, commonsense, and standardized exams", open-weight models; coverage guarantee of at least 1 - K*alpha per accepting tier; the motivation it states is that LLM confidence is miscalibrated and thresholds "must be tuned per model pair and domain". Non-English coverage not stated. Read via abstract-page summary.
5. CascadeDebate (arXiv 2604.12262, submitted 2026-04-14): confidence-based routers send only uncertain cases to small ensembles then to humans; five benchmarks "spanning science, medicine, and general knowledge"; up to 26.75% better than single-model cascades, and an online threshold optimizer gives 20.98 to 52.33% relative improvement over fixed policies, i.e. fixed thresholds are brittle under drift. Also "Cascaded Language Models for Cost-effective Human-AI Decision-Making" (arXiv 2506.11887, v1 2025-06, v3 2025-10): base model, then larger model, then human expert, with online learning of the deferral policy, tested on ARC, MMLU, MedQA and MedMCQA.
6. Medical overconfidence: "When Confidence Fails: Overconfidence in LLMs under Uncertainty and Missing Clinical Information" (arXiv 2608.09080, submitted 2026-08-10): 500 MedMCQA questions under ambiguous wording and removed correct answers; "Although accuracy degrades under increasing uncertainty, model confidence remains misaligned with accuracy"; models fail to notice that information is insufficient. This is the failure a confidence gate is supposed to catch and it does not, when the missing piece is the source itself.
7. Judges in health care: "LLM-as-a-Judge in Healthcare: A Scoping Analysis of Applications, Methods, and Human Alignment" (arXiv 2605.25273, 2026-05-24): PRISMA review of 134 studies; judges "often show moderate to strong alignment with expert judgments, although reliability varies substantially across tasks"; task-specific validation is required. "Reliability without Validity" (arXiv 2606.19544, 2026-06-17): 21 judges from nine providers, about 541,000 judgments; kappa 33-41 points below exact-match agreement on MT-Bench; two production judges with test-retest reliability above 0.95 and severe position bias above 0.10, so a stable judge can still be wrong in a stable way.
8. Chinese: the only Chinese medical judge evidence I found is ClinConsensus (arXiv 2603.02097, v1 2026-03-02, final 2026-09-08): 2,500 expert-curated cases, 36 specialties; evaluation by "a GPT-5.1 grader with a physician-supervised Qwen3-8B judge", i.e. the authors did not trust a small judge alone and calibrated it to physicians. I found no published evaluation of a cheap judge cascade on Chinese medical text. For Jev the Chinese evidence is C-Eval 83.9% (ECE 0.014) in the Bonn benchmark and the vendor's "handled but not equally well" statement; the radiology paper is English.
9. Judges manipulated by the judged text: "Adversarial Attacks on LLM-as-a-Judge Systems: Insights from Prompt Injections" (arXiv 2504.18333, 2025-04): content-author attacks (the judged text carries the attack) with an adaptive search-based attack changing verdicts in 24.1 to 53.7% of cases across five models (search summary figure); "One Token to Fool LLM-as-a-Judge" (arXiv 2507.08794, 2025-07, revised 2026-06): "master keys" such as a colon or "Thought process:" produce false-positive verdicts, up to 80% on some models including leading proprietary ones, fixed by adversarial-negative training; "Security in LLM-as-a-Judge: A Comprehensive SoK" (arXiv 2603.29403, 2026-03-31): 45 studies, judges are both targets and instruments of attack. Jev's own docs list this as an unfixed weakness (section 2.1 item 6).
10. Why a static injection test overstates safety: "The Attacker Moves Second" (arXiv 2510.09023, 2025-10-10; authors from OpenAI, Anthropic, Google DeepMind and others): adaptive attackers (gradient search, reinforcement learning, random search, human red teaming) bypassed 12 recent jailbreak and prompt-injection defences with success above 90% for most, though most had reported near-zero attack success. The Bonn benchmark result for Jev on a static 116-prompt injection set (recall 50% at 0.5) is therefore an optimistic number for an adversary who knows a judge reads the text.
Gaps stated honestly: no study of a decision-only judge cascade on Chinese-language medical text; no study of Jev on medical free-text reasoning; no adaptive-attack test of Jev.

## 6. Facts that change a design decision

1. Pin `jev-1.13.0`, never `jev-latest`. Only one build exists (2026-10-06), the docs say aliases move and "the answers behind it can change", the jaggedness page says "Many of these will be fixed in later versions", and the contract gives no deprecation period (best-effort notice only). Any confidence threshold is version-specific, so a version change needs a re-run of the local calibration set before it is allowed to gate anything. Also record the response `model` field per call.
2. `confidence` is not a probability of being right. It is a function of the answer's own probabilities (Choice: (p_max - 1/n)/(1 - 1/n); Noul has none). Calibration is claimed for groups, and independent data show it is task-dependent: pooled Choice ECE 0.028 but PubMedQA 0.129, prompt-injection set 0.236, radiology sentence support 0.119, reference-free prose AUROC for detecting its own errors 0.498 with mean confidence 0.91 to 0.96. Decision: thresholds come from about 100 labelled items of OUR task (CMU recipe: lower confidence bound of accuracy loss, both orders averaged, one fixed output type), per capability, in Chinese and English separately.
3. Do not use Jev as a gate on free-form prose with no reference. In the CMU study every judge was near chance and confident there; Jev's confidence is informative only where a verdict can be read off supplied text (statement vs a named source passage, topic or intent routing, moderation-style yes/no). That maps to the quote-bond and citation-support checks, and away from "is this synthesis correct".
4. Jev is declared steerable by the judged text ("text that argues for its own classification, can move the answer"), and a static injection test already shows 50% recall at 0.5 on one set. Anything in the judged state that came from a source document, web page, or an author with an interest (a manuscript, a retrieved paper, a user upload) must be treated as adversarial. Keep it out of any blocking path; if it is used at all, escalate or flag, never auto-accept, and never let one Jev verdict be the only barrier (adaptive attackers beat 12 published defences at over 90%).
5. Language: the vendor says CJK is "handled but not equally well" and publishes no Chinese number; the only independent data are C-Eval 83.9% (general knowledge, not medical, not judge-style) and hobbyist hand-built tests. No Chinese medical judge-cascade evidence exists in the literature I found. Decision: nothing Chinese-medical goes through Jev unless a local Chinese eval of at least 100 labelled items passes first.
6. Jev is a US-hosted third-party API (privacy policy: hosted in the United States; no region choice; subprocessor list unreadable; no HIPAA/SOC 2 statement confirmed). Privacy policy bars training on Input, but the MCA lets TypeSafe keep "Telemetry" (hashes, classifications, learnings) "in perpetuity" to improve its services and retains no obligation to delete. Patient-level or unpublished manuscript text should not be sent. Published abstracts and short statements are a different category. Note also that mu's default (no key) sends everything judged to a free relay (OpenCode Zen); do not copy that default.
7. Latency is not 70 to 500 ms for a distant client. Vendor figures are from the US West Coast; the third-party benchmark saw 0.36 s mean at 32 concurrent requests; mu's authors measured 0.3 s warm but 1.7 s cold on HTTP/2 and 3.9 s cold on HTTP/1.1 from their network, real-session p90 of 3.8 to 20 s per decision point, a server idle cut at about 90 s, and an HTTP/2 connection that once went silent for 7 and 26 minutes. A control plane that calls it needs warm connections or per-call timeouts with a fail-open default, and must not put it in a path where the run waits unboundedly.
8. Rate and size limits shape batching: 80 requests/s and 100k tokens/s "adjusting dynamically", 64k tokens per request and 32k for state plus the longest question (32k on OpenRouter). Put ONE state and many questions in a request (cost 12x lower in the vendor demo, verdicts unchanged), but note the multi-label fan-out changes the probability scale (mean P(yes) 0.209 vs observed 0.041 in the Bonn study), so a threshold tuned on one fan-out shape does not transfer to another.
9. The "Choice, Noul, Score" output types are not interchangeable: the same binary question gave probabilities differing by 0.055 on average between Choice and Noul, and one close decision flipped; Noul runs under-confident, Choice over-confident. Pick one type per question and freeze it with the threshold. Order of options biases toward the first option; presentation-order reversal flips pair verdicts 3.7% to 11.1% of the time, so shuffle and re-ask when a decision matters.
10. Do not build on the vendor's cost headline. A third-party tweet analysis relayed by InfoQ reports a median 7x speed-up and 30x saving (not 193.6x/444x); the vendor's own four-workflow eval, as relayed by Arize, has Jev at 68% against 68% and 73% for two frontier models; one startup quoted by InfoQ found it 10 to 20 times more expensive than a cheap LLM because the document is re-sent per call. Costs are per input token only, so cost depends on how much state is sent per decision.
11. mu is useful as a design reference, not as evidence. It is 3 weeks old, defaults changed to "act" on 2026-10-06, and its own retrospective (2026-09-21) found its tool-output admission dropped nothing in 2,412 chunks while spending 54% of Jev input; a calibration comment dated 2026-09-24 in its hive code says the cross-investigator "supersedes" judgment was right 0 of 6 times at the 0.6 bar. The 51% saving is a deterministic, lossless exact-repeat fold on 15 failing Vitest logs from one developer, with no Jev call. The hackathon win is unverified. Patterns worth keeping: shadow mode before active, ledger of every verdict, fail-open fallback per point, code counts facts and the judge reads only language (turn.completion), a higher bar for the action that deletes another agent's information (0.9 for cross-agent "supersedes"), measure on a held-out set labelled before the run.
12. Do not copy mu's tool-output admission class list ("repeated warnings", "passing checks", "progress" are droppable at P >= 0.6). For scientific and medical output the repeated warning, the dropped-rows notice, the passed QC check and the one odd table row are evidence. If any admission step is built, it must be lossless (byte-exact fold with counts, archive reachable by the model) and applied only to recognised log formats, never to data or analysis output; a model-judged drop belongs in shadow first (principle 4 and 5 of our own rules).
13. Contract detail that blocks one tempting design: MCA clause 2.3(b) forbids using the Services or any Output "to perform model distillation, train a model to imitate the output of the Services". Training a local small judge on Jev's labels (mu's stated roadmap) would breach it for a TypeSafe customer; a local judge has to be trained on our own human labels. Also, a local judge is not free of risk: Laya zero-shot was near chance in both mu's tests and the CMU paper, and mu's authors saw high-confidence wrong answers.
14. If a cascade is wanted for the evidence pipeline, the strongest transferable design from the literature is: cheap judge on a fixed question, both orders averaged, exact-match / code checks first (the TypeSafe citation-check cookbook itself does the string match before asking the judge), escalate everything below the calibrated threshold to the stronger model (DeepSeek Pro or Flash with reasoning, per our own routing), keep a random audit sample of ACCEPTED verdicts to detect drift and manipulation, and treat the whole thing as advisory notice, not a blocking check, until its observed false-accept rate on our data is known (our principle 4: blocking points are budgeted).
