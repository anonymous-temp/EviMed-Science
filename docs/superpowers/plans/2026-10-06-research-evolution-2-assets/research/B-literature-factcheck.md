### 1.2 Mechanism (paper v3 §3, App. D–E; code `be50316e`)

**(a) Proposal budget.** Eq. 4 sets b_t = ⌈b_min + (b_max − b_min)·½(1 + cos(πt/T))⌉, which "limits how many mechanisms can change in response to one round of feedback". Table 5: b_min = 1; b_max = 4 for coding and engineering, 3 for workspace; T = 20/20/40; m = 2 candidates per round. `propose.py` enforces the cap in `done()`: an over-budget or untagged submission is sent back. Each edit must carry id, component, hypothesis, targets_mode, predicted task ids and a three-part retroactive check. Rounds run t = 0…T−1 and the result is rounded up, so the cap never reaches 1:
- coding: 4 for t = 0–7, 3 for t = 8–12, 2 for t = 13–19
- workspace: 3 for t = 0–9, 2 for t = 10–19
- engineering: 4 for t = 0–15, 3 for t = 16–24, 2 for t = 25–39

The single-edit closing rounds promised in E.1 happen only when the proposer ships fewer edits than allowed, which it usually did late in the released runs.

**(b) History and proposer view.** §3.2: RRSI "records, for every evaluated candidate, the component it modifies, the hypothesis it tests, the source diff, the resulting score and cost changes, and whether the candidate was accepted" (Eq. 10). In the code this is `runs/<domain>/history.jsonl`, one line per edit. Each line holds the round, variant, component, hypothesis, targets, predicted tasks, diff path, ΔS, ΔC, accepted flag, outcome (ACCEPTED, LOST, REJECTED or a gate failure), S, C, bundle size and a detail field of up to 600 characters. Bundled edits share their candidate's measurement. Gate failures are kept but excluded from T_t and g_t.

Each round the proposer sees:
- `History.render(n=40)`: the 40 most recent records, at most 4 of them unmeasured, without diffs
- the last 20 attribution rows (prediction hit rate, unpredicted regressions)
- the analyst's three-lens report (failure modes, capability gaps, success habits) and per-task digests
- the worst trial of the 30, 60 or 22 lowest-scoring tasks (coding, workspace, engineering) plus the best trials of the top 6
- the full incumbent source, `SKILL.md` and `PATTERNS.md`

**(c) Stagnation.** §3.2 calls the search stalled "when its progress over the previous w rounds remains within the empirical noise band δ". Eq. 13: σ_t = 1[Ŝ_t − Ŝ_{t−w} ≤ δ] with w = 3, and σ_t = 0 while t < w. During a stall, m_draft = 1 of the 2 slots is reserved, and that variant must put at least one edit on a component that has never had a measured edit. The component list is prompt, control_flow, config, output_plumbing, context_mgmt, client_tool, skill, memory and subagent. The declared tag is checked against the diff with regex signals; if re-tagging leaves the reserved slot unmet, the candidate is rejected. Once every component has been tried, nothing is reserved.

**(d) Screening for benchmark-specific edits.** §3.3: before full evaluation "a critic reads each candidate diff and rejects edits that explicitly encode task names, entity names, task-specific values, answers, or other logic specific to the evolve benchmark, as well as edits that add inert machinery". `critic.py` works in two layers:
1. A deterministic precheck: a credential regex plus per-domain denylists (every Terminal-Bench task name, verifier, test, reward and solution paths, judge references, task-id patterns, network and package installs).
2. An Opus 4.8 review with six reject classes: leakage or task specialisation, no-op code or removal of safety mechanisms, grader gaming, undeclared bundling, runtime memory or skill leakage across trials, and unbounded work. The leakage litmus test is: "would this change still make sense, and still help, on an unfamiliar task from a different suite".

The critic reads only the diff (up to 120,000 characters). Objections go back to the proposer for up to 5 repair rounds; a candidate that is still rejected is recorded unmeasured. In the released coding run the critic rejected 1 of 38 candidates, round 10-B, because the declared component did not match the diff.

**(e) Noise-adjusted floor.** Eq. 5: Ŝ(H′) ≥ S* − δ, where S* is the best score accepted so far and "the floor never moves down". δ is measured before evolution on the unchanged base harness, as "how far apart two evaluations of the same harness land" (E.1):
- coding: 3 passes of 178 trials, δ = 0.017
- workspace: 60 of about 14,100 criterion verdicts, δ = 0.004
- engineering: 5 of 244 passes, δ = 0.020, "read off the first percentile of a null built by half-splitting the base evaluation's own trials"

The paper does not report how many base repeats were run. In `calibrate.py`, δ = z·sd(null ΔS) with z = 2, so an unchanged harness clears the floor about 97.5% of the time. With two or more base evaluations, sd = stdev(S_r)·√2. With one evaluation, sd = √2 × the bootstrap SE (2,000 resamples of trials within tasks). The `rrsi.json` files fix δ at the Table 5 values. δ also sets the threshold for the cost-rule branch and for the stall test.

**(f) Cost and complexity.** Eq. 6–7: ΔC is the relative change in policy tokens per trial. When ΔS > δ, the candidate must satisfy ΔC ≤ β0 + β1·ΔS, because "additional inference cost must be justified by measurable performance improvement":
- coding: β0 = 0.10, β1 = 44.5 (25% more tokens per extra pass)
- workspace: β0 = 0.10, β1 = 35.4 (25% per 100 extra criteria)
- engineering: β0 = 0.15, β1 = 24.4 (10% per extra pass)

E.1's worked example: a gain of 7 passes allows 10 + 7×25 = 185% token growth, so a measured 130% is admitted.

When ΔS ≤ δ, Eq. 17 applies: w_s·ΔS − w_c·ΔC + w_n·ν > 0, where ν counts the structural types (client_tool, skill, memory, subagent) that have never appeared in a winning edit (Eq. 16). The weights are only in `rrsi.json`:
- coding (0, 15, 0.5): a within-band gain alone never counts, so the candidate needs a token saving or a new structural component
- workspace (1414, 15, 0.5)
- engineering (244, 2, 0.5)

Engineering also has a guard: a drop in valid-output rate above 0.03, or a rise in no-submission rate above 0.02, rejects the candidate. Among admissible candidates the highest Ŝ wins; if none is admissible, the incumbent stays.

**(g) Pruning.** Eq. 11/14: g_t(ℓ) is the largest ΔS among measured edits on component ℓ in the last n_prune rounds (4, or 5 for engineering), with max ∅ = −∞. B_t is the set of tried components with g_t(ℓ) ≤ 0. The proposer receives B_t together with the accepted machinery under the heading "COMPONENTS TO PRUNE … it has stopped earning its place". A deletion is just another candidate and must pass the critic, the smoke test and selection; no removal or ablation experiment is run. Because a component with no recent measured edit gets −∞, any component not edited in the last 4–5 rounds is flagged. The flag therefore marks staleness, not demonstrated uselessness.

**(h) Smoke tests.** The smoke test runs after the critic and before evaluation, as a "liveness smoke … not a selection rule". It runs `compileall` and constructor/template checks, then one trial (k = 1) on a small task set:
- coding: two fixed tasks, extract-elf and fix-git
- engineering: four tasks the incumbent always solves; the run also needs zero missing submissions and a mean score above 0
- workspace: a fixed smoke split

Any exception or missing trajectory gives `smoke_fail`, recorded unmeasured. In full evaluation a missing trial scores 0 against the full denominator. If more than 10–20% of trials are missing (the per-domain threshold), the evaluation is retried once and then marked invalid.

## 3 The corrections that matter most

1. **The Gemini 64.6→78.7 curve is not evidence for the published algorithm.** The curve and its 10/9/6/2/3 counts exist only in the project-page explorer. That run used two 15-iteration legs with one candidate each and a 24-task performance pre-screen. Its first leg recorded no token costs, and it includes an acceptance that the published coding rule rejects. Do not cite it for Algorithms 1–2 or for leakage screening: "6 rejected at screening" means a cheap performance screen.
2. **RRSI's uncertainty evidence is narrow.** It exists only in v3, covers only RRSI against H0, and has one repeat per domain. Table 2 (the table the draft reproduces), Table 1 and the cost comparison have no intervals or repeats. The token metric leaves out all search-side cost, and the abstract's "30%" contradicts Table 2's 36.3%.
3. **If EviMed borrows RRSI's parameters, take them from `rrsi.json` and record these caveats:**
   - the within-band weights are not in the paper;
   - the released Opus run used δ = 0.034, not the 0.017 in Table 5;
   - the cosine budget never gets down to one edit;
   - the prune set flags stale components, not ones measured as useless.
4. **TextGrad** should be cited as Nature 639:609–616 (2025).
5. **Dwork et al.:** arXiv 1506.02629 is the NeurIPS 2015 paper. The Science 2015 paper is a different article, "The reusable holdout…" (doi 10.1126/science.aaa9375).
6. **"Rethinking the Evaluation of Harness Evolution"** is now at v4 (2026-10-05) and reports a positive matched-budget result on long-horizon games. Cite v4 and qualify the claim.
7. **Venue labels that are now verifiable:**
   - ADAS: ICLR 2025
   - DGM and ACE: ICLR 2026
   - GEPA: ICLR 2026 Oral
   - Meta-Harness and Agent0: COLM 2026
   - EvolveR: ICML 2026, under a different title
