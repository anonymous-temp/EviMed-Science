# Hosted Web Operations Runbook

Date: 2026-07-13

Scope: the controlled, single-node hosted Web deployment described by
`deploy/web/docker-compose.yml`, one identity overlay, and
`deploy/web/docker-compose.monitoring.yml`.
This runbook does not replace the organization's incident-response, privacy,
identity, backup-custody, or legal procedures.

Security, privacy, tenant-isolation, credential, and Runtime Controller
incidents must follow `docs/WEB_SECURITY_INCIDENT_RESPONSE.md`. Its independent
data-access approval and recovery gates are mandatory for the hosted service.

## Access Boundary

- The Node API host mapping is fixed to
  `127.0.0.1:${OPEN_SCIENCE_API_PORT:-8787}:8787` for local diagnostics. Public
  traffic must enter only through Caddy on ports 80/443; never add a wildcard or
  public-interface mapping for container port 8787, and always start the `tls`
  profile.
- Keep `OPEN_SCIENCE_TRUST_PROXY=true`. The bundled Caddy profile replaces
  `X-Forwarded-For` with the observed remote IP before Node applies API and login
  rate limits. A custom proxy must provide the same overwrite behavior; do not
  send proxy headers during direct loopback diagnostics.
- Prometheus, Alertmanager, and Grafana bind to host loopback only. Reach them
  through an authenticated operator path; do not publish ports 9090, 9093, or
  3000 directly.
- Give the metrics bearer token only to Prometheus and deployment smoke. Store
  the token, Grafana password, and Alertmanager webhook config as owner-only
  files generated by `pnpm configure:monitoring`.
- For local identity, keep the bootstrap password only in the owner-only file
  generated by `pnpm configure:local-auth`; production readiness rejects a
  direct environment password. Use `docker-compose.oidc.yml` instead for OIDC.
- Do not add user names, project IDs, file paths, prompts, file contents,
  request bodies, query strings, cookies, model keys, or authorization headers
  to metric labels, alert annotations, or dashboard variables.
- Access to project workspaces or cross-user logs requires separately recorded
  incident authorization. Monitoring alerts alone do not authorize reading
  research data.
- Never mount `/var/run/docker.sock` into `open-science-web` or publish the
  Runtime Controller. Only `open-science-runtime-controller` may hold the Docker
  socket; the API reaches its fixed protocol through a read-only view of the
  private control volume. Set `OPEN_SCIENCE_DOCKER_SOCKET_GID` to the numeric
  output of `stat -c '%g' /var/run/docker.sock`; host preflight must confirm the
  socket owner and group read/write mode before Compose starts.
- Keep the Web API root filesystem read-only with all capabilities dropped,
  `no-new-privileges`, and the bounded `/tmp` tmpfs from the supplied Compose
  file. Treat any drift in those container settings as a failed deployment.

## Isolated release image preparation

The September 7 serving-host build exhausted disk and restarted Web behind 502s.
All release image writes must be admitted before they start. Never build on the
serving host or the default Colima profile. `release:images` currently admits
only a dependency-preserving isolated `build` and a layer-wise serving-host
`pull`; `check-build` / `check-pull` perform the same read-only admission. It does
not prepare a registry, start a VM, change Docker context, push, save/load an
archive, prune, delete, deploy or run arbitrary operator shell commands.

```bash
pnpm release:images check-build --plan /absolute/release/build-plan.json
pnpm release:images build --plan /absolute/release/build-plan.json
# After the candidate's original smoke and the registry/SSH checks:
pnpm release:images check-pull --plan /absolute/release/pull-plan.json
pnpm release:images pull --plan /absolute/release/pull-plan.json
```

Keep these operator plans outside the immutable build checkout. A plan is
admission input, not a new image format or proof that an unmeasured operation
is safe. Evidence references have `{file: "/absolute/path", sha256:
"sha256:<64 lowercase hex>"}` and bind regular files no larger than 2 MiB.
Reads are nonblocking and bounded even if a file grows; FIFOs and symlinks are
refused. Metadata output must not exist, including as a dangling symlink.
Never invent measurements or mark a smoke pass without its underlying run.
[BuildKit's native metadata](https://docs.docker.com/reference/cli/docker/buildx/build/#metadata-file)
and OCI/Distribution manifests retain their original formats.

Both plans require `operation` (`build` or `pull`), `component` (`web` or
`runtime`), `platform: "linux/amd64"`,
`sourceRevision` (full 40-character commit), positive integer `floorBytes`,
positive integer `growthReserveBytes`, `target`, and a `measurement` reference.
The measurement JSON records the same operation/revision/component/platform,
`engineId`, and `peaks`: positive integer measured incremental peak bytes by storage-plane name.
Build measurements also bind `recipeSha256`, `baseReference` and the identical
`dependencyInputs` map; pull measurements bind `image` and `configDigest`.
For each actual filesystem, admission is:

`max(floorBytes, 5 GiB) + sum(measured plane peaks) + growthReserveBytes`.

The minimum observed available capacity is used when several planes share a
filesystem; their free bytes are never added. During execution, the retained
threshold is `max(floorBytes, 5 GiB) + growthReserveBytes`. Required planes are
`engine-root`, `engine-docker`, `engine-containerd`, `engine-tmp`; builds also
require `host-source`, `host-builder`, `host-tmp`. The guarded layout observes
`/`, the live Docker root, `/var/lib/containerd`, `/tmp`, the source checkout,
`~/.colima/evimed-builder` and host temporary directory. Missing or unreadable
planes refuse. Hosts with a different containerd storage layout need verified
probe support before use. Measurements must include unpack/export overhead and
new layers, and count separate plane footprints only once within each estimate.
Use a peak from an equivalent measured operation with a documented growth
reserve; a current-free-space snapshot alone is not a peak measurement.

The monitor checks at admission, just before writes, during the child operation
and after it exits. Each probe is bounded to five seconds. A failed/unreadable
sample or timeout sends SIGTERM only to the owned Docker/buildx process group,
then escalates that group to SIGKILL after five seconds even if its leader has
already exited; leader exit cannot leave a surviving buildx descendant behind.
The failure result remains bounded. Verify
that the daemon cancelled the request before a retry. The one-hour operation
limit is fixed. These sampled checks cannot guarantee protection against
unrelated concurrent writes, a stalled kernel or writes between samples. They
never reclaim current/rollback images, volumes or cache. Keep other workloads
and all default-profile containers outside this operation.

A build target records `context: "colima-evimed-builder"`, the exact endpoint
`unix:///Users/wangzeyuan/.colima/evimed-builder/docker.sock`, live `engineId`,
`engineName`, builder `hostName`, and distinct `servingHostName`. The live context,
engine and single-node Buildx Docker driver must agree. `sourceRoot` is an
absolute clean Git checkout, `sourceTree` its full tree ID, `inputs` a list of
hashed dependency files, `dockerfile` the hashed fixed recipe, `image` a new
explicit local release tag, and `metadataFile` a new absolute output path.
`base` records the digest-pinned `reference`, its daemon-local `imageId`, and
`dependencyInputs` mapping relative input paths to their SHA-256 values.
`platformSmoke` references the actual endpoint/engine/base-specific JSON with
`endpoint`, `engineId`, `platform`, `baseReference`, `nodeVersion: "v22.22.0"`,
`nodeExitCode: 0` and `buildRunExitCode: 0`. Advertised BuildKit platforms do not
satisfy this requirement.

The hashed recipe uses one literal digest-pinned `FROM`, actual local `COPY`
instructions and reviewed fixed `RUN` commands. Supported COPY forms are plain
unquoted paths or JSON arrays, optionally with `--chown`/octal `--chmod`.
Backslash continuations and multiple COPY/RUN instructions are supported. Static
WORKDIR, USER, ENV, LABEL, ENTRYPOINT, CMD, SHELL, EXPOSE, STOPSIGNAL and HEALTHCHECK
instructions are also allowed. Parser directives, heredocs, ARG, extra/flagged
FROMs, COPY --from, RUN flags (including mounts/network overrides), ADD, ONBUILD,
remote sources and inherited ONBUILD triggers are refused before Docker runs.
The build uses `--network none`. Canonical dependency input paths must be unique
and match the base's exact key set before their digests are compared. Compare the base's recorded
lockfiles/dependency inputs to the candidate, update the real package copies
loaded from the DSH seed pnpm tree, reseal, and execute the original runtime
build-smoke in this recipe. Replacing only a visible bundle or retagging an old
image is not a delta. The guard verifies an added rootfs layer over the exact
base prefix and links the inspected result to native BuildKit export metadata
(`exportDigest` may identify an OCI index, separately from `configDigest`); original smoke and seed-copy
correctness still require the retained acceptance evidence before transfer.
A dependency change needs a separately reviewed full rebuild procedure.

A pull target records `endpoint: "unix:///var/run/docker.sock"`, the serving
`engineId`, `engineName` and `hostName`, without a context selector. `image` is
`127.0.0.1:<forward-port>/<repository>@sha256:<platform-manifest-digest>` and
`configDigest` is the expected OCI config digest. `transferEvidence` references
JSON containing a digest-pinned Distribution `registryImage`, `bindAddress:
"127.0.0.1"`, `forwardBindAddress: "127.0.0.1"`, `reverseForwardVerified: true`,
the exact `image`, `sourceRevision` and serving `engineId`. The registry must
already exist on local loopback and reach production loopback through a verified
SSH reverse forward. Do not broaden insecure-registry configuration. Registry
setup/publication/forwarding need their own measured, reviewed operator steps;
this CLI refuses missing metadata and never fabricates that infrastructure.

`releaseSmoke` references the same `sourceRevision` and `configDigest`, with
recorded `originalSmokePassed`, `profileSeedCopiesVerified`, `resealed` and
`rootFsPrefixVerified` all true for the runtime candidate. Web candidates require
only the original smoke and rootfs-prefix evidence; DSH seed checks do not apply. The CLI reads the raw
single-platform manifest/config through the loopback forward, hashes both and
checks source/platform/rootfs, then pulls that manifest digest and verifies the
received RepoDigest and rootfs. Daemon-local image IDs are recorded separately:
containerd may expose an OCI index ID while classic Docker exposes the config
ID. Do not compare those IDs across stores as if they meant the same thing.

After prepared image identity, release-manifest, backup integrity and restore
drill verification, run production host preflight and recreate only the selected
services with `compose up --no-build --pull never`. The host preflight keeps a
10 GiB default floor and refuses overrides below 5 GiB. Build/transfer success
alone is not deployment or OPS03 acceptance.

## Deployment Check

Run before opening traffic and after every deployment:

The Docker host must run Engine 26 or newer for project-scoped
`volume-subpath` mounts.

Run the fail-closed host preflight before starting or updating Compose:

```bash
stat -c '%g' /var/run/docker.sock
# Set that numeric output as OPEN_SCIENCE_DOCKER_SOCKET_GID in deploy/web/.env.
chmod 600 deploy/web/.env
pnpm preflight:host --env-file deploy/web/.env
```

When `OPEN_SCIENCE_DEEPSEEK_PROVIDER_ENABLED=true`, production readiness wants a
signed model receipt: it attests that the model which actually answers drove the
whole tool chain — streaming, tool-result iterations, session history, structured
final answer — through the internal gateway, rather than that a model of that
name exists.

**The minting half drives a real runtime container, so it runs where one can be
started — not from a laptop checkout.** `pnpm preflight:deepseek:release` starts
the runtime image the way `buildRuntimeLaunchPlan` starts it, points it at a
model gateway this process owns so the requests can be counted, asks the model
to normalize one term through the research MCP and write one file, and reads the
evidence out of the resulting `session/*` events. It signs nothing it did not
observe: a run that never completed a tool result, never wrote the artifact, or
never answered with a structured object fails by name and leaves no receipt.

Three consequences for operations, all of them measured rather than assumed.
First, **it must run inside the deployment**:
the `evimed-universal` preset, the research MCP and the capability trees live at
`/opt/evimed` inside the runtime image, and the runtime container reaches the
gateway by the deployment's own service name — the `receipt` compose profile is
that container, and it needs the runtime controller socket and the runtime
network, exactly as the web service does. Second, **it runs after
`release:manifest`, not before**: the gate refuses to launch a runtime whose
image the manifest does not name. The retired gate ran first only because it
drove a bare binary that no manifest described. Third, and for the same family
of reason, **it runs after the new stack is up**: the runtime controller checks
that the caller's `releaseId` equals its own and answers
`runtime_controller_release_mismatch` otherwise, so a receipt for the new
release cannot be minted while the previous release's controller is the one
running. Expect `/api/ready` to be red on the receipt alone for the minutes
between `compose up` and the mint; the scheduler then keeps it fresh.

There is no `--fake` chain. The flag is still read and still refused
(`deepseek_release_mode_invalid`) rather than ignored, because emulating a chain
here would mean certifying the mock kernel — which answers one tool call and a
fixed sentence.

The verification half is unchanged and still enforced. A receipt is HMAC-signed
with a domain-separated key derived from the Model Gateway signing secret, over
its whole body including the `dshVersion` field that names the kernel — a field
renamed on one side alone verifies as tampering. Host preflight and `/api/ready`
verify the signature, release identity, and timestamp; the default maximum
receipt age is 24 hours and timestamps more than five minutes in the future are
rejected.

Every credential the gate touches arrives by path, never by value. These are the
variables it reads:

```bash
umask 077
export OPEN_SCIENCE_DEEPSEEK_API_KEY_FILE="$PWD/deploy/web/secrets/deepseek-api-key.txt"
export OPEN_SCIENCE_MODEL_GATEWAY_SIGNING_SECRET_FILE="$PWD/deploy/web/secrets/model-gateway-signing-key.txt"
export OPEN_SCIENCE_DEEPSEEK_RELEASE_RECEIPT_FILE="$PWD/deploy/web/secrets/deepseek-release-receipt.json"
export OPEN_SCIENCE_DEEPSEEK_RELEASE_RECEIPT_ID="dsrg_$(openssl rand -hex 16)"
export OPEN_SCIENCE_SOURCE_REVISION="$(git rev-parse HEAD)"
export OPEN_SCIENCE_DEEPSEEK_CONFIG_REVISION="$(grep -E '^OPEN_SCIENCE_DEEPSEEK_CONFIG_REVISION=' deploy/web/.env | cut -d= -f2-)"
pnpm preflight:deepseek:release
```

Never pass the provider key on the command line or in
`OPEN_SCIENCE_DEEPSEEK_API_KEY`. `OPEN_SCIENCE_OPENCODE_BIN` was removed with the
second kernel — exporting it now makes the API refuse to start by name rather
than starting with it ignored.

Once a minting path exists again, copy the receipt ID, config revision, receipt
host path, and source revision unchanged into `deploy/web/.env`. A
`mode: "fake"` receipt is CI evidence only and cannot satisfy production host
preflight or `/api/ready`.

Keep both provider and signing-secret files owner-readable only (`chmod 600`).
The gateway rejects group/world-readable secret files, caps each request at 2
MiB and each upstream response at 32 MiB by default, and aborts upstream work
when the downstream closes. Adjust the byte limits only after reviewing the
workload and memory impact.

For the production profile, keep
`OPEN_SCIENCE_PREFLIGHT_OBJECT_STORAGE=true` and configure a credential-free
`OPEN_SCIENCE_OBJECT_BACKUP_URI`. The offline preflight performs a temporary
write, byte-for-byte read-back, and delete using workload identity. The host
running preflight must provide `aws` or the audited executable named by
`OPEN_SCIENCE_OBJECT_BACKUP_CLI`, under the same identity used by the backup
scheduler. Verify that
the probe leaves no `open-science-preflight` objects behind after a forced
failure test.

```bash
export OPEN_SCIENCE_IDENTITY_COMPOSE=deploy/web/docker-compose.local-auth.yml
# For OIDC, select docker-compose.oidc.yml and run pnpm check:oidc instead.
pnpm check:local-auth
pnpm verify:release-manifest
# Verify backup integrity and the recorded restore drill before recreation.
pnpm preflight:host --env-file deploy/web/.env
pnpm check:monitoring
docker compose --env-file deploy/web/.env \
  -f deploy/web/docker-compose.yml \
  -f "$OPEN_SCIENCE_IDENTITY_COMPOSE" \
  -f deploy/web/docker-compose.monitoring.yml \
  --profile monitoring --profile tls config >/dev/null
docker compose --env-file deploy/web/.env \
  -f deploy/web/docker-compose.yml \
  -f "$OPEN_SCIENCE_IDENTITY_COMPOSE" \
  -f deploy/web/docker-compose.monitoring.yml \
  --profile monitoring --profile tls up -d --no-build --pull never
```

Then verify:

1. `/api/health` reports the expected release ID and `/api/ready` returns
   success through the public TLS route, including the `release` check.
2. Host socket inspection shows the configured `OPEN_SCIENCE_API_PORT` bound
   only to `127.0.0.1`; ports 80/443 are the only public Compose entry points.
3. Prometheus targets `open-science-web`, `open-science-health`, and
   `open-science-readiness` are up.
4. Alertmanager shows the configured `operator-webhook` receiver. With
   `OPEN_SCIENCE_PREFLIGHT_ALERT_DELIVERY=true`, online host preflight sends a
   synthetic resolved notification to that exact receiver and requires a 2xx
   response; separately confirm it reaches the human-owned escalation path.
5. Grafana opens the provisioned `EviMed Operations` dashboard and does
   not allow anonymous access.
6. `/api/ready` reports runtime `controlPlane=controller_socket`,
   `transport=unix`, `dataMount=volume`, and
   `networkMode=open-science-runtime-internal` for the supplied Compose profile.
7. `pnpm smoke:deployment` succeeds with
   `OPEN_SCIENCE_SMOKE_METRICS_TOKEN_FILE` pointing at the generated metrics
  token file.
8. After the public TLS route is active,
   `pnpm preflight:host --env-file deploy/web/.env --online` succeeds.
   This run performs the configured alert-delivery probe and is intentionally
   not side-effect free.

Do not edit a generated release manifest to make readiness pass. Use the guarded
isolated build and digest pull procedure, regenerate the manifest from the immutable release
context, run `pnpm verify:release-manifest`, and recreate the API container.
Preserve the manifest with deployment records because it links the release ID
and source revision to actual image IDs, complete hosted source-tree digests,
and skill/build-input digests.

If readiness reports `runtime_controller_unavailable`,
`runtime_controller_protocol_mismatch`, or
`runtime_controller_release_mismatch`, stop accepting runtime starts and inspect
`open-science-runtime-controller` logs plus the private control volume. Confirm
that the API container has no `/var/run/docker.sock` mount before recovery.
Recreate the controller from the same immutable Web image and release manifest,
wait for its health check, then rerun readiness and deployment smoke. Do not
temporarily switch the API to direct Docker control to clear the alert.

If readiness reports `runtime_controller_limit_mismatch`, confirm that
`OPEN_SCIENCE_MAX_RUNNING_RUNTIMES` and
`OPEN_SCIENCE_MAX_RUNNING_RUNTIMES_PER_USER`, as well as
`OPEN_SCIENCE_MAX_CONCURRENT_KERNELS` and
`OPEN_SCIENCE_MAX_CONCURRENT_KERNELS_PER_USER`, have identical values in the
API and Controller services. Do not raise only the Controller limit: both
layers must enforce the reviewed deployment capacity.

If Controller startup fails with `kernel_orphan_cleanup_failed`, keep the API
out of service, inspect containers labelled `open-science.web.kernel=true`, and
remove the identified kernels through the trusted Docker operator path. Do not
delete the Controller socket or bypass startup cleanup while a labelled kernel
remains.

The `docker-hosted` GitHub job exercises Compose and a real DSH runtime container
boundary on a Linux runner. It also starts Caddy with a temporary local CA,
trusts that CA in the runner, and sends online preflight plus deployment smoke
through HTTPS instead of treating the API's host port as reverse-proxy proof.
Require that job to pass, then repeat deployment
smoke on the target host: CI still cannot prove that host's controller access to
the Docker socket, storage quotas, TLS route, outbound network controls,
backups, or external webhook delivery.

## Alert Response

| Alert | First checks | Immediate action |
| --- | --- | --- |
| `OpenScienceApiMetricsUnavailable` | API container state, Prometheus target error, token-file mount | Restore the scrape secret or API; if API health also fails, remove traffic and restart only after logs are captured. |
| `OpenScienceHealthProbeFailed` | Container process, host memory/disk, reverse proxy and Docker logs | Remove the instance from traffic, preserve error/runtime logs, and restart or roll back. |
| `OpenScienceReadinessProbeFailed` | `/api/ready` check code | Correct the named readiness dependency; do not bypass the readiness gate. |
| `OpenScienceReadinessCheckFailed` | `check` and `code` labels | Follow the corresponding auth, backup, security, resource, runtime, kernel, or observability configuration owner. |
| `OpenScienceApiServerErrors` / `OpenScienceApiHighErrorRatio` | Normalized route/status metrics and `.openscience/errors.jsonl` request IDs | Rate-limit or disable the affected feature, roll back a bad release, and preserve sanitized evidence. |
| `OpenScienceRateLimitPressure` | Source gateway logs and normalized error codes | Confirm abuse versus legitimate load; tighten gateway limits or add controlled capacity without disabling isolation controls. |
| `OpenScienceTaskQueueNearCapacity` | Queue depth, active tasks, task timeouts | Stop accepting new long tasks, cancel confirmed runaway work, and inspect task/runtime logs. |
| `OpenScienceRuntimeCapacityNearLimit` | Running/starting runtime count and idle timeout | Stop orphaned/idle runtimes and restrict new starts; do not raise limits beyond host capacity. |
| `OpenScienceRuntimeQuotaMonitorGap` | Runtime manager logs and quota-monitor interval | Stop uncovered runtimes immediately; restore monitoring before allowing restart. |
| `OpenScienceCertificateExpiringSoon` | `systemctl status certbot.timer`, `certbot certificates`, the last renewal log | The certificate is short-lived and the timer normally renews it, so this alert means renewal has stopped, not that a renewal is due. Fix the timer or renew by hand before the remaining hours run out. |
| `OpenScienceHostDiskLow` / `OpenScienceHostDiskCritical` | `df -h /`, `docker system df`, `ls /srv/evimed-science/releases` | Run `node scripts/ops/release-retention.mjs` (keeps the newest N and anything a container still bind-mounts), then prune images this deployment no longer references. On a host shared with other products, confirm what an image belongs to before removing it. |

For every critical alert, record start/end time, affected release, readiness
codes, request IDs, containment action, data-access approvals, recovery evidence,
and follow-up owner. Never paste raw workspace files or credentials into the
incident channel.

Alerts indicating cross-user access, Docker socket exposure, Runtime Controller
compromise, credential disclosure, or research-file exfiltration immediately
activate `docs/WEB_SECURITY_INCIDENT_RESPONSE.md`; routine restart guidance is
not sufficient containment for those events.

## Secret Rotation

1. For OIDC, rotate the provider client secret first, then run
   `OPEN_SCIENCE_OIDC_CLIENT_SECRET=... pnpm configure:oidc -- --rotate` and
   `pnpm check:oidc`. Recreate the Web service and complete an interactive SSO
   login before revoking the old provider secret. Flow-secret rotation only
   invalidates login redirects currently in flight.
2. Export a new metrics token and Grafana password and supply the approved HTTPS
   alert webhook URL to `pnpm configure:monitoring`.
3. Run `pnpm check:monitoring` and confirm files remain mode `0600` under a mode
   `0700` directory.
4. Recreate `open-science-web`, Prometheus, Alertmanager, and Grafana together so
   the API and scraper switch to the same token.
5. Run deployment smoke with the token file, verify the alert receiver, and
   revoke the old webhook/token in the external system.
6. Record the rotation without recording secret values, session cookies, or
   webhook query data.

## Evidence and Recovery

- Preserve sanitized API error, security, audit, task, and runtime JSONL logs
  before destructive recovery. Their local `.1` rotation is not centralized
  retention.
- Preserve Prometheus/Alertmanager data volumes only when the privacy and
  incident policy permits; time-series data remains operator-sensitive.
- Follow `scripts/ops/backup-data.sh`, `restore-data.sh`, and
  `restore-drill.sh` for application data recovery. Monitoring volumes are not
  a substitute for `OPEN_SCIENCE_DATA_DIR` backups.
- For the local backup profile, inspect
  `/backups/.open-science-backup-state.json` through the backup service and run
  `node scripts/ops/backup-scheduler.mjs health`. A failed or stale state means
  backup readiness is not proven even when old archives exist. Keep the API's
  backup mount read-only; only the backup service may create or prune archives.
- The production host also has the single `evimed-postgres-backup.timer` unit.
  Its versioned implementation is `scripts/ops/postgres-backup.py`, installed
  as `/usr/local/sbin/evimed-postgres-backup`; the existing unit names and daily
  schedule live in `deploy/host/`. Confirm the service is inactive before
  replacing its executable. Install the script with mode 0755 and the unit
  files with mode 0644, reload systemd, enable the existing timer, and run its
  service once before deploying Web's PostgreSQL backup readiness requirement.
  Do not create a second scheduler. The source container's PostgreSQL 16 tools
  produce an encrypted snapshot and verify exact application tables/row counts
  in a uniquely named temporary database; the source database is never a
  restore target. The existing 30-day retention and encrypted archive format
  remain supported. Unresolved drill cleanup stays in the receipt and is
  retried before another backup can report healthy.
- Set `OPEN_SCIENCE_POSTGRES_BACKUP_STATUS_DIR` to the existing host backup
  directory's `status` subdirectory (normally
  `/srv/evimed-science/shared/backups/postgres/status`). Mount only that
  non-secret status directory read-only. Web verifies its age, restore/cleanup
  proof and actual PostgreSQL system identifier, database OID and name. The
  tracked empty default directory preserves non-PostgreSQL local deployment;
  it is not a production restore receipt. This database dump does not cover
  separate attachment volumes, MemOS stores/queues or OpenList configuration.
- When S3-compatible off-host backup is configured, record the uploaded object
  URI without credentials, download it with `pnpm restore:object`, verify its
  checksum, and run a disposable restore drill. Confirm bucket versioning,
  lifecycle/object-lock policy, workload identity, and client-side passphrase
  custody independently of the application host.
- After recovery, require `/api/ready`, monitoring targets, alert delivery,
  backup scheduler health, deployment smoke, and runtime stop/cleanup checks to
  pass before restoring traffic.
