# Active Research: execution gaps and implementation plan

Status: 2026-10-28. This branch is a code handoff, not a deployment or production acceptance. The owner confirmed that supplied patient and personal data are already authorized and requested no additional online authorization workflow. Use the existing account and project access boundaries; do not introduce a consent gate.

## What this branch implements

- **One 主动科研 workspace per project** (`/app/active-research`): a research queue of every long goal (LoopX) and scheduled study, running ones first; the observatory of the selected one; its findings (with how each was checked), every file its executions handed over, its materials, and its execution history. A long goal is named by what was asked when it was set and lists its rounds.
- **The observatory** (`ResearchObservatory`, model `lib/researchObservation.ts`): a fixed dark mission-control scene folded incrementally from the run's event stream — elapsed clock, model calls, tokens, operations, literature included, conclusions checked and cost; the seven-stage research line with the orchestrator and every delegated member standing at the stage of its last call; the latest reasoning; the live operations feed with input and result. Counts never drop below the run's stored aggregate; anything unreported reads “—”. Reduced motion stops every animation.
- **Steering.** For an interactive running execution a direction is sent through the run-steer endpoint; otherwise it is a follow-up for the next execution. An uncertain submission is not retried automatically.
- **Database import.** The connector exists in production only when the operator sets `OPEN_SCIENCE_RESEARCH_DB_ALLOW` (egress allowlist) and `OPEN_SCIENCE_RESEARCH_DB_KEYRING_FILE` (an independent owner-only keyring, mounted from `OPEN_SCIENCE_RESEARCH_DB_KEYRING_HOST_FILE`); otherwise `GET /api/research-databases/status` answers `available: false` and the page offers no database entry. A saved connection lists its readable tables; the person picks a table and its columns, and the table is imported as a CSV dataset (up to 20,000 rows, 64 columns, 12 MB of cell text) into the knowledge base and the research. Patient and personal data are used under the owner's existing authorization; there is no online authorization step.

## Remaining implementation and acceptance

1. **Database production activation.** The keyring file, allowlist and compose wiring exist (start-up checks every saved credential's key against the keyring and answers `research_db_keyring_incomplete` on a gap). Still open: keyring backup and recovery, versioned rotation and retirement with a multi-instance protocol that prevents an old version becoming active after retirement, and resource budgets across replicas. Validate the resulting data path, isolation and failure recovery using disposable datasets including synthetic patient-like records. No new online authorization process is requested.
2. **Dataset breadth.** Design complete and reproducible ingestion for larger datasets and database connectors, including stable snapshot identity, types, schema evolution, source versioning, capacity limits and provenance. The snapshot is now a 20,000-row CSV of the first rows PostgreSQL returns (no ORDER BY, so no guaranteed order) with the column types dropped from the file and cells written verbatim (no spreadsheet formula escaping, so the analysis sees the real values); when `truncated` it must not be presented as a complete dataset. Verify that research can actually read associated sources and trace its results to the correct source version.
3. **Long-running research.** Provide a durable project-level inventory of LoopX goals, authoritative goal state and run-to-goal lineage, including work between continuation turns. Exercise creation, unattended continuation, pause, recovery and results with a real runtime and model. The current view observes continuation runs; it does not prove a 24-hour autonomous study.
4. **Live steering.** Implement and verify bounded-runtime delivery if current in-flight intervention is required for those runs, including correct run ownership, delivery acknowledgements, cancellation and correction budgets. Validate the existing interactive path against a real runtime. Until then, show the current follow-up semantics without claiming the running bounded task changed.
5. **Outputs and versions.** Connect a complete, project-scoped results and version inventory to authoritative artifact records, including intermediate outputs, code and paper revisions; verify identity, access and historical retrieval. The current links expose artifacts present in recorded runs, not an exhaustive version history.
6. **Integration and release.** The full server suite ran on Linux (2026-10-28): 12,698 tests, 83 failures, and the same 83 fail on the base commit in the same sparse checkout (missing `项目代码/` and `docs/`, no Docker or Chromium) — none from this work; a full checkout in CI is the gate. The fixture UI walk of `/app/active-research` was run on int/1029 (2026-10-28) and the console was brought inside the data page's budget (three kinds of border, five size × weight pairs) instead of being given an override. Still open: the TLS integration test on an SSL-enabled PostgreSQL, and real runtime acceptance with a live LoopX goal. Deployment remains a separate instruction.

Database tests use disposable local PostgreSQL databases; the TLS integration test needs a PostgreSQL built with SSL (`OPEN_SCIENCE_TEST_RESEARCH_TLS=1`) and was not run on the Linux dev box.
