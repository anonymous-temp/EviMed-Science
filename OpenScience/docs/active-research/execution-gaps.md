# Active Research: execution gaps and implementation plan

Status: 2026-10-28. This branch is a code handoff, not a deployment or production acceptance. The owner confirmed that supplied patient and personal data are already authorized and requested no additional online authorization workflow. Use the existing account and project access boundaries; do not introduce a consent gate.

## What this branch implements

- **One 主动科研 workspace per project** (`/app/active-research`): a research queue of every long goal (LoopX) and scheduled study, running ones first; the observatory of the selected one; its findings (with how each was checked), every file its executions handed over, its materials, and its execution history. A long goal is named by what was asked when it was set and lists its rounds.
- **The observatory** (`ResearchObservatory`, model `lib/researchObservation.ts`): a fixed dark mission-control scene folded incrementally from the run's event stream — elapsed clock, model calls, tokens, operations, literature included, conclusions checked and cost; the seven-stage research line with the orchestrator and every delegated member standing at the stage of its last call; the latest reasoning; the live operations feed with input and result. Counts never drop below the run's stored aggregate; anything unreported reads “—”. Reduced motion stops every animation.
- **Steering.** For an interactive running execution a direction is sent through the run-steer endpoint; otherwise it is a follow-up for the next execution. An uncertain submission is not retried automatically.
- **Database import.** The connector exists in production only when the operator sets `OPEN_SCIENCE_RESEARCH_DB_ALLOW` (egress allowlist, `host:port=IPv4`, the host matched in lower case, only the IPv4 answers of the name checked) and `OPEN_SCIENCE_RESEARCH_DB_KEYRING_FILE` (an independent owner-only keyring, mounted from `OPEN_SCIENCE_RESEARCH_DB_KEYRING_HOST_FILE`); otherwise `GET /api/research-databases/status` answers `available: false` and the page offers no database entry. A database whose certificate chain does not end in a public authority (a cloud provider's own root, a self-signed certificate) needs its certificate in the operator's CA directory, `OPEN_SCIENCE_RESEARCH_DB_CA_HOST_DIR/<host>.pem`. A saved connection is listed by its host and database name and lists its readable tables, with the columns the snapshot will not read; the person picks a table and its columns, and the table is imported as a CSV dataset into the knowledge base and the research. Every limit (20,000 rows, 64 columns, 12 MB of cell text, 32 KB a cell, 200 tables, 4 connections at once and 1 a person, 50 saved credentials a project, 30 s a connection, 24 MB on the wire) is a key of `researchDbConfig.mjs` with its reason, and every refusal or limit that bit is a counter (`open_science_research_db_refusals_total{reason}`, `..._imports_total{outcome}`; `docs/WEB_OPERATIONS_RUNBOOK.md`). A certificate that does not verify, a refused login, no answer and a role that bypasses row security are four different answers. Patient and personal data are used under the owner's existing authorization; there is no online authorization step.
- **An import says what it left out.** The title of the source carries it (`public.cohort（前 20,000 行，共 52,340 行；…）`), `payload.snapshot` has the facts, the study's material entry has a compact `import` (partial, rows kept and in the table, withheld cells, dropped columns, the path of the note), and the sidecar `<name>.import.json` beside the CSV is what a run opens. A cell over the cell limit is written `__evimed_withheld__`, never empty (an empty cell is a NULL); a column of an unsupported type or past the column cap is named with its type. Importing the table again is a new version of the same source (the logical path is the database, the schema and the table, not the capture time), and it takes the old version's place in the question's material; a full list of material refuses a new table before the remote database is read. The table is kept out of the knowledge engine, the wiki and graph compile and the personal library; the project's runs read it as a file and with `kb_search`.

## Remaining implementation and acceptance

1. **Database production activation.** The keyring file, allowlist, CA directory and compose wiring exist (start-up checks every saved credential's key against the keyring and answers `research_db_keyring_incomplete` on a gap; `/api/ready` carries it as a warning on the `researchDb` check). Still open: keyring backup and recovery, versioned rotation and retirement with a multi-instance protocol that prevents an old version becoming active after retirement (the unused single-row rewrap was deleted on 2026-10-29: it had no caller), and resource budgets across replicas (the admission caps are per process since 2026-10-29: two replicas admit twice the readers). Validate the resulting data path, isolation and failure recovery using disposable datasets including synthetic patient-like records. No new online authorization process is requested.
2. **Dataset breadth.** Design complete and reproducible ingestion for larger datasets and database connectors, including types, schema evolution, source versioning, capacity limits and provenance. The snapshot is a CSV of the first rows PostgreSQL returns (no ORDER BY, so no guaranteed order and not a sample); what it left out is stated in the title, the source, the sidecar and the material entry (see above), and a re-import is a new version of the same source. Still open: a deterministic order or a keyed sample for tables past the row cap, the column types in the file, schema evolution between versions (a column added or retyped is shown in the sidecar of each version and not compared), and tracing a run's result to the version of the table it read. Verify that research can actually read associated sources and trace its results to the correct source version.
3. **Long-running research.** Provide a durable project-level inventory of LoopX goals, authoritative goal state and run-to-goal lineage, including work between continuation turns. Exercise creation, unattended continuation, pause, recovery and results with a real runtime and model. The current view observes continuation runs; it does not prove a 24-hour autonomous study.
4. **Live steering.** Implement and verify bounded-runtime delivery if current in-flight intervention is required for those runs, including correct run ownership, delivery acknowledgements, cancellation and correction budgets. Validate the existing interactive path against a real runtime. Until then, show the current follow-up semantics without claiming the running bounded task changed.
5. **Outputs and versions.** Connect a complete, project-scoped results and version inventory to authoritative artifact records, including intermediate outputs, code and paper revisions; verify identity, access and historical retrieval. The current links expose artifacts present in recorded runs, not an exhaustive version history.
6. **Integration and release.** The full server suite ran on Linux (2026-10-28): 12,698 tests, 83 failures, and the same 83 fail on the base commit in the same sparse checkout (missing `项目代码/` and `docs/`, no Docker or Chromium) — none from this work; a full checkout in CI is the gate. The fixture UI walk of `/app/active-research` was run on int/1029 (2026-10-28) and the console was brought inside the data page's budget (three kinds of border, five size × weight pairs) instead of being given an override. The TLS integration test ran on the Linux dev box on 2026-10-29 (it passes) with the dev box's portable PostgreSQL, which has no OpenSSL: a TLS terminator in the test stands in front of it, so the client's real handshake, chain and name verification, CA file and the three failure answers are exercised, and a PostgreSQL built with OpenSSL terminates TLS itself with the same test. Still open: that test against an SSL-enabled PostgreSQL, and real runtime acceptance with a live LoopX goal. Deployment remains a separate instruction.

## Evidence and limits

Results of the 2026-10-28 take-over are in `PROGRESS.md`. The observatory and the page were inspected in a local browser with a synthetic event stream (1440 px and 390 px), not a live customer session. Database tests use disposable local PostgreSQL databases; the TLS integration test (`OPEN_SCIENCE_TEST_RESEARCH_TLS=1`, with the server tools and `openssl`) runs against a PostgreSQL with or without OpenSSL. A LoopX goal appears in the queue from its first continuation round; a goal whose first turn has not yet been continued is reached through its conversation.
