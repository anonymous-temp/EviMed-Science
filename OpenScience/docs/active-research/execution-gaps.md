# Active Research: execution gaps and implementation plan

Status: 2026-10-28. This branch is a code handoff, not a deployment or production acceptance. The owner confirmed that supplied patient and personal data are already authorized and requested no additional online authorization workflow. Use the existing account and project access boundaries; do not introduce a consent gate.

## What this branch implements

- A single Active Research workspace with a project-scoped task list, an observatory driven by observed run events, default execution details, artifacts and usage when the ledger supplies them, associated materials, uploads, and links to recorded files. Missing or contradictory observations remain unknown.
- In-page access to the existing LoopX conversation and a list of observed continuation runs. The list is not a complete inventory of goals and a continuation's status is not the current goal status.
- For an interactive running episode, a direction is sent through the existing run-steer endpoint. For a bounded episode, the direction is handled as a follow-up; it does not change the current execution. An uncertain submission is not automatically retried.
- A PostgreSQL snapshot interface and isolated server implementation. **The database route is enabled only by explicit test injection; production remains unavailable.** Its tested scope is a read-only snapshot of up to 200 rows and 24 selected columns, not a complete database ingestion pipeline. This is not a general database-plugin integration.

## Remaining implementation and acceptance

1. **Database production activation.** Finish independent keyring provisioning, backup and recovery, versioned rotation and retirement with a multi-instance protocol that prevents an old version becoming active after retirement. Check all existing ciphertext before removing keys; reject unknown or null key versions without guessing. Wire an operator-owned configuration and deployment secret only after tests and security review; establish explicit endpoint/network policy and resource budgets across replicas. Validate the resulting data path, isolation and failure recovery using disposable datasets including synthetic patient-like records. No new online authorization process is requested.
2. **Dataset breadth.** Design complete and reproducible ingestion for larger datasets and database connectors, including stable snapshot identity, types, schema evolution, source versioning, capacity limits and provenance. The current PostgreSQL sample has no guaranteed row order and must not be presented as a complete dataset. Verify that research can actually read associated sources and trace its results to the correct source version.
3. **Long-running research.** Provide a durable project-level inventory of LoopX goals, authoritative goal state and run-to-goal lineage, including work between continuation turns. Exercise creation, unattended continuation, pause, recovery and results with a real runtime and model. The current view observes continuation runs; it does not prove a 24-hour autonomous study.
4. **Live steering.** Implement and verify bounded-runtime delivery if current in-flight intervention is required for those runs, including correct run ownership, delivery acknowledgements, cancellation and correction budgets. Validate the existing interactive path against a real runtime. Until then, show the current follow-up semantics without claiming the running bounded task changed.
5. **Outputs and versions.** Connect a complete, project-scoped results and version inventory to authoritative artifact records, including intermediate outputs, code and paper revisions; verify identity, access and historical retrieval. The current links expose artifacts present in recorded runs, not an exhaustive version history.
6. **Integration and release.** Run the server suite in its supported Linux environment with its required services, investigate any remaining failures, and run the authenticated UI walk and real runtime acceptance. Verify production data and security configuration separately. Commit/push and a local fixture are not deployment or customer-path acceptance. Deployment remains a separate instruction.
