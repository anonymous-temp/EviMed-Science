## Completion and interpretation

This is an incomplete product-path attempt: 17 of the frozen 100 questions were observed, from M01 (14) and U03 (3), covering 7 of 24 categories. Sixteen valid pairs pass in both arms: 100%, Wilson 95% interval 80.6–100%; paired difference 0 percentage points, conservative exact 95% interval −24.0 to +24.0. One registered invalid item, M01-q005, remains in the legacy denominator (16/17 in each arm). The source says Thursday and the gold expects Monday. No missing question is counted as an answer failure or pass.

The unchanged product cannot finish U03: its default-project run ledger reaches 1,048,339 bytes against a 1,048,576-byte ceiling at source session 39. Adding the next event raises `agent_runs_too_large`. The first observed monitor failure is 2026-11-11T11:08:23.321Z, run `run_4e540539ea837cad5ebd23cd7158c112`; 708 events cover 142 runs. Completion and cancellation cannot be recorded, and process restarts return the same accepted run. The immutable ledger, its SHA-256, and first/last error records are under `/srv/evimed/runs/g1pp-eg-5/cases/U03/BLOCKED.json` and `blocked-ledger.jsonl`. This is a measured product defect; the earlier HTTP cancellation timeouts alone did not establish its cause.

G1 was closed at 12:17 UTC so the remaining original twelve-hour allowance could cover G10 then G3. Twenty U03 probes were unobserved because of the blocker; 63 P01/P02 probes were unobserved when the phase was closed. P01 had partially ingested source conversations but no measured question. These omissions cannot support a proxy claim across categories or users. The observed agreement does not establish that the engine-layer accuracy transfers to real conversations.

## Observed path differences

- The baseline engine commit is `1e4c750aa349729140de743bac70a7b3d30ee699`; product code is integration commit `aba955293db897e4c09cc7d1702de89d17a7b138` plus evaluation scaffolding. The baseline records history search and rejection judging, but not all current candidate switches. This is a comparison of these two paths, not an isolated causal estimate of a switch.
- Both use DeepSeek Flash with thinking enabled. The native wire explicitly sets a 65,536-token output limit; the engine's DeepSeek request leaves that limit unspecified and has an eight-round tool loop. Captured product requests offer 51 tools; the engine runner offers five memory tools and `skill`. Product queries can use workspace files, the web, office skills, subagents and interactive questions. Matching fact availability is an anchor observation, not proof of causal use.
- Fact-bearing native profile blocks average 873.7 characters in the engine and 1,167.9 in the product. The product also has a counts-only memory index (115.3 characters on average) and earlier-file context (351.4 characters). Corresponding raw engine wire fields were not captured and are unobserved. No resident memo/project-card block was observed in these 17 product openings. The counts-only index contains no remembered facts.
- Matching native-profile context occurs in 5/17 engine openings and 7/17 product openings. Search/retrieval anchors occur in 13/17 engine answers and 12/17 product answers. Sixteen answers in each arm are correct with matching memory context available; none has a matching non-memory tool output under this anchor check. Workspace files still provide an alternative recall surface and survive source conversations.
- Eleven pairs search in both arms, and all eleven have different query sequences. The engine makes 23 search calls returning 170 structured hits; the product makes 17 returning 153. Mean hits per call are 7.39 versus 9.00. Relative memory-path Jaccard overlaps range from 0.071 to 0.263; equal paths would not establish equal contents. Product text appended outside the first JSON object averages 7,816.6 characters versus 2,828.0; this includes additional textual context, not just structured hits. The native tool combines JSON and following text into one block; the engine keeps separate blocks. Both formats are parsed without discarding the following text.
- Mean question input tokens are 21,097 engine versus 54,229 product; output tokens 712 versus 600. Mean recorded question time is 9.91 versus 16.91 seconds, with different timing scopes on a heavily shared lab host. These are not production latency estimates. Source conversations, checkpoint waits and setup are additional overhead, excluded from these question means.
- The product regenerates assistant responses and real files from every original human turn. The engine replays supplied assistant messages. Product probes are themselves real conversations that can commit memory, remember or forget; engine probes are read-only. Actual earlier probe/source transcripts are supplied to the existing judge, while expected answers remain unchanged. A changed assistant suggestion may dispute gold rather than manufacture a memory failure.
- Source calendar dates are retained as metadata, while product conversations use the actual wall clock. The engine uses its lab clock. Checkpoint commits are awaited before probes, with a ten-minute ceiling: the first native checkpoint took 251 seconds; M01's final checkpoint reached the ceiling. Per-question snapshots and original provider requests are immutable. Pending commits, canceled source turns and wall-clock/date differences are disclosed rather than silently excluded.
- The real classifier remains on. General harness placement uses local authentication, host kernels, one runtime per active slot and a shared pinned OpenViking engine, rather than production container scheduling. G1/G10 disable learning, titles, LoopX and JEV as the general-task harness does; source ingestion and web search remain on. G3 enables learning and drives the native browser composer. G1/G10 explicitly warm memory tool registration; G3 uses native startup.
