# G1, G10 and G3 on the product path

Evaluation scaffolding for the November 11 campaign. The control plane, routing,
kernel, memory plugin, gateways, extraction, delivery and usage ledger are real.
The existing host-process kernel provider replaces container placement only.
No production account, deployment or serving database is used.

Run on the lab host, never the development box. `lab.sh` expects the existing
`/srv/evimed/pp` installation. Use `setsid nohup`, a distinct reserved port and
Postgres port per active slot, and `queue-slot.py` to respect the host-wide
limit of two product slots. It counts all live product slot environments,
including diagnostic harnesses, and reserves capacity while a slot starts.

All runs require `candidate.env`: lock isolation, search hint, opening index,
secret redaction, pasted-instruction checking and history retrieval v2 are on;
safety notes are off. Each attempt records these values in `provenance.json`.
The engine's actual mounted templates and image are recorded independently.
The shared balance guard stops at CNY 340 of balance decline (CNY 10 reserve)
or twelve hours from the campaign's initial snapshot. Other lanes' spend makes
that guard conservative. Account usage receipts provide attributed cost.

Order: G1, then G10, then G3. Do not start a new batch below CNY 400 balance.

## G1

`g1-select.mjs DATA OUTPUT` freezes 100 development questions: 25 each from
M01, P01, P02 and U03, one per category before taking a second, earliest
checkpoint first. The sample covers all 24 categories found in these users.
The runner sees normalized inputs and selected question ids only; gold is
confined to the separate selector and existing scorer.

`g1.mjs --tree OS --out RUN --selection SAMPLE --users M01,P01,P02`
and a second slot with `--users U03` ingest every preceding source conversation
in order, with all user turns. Assistant replies are generated by the product.
Every checkpoint question starts a new conversation. The kernel remains alive
across conversations as it does for a person. Commit settlement and memory
snapshots are read-only observations, not seeded expected answers.

These are attended simulated people on isolated, freshly registered accounts,
as in LX. An automated run is deliberately excluded from memory admission.
The initial `g1pp-eg-1` smoke incorrectly used automated turns and is invalid;
it is retained separately and excluded from scores.

Progress, stable dispatch ids, per-turn partial records, full compressed
transcripts, copied first provider requests, exact tool outputs, checkpoint
memory snapshots and usage receipts make runs resumable and reviewable.
Cancelled work is retained; resumption uses the same dispatch ids and proceeds
with the next source user turn. No earlier checkpoint is answered from a later
memory snapshot. Source times are metadata; product conversations use the real
wall clock. Replay and product assistant replies can therefore differ.

Use the existing `run/score.mjs` with the same development data and Qwen key
file; `report.mjs --suite g1 --selection SAMPLE --engine BASELINE --runs A,B
--out REPORT` restricts the comparison to the frozen 100 pairs. It reports
category, observed stage, and legacy failure-stage columns with intervals.
Legacy stages are anchor observations; opening context is not a tool retrieval.
Four users cannot establish user-population uncertainty.

## G10

`g10.mjs --tree OS --out RUN --arm empty|seeded` runs the existing general-task
cases and deterministic judges. Both arms retain the same memory plugin and
flags. The seeded arm first sends the frozen seed statements in a real prior
conversation and waits for extraction; it records what was actually retained.
Case/seed digests are verified before any model call. G06/G07 retain their
existing shared conversation and get both cases' seed sets. All 29 seed sets
are used, with normal variants only. Report paired pass, tools, input/output
tokens and their differences; do not treat an inconclusive difference as
proven non-inferiority.

## G3

`g3.mjs --tree OS --out RUN --repeats 1,2,3,4,5` uses the existing eleven
longitudinal scenarios, scoring and native browser composer driver unchanged.
`g3_host.py` changes placement to the lab's SQL and host Chromium, and serves
the integration tree's built frontend through the real control plane. Learning
is on for this suite. Each scenario registers and deletes its throwaway
accounts; failed deletion is still a failure. Scenario premises and outdated
criteria are reported rather than silently rewritten. The headline is the
share of eleven scenarios for which all five repetitions pass.

`report.mjs` uses Wilson proportion intervals and a fixed-seed paired bootstrap
for differences. Missing runs never pass. Raw data remains outside Git.
