# R17 RUN, 2026-11-10: one engine job at a time against two

Protocol: `PROTOCOL.md` (frozen before the measured runs; one amendment made after a
smoke run and before them: B1 raised from 20000 to 40000 replicates so the
batch share matched the protocol's ~90% offered load). Driver: `capacity.py`;
raw per-job rows: `results/run-20261110-{n1,n2,n1b}.json`. Box: `taskset -c 2,3`
(2 cores, shared dev box, other streams on the rest), engine at `cores=1`, R 4.3.3,
75 jobs per run, 600 s of arrivals. No paid calls, no container.

## Finding about the engine itself
There is no concurrency setting. `Engine` (`service/app.py`) starts one worker thread
and one FIFO; the docstring says concurrency is one by design until the engine has its
own compute node. The control plane's engine lane claims `jobs.maxConcurrent`
(default 1) jobs, but a single engine would still run them serially, so raising only
the control plane's number changes nothing. "Two" was therefore measured as two engine
services with separate work dirs behind a FIFO of two slots (what two containers, or a
worker count in `Engine`, would give). No product code was changed.

Reading it:
- Throughput does not move. The offered load (about 0.9 of one worker, 600 s of
  arrivals) is below one worker's capacity, so both settings drain the same
  work in the same time; this test says nothing about a saturated queue beyond that
  (that would only scale n1's waits up, and n2 would absorb it up to two jobs).
- The benefit is latency. With one worker an interactive job waits behind whichever
  batch job is running (a 2 s analytic design waited 24 s at the median). With two,
  it waits only when both slots hold a batch job (p95 wait 20 s: B1 plus B2 overlap
  each cycle). Interactive p95 fell to 0.44 of the first n1 run and 0.34 of the
  repeat; batch p95 also fell, because batch jobs stopped queueing behind each other.
- Per-job service time was not slowed by sharing the two cores (B3 17.3 s
  against 17.4 s alone, B2 25.6 s against 23 s alone, B1 41 s against ~44 s).
- The repeat of n1 was slower than the first (p95 65.5 against 50.2 s) while its
  host MemAvailable low fell to 1.4 GB: other streams were working on the box.
  The n1 to n1 spread is therefore about +-15 s p95; the n2 gain exceeds it, but
  absolute figures are not production figures.
- Memory is small: one engine peaked about 190-210 MB (service about 50 MB, a
  running R about 150 MB at these job sizes); two peaked at 377 MB PSS (417 MB RSS).
  Jobs here are small (500 patients, 40,000 replicates); a job that reads a large
  patient table, or one at the 200,000-replicate cap, will hold more, so the
  budget below is a planning figure, not a measured bound.

## Seeds
`outputHash` (the contract's hash of the canonical result) is equal for all 75
arrival indices in n1, n2 and the n1 repeat (75/75 and 75/75): the same seed gives the
same bytes with one worker and with two concurrent workers. The driver's own
`canonical` digest in the result files also hashed `jobId` and two wall-clock
diagnostics and so differed (0/75 between settings, 58/75 between the two n1 runs);
that was the digest's defect, not the engine's. `repro.py` re-ran the eight job
classes once alone and once in concurrent pairs with the same body and seed and
lists every differing path: only `jobId`, `manifest.{startedAt,finishedAt,cpuSeconds}`
and (for the two simulation classes) `diagnostics.{cpuSeconds,elapsedSeconds}`, all
wall-clock, none in `outputHash`. The driver's `canonical_hash` now drops them; the
committed result files keep the stricter old field, which should be ignored.

## Decision recommendation
Against the rule frozen in `PROTOCOL.md`: (1) interactive p95 <= half of n1: met
(0.44 and 0.34); (2) no failure, bit-identical: met; (3) batch throughput does not
fall: met; (4) memory: met on this box (about 0.4 GB for two engines peak at these
job sizes); (5) benefit holds with the two cores the box gives, not idle ones: met
here (both cores were the only ones the engine had), but not provable for the
production host, which is a shared four-core box.

Recommendation: keep production at one until the host can give the engine two
cores for itself; with that, go to two, because the numbers justify it where a
person waits on a short design behind a batch simulation. What the host would need:
- Two reserved cores for the engine (not shared with the database, runtime and web
  containers at their peaks), a memory limit of about 1.5 GB for the engine
  container(s) (measured peak 0.4 GB, headroom for large input tables and the
  200,000-replicate cap), and `VCR_ENGINE_CORES=1` per job unchanged.
- A code change, since no setting exists: either a worker count in `Engine`
  (`_run_forever` per worker thread over the same `Queue`; job state and the work
  directory are per job, but the cancel marker, checkpoint and sweep paths were
  written for one running job and need a read) or two engine containers with the
  control plane spreading jobs, plus `jobs.maxConcurrent = 2` for the engine lane.
  Not done here (outside this stream's scope).
- Not measured, and a cheaper alternative to test first: keep one worker but start
  queued interactive-class jobs (short analytic designs) ahead of queued batch jobs.
  That removes most of the interactive wait without a second core, but does nothing
  for a running 40 s job; the test above gives no number for it.
- Not measured: a fully saturated queue, three or more batch jobs at once, jobs that
  read patient tables, and any interference with the other containers on the host.
