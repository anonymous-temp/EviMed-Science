# 论文里的基线表，解析器读得对不对

这个台子回答 `population.literature` 的上游问题：**一篇论文印出来的基线表（Table 1），拿一个解析器去读，读出来的每一格有多少是对的**。它把 20 篇开放获取随机对照试验的基线表，按“变量、组别、数值”逐格和人工转写的金标准对一遍，量三种 pdfplumber 的用法和 Docling；平台自己的文档解析接口这次没能量（见“没跑成的”）。

## 先说结论

- **Docling（版面模型加 TableFormer，CPU 上跑）把 1104 格读对了 1103 格，20 篇每篇都在 98% 以上。** 唯一错的一格是 PDF 里的上标字母 `0.191ᵃ` 被读成了 `0.191 a`。
- **pdfplumber 不做任何调参时，只有带完整框线的表读得对**：默认设置下 20 篇里只有 2 篇（两张四周都有线的小表）全对，17 篇一格都没读对，另一篇读对 3%。改成按文字对齐切格子后读对 27.7%，数值落在对的行里的占 52.5%，但表头和格子对不上，也经常把一个词切成两半。
- 也就是说，**一个只会找线框、或者只会把版面文字按空格切开的解析器，读基线表会静悄悄地出错**：多数数字其实在对的行里，但归到哪一组说不准。要把论文的基线表当作 `population.literature` 的来源，用的是版面感知的表格解析器，并且按印出来的表头认组别，不要按行里数字的先后顺序。

## 怎么做的

1. **选论文。** Europe PMC 检索接口按期刊（BMJ Open、PLoS One、Trials、BMC Medicine、Nutrients、Sci Rep、BMC Cancer、Medicine、BMC Public Health、Diabetes Obes Metab、Eur J Med Res、BMC Pulm Med、BMC Geriatr、Medicina 等）找“随机对照试验、开放获取、在 PMC、署名许可”的论文；PDF、许可记录和 JATS XML 取自 PMC 开放获取数据集（AWS 上的 `pmc-oa-opendata`，纯 HTTPS，不带密钥，也不带任何联系身份）。PMC 老的 `oa.fcgi` 接口现在返回 404，Europe PMC 的 PDF 下载要先过浏览器验证（403），所以走的是这个数据集。`select_papers.py` 把 98 篇候选的 PDF 取下来，用 `pdftotext` 找哪一页有“基线特征”的表；入选 20 篇，要求表里有按组分列的数，不是受试者逐人列表（例如 PMC12787583 排除），也不是每组再分“例数/百分比”两个子列的表（例如 PMC12333169、PMC12359957、PMC12595693 排除），也不是按行分层的表（例如 PMC12409236 排除）。**这个排除本身就是一个限制：真实文献里有这些表，这个台子没有量它们。**入选论文的 PMC 编号、期刊、年份、许可、页码、PDF 的 SHA-256 在 `papers.json`；许可是 CC BY（19 篇）和 CC0（1 篇）。**PDF 不入库**，要重取，运行 `select_papers.py` 再按 `papers.json` 的 SHA-256 核对。
2. **金标准。** 每篇的基线表由我（一个语言模型）看着渲染出来的页面图，把每个有数的格子转写成 `gold/<PMC 编号>.json`：每行一个标签加各组的值，另有各列的名字和能在表头里认出这一列的关键词。**这是一个模型读页面图得来的，不是两个人独立标的；它只拿来检查解析器，不拿来证明任何别的东西。**为了查转写错误，用同一篇文章的 JATS XML 里的同一张表做了交叉核对（`xml_check.py`，XML 只用来提示、从不抄进金标准）：核出两处错，一处是把 `0.5 (0.4, 0.6)` 看成了 `0.5 (0.3, 0.6)`（PMC12587262），一处是把原文就缺的右括号补上了（`971 (46.26%`，PMC12175447，XML 和 PDF 文字层都缺），都已更正；核对后，1104 个金标准格子的值都能在对应 XML 表的文字里找到。上标的脚注符号（\*、†、‡）不算数值的一部分，两边都去掉；上标字母（如 `0.191ᵃ`）不去，被解析器压平成 `0.191a` 就算错，这对所有解析器一样。
3. **解析器。** 都没有针对任何一篇调过参：
   - `pdfplumber` 0.11.10 的三种用法：默认的 `extract_tables()`（靠线框）；两个方向都设成 `text`（靠文字对齐）；完全不找表，把整页版面文字按两个以上空格切开（没有表格识别的流水线就会这么做）。
   - Docling 2.146.0（torch 2.15 CPU 版），不做 OCR（这些 PDF 都有文字层），版面模型加 TableFormer，导出 Markdown 后取其中的表。
   - 平台自己的文档解析接口：没能量，见下。
4. **评分。** 一个解析器对一篇论文给出若干个表格（网格）；取和金标准行标签重合最多的那一个当它读这张表的结果（所以找表这一步等于由金标准代劳，量的是“读格子”，不是“在许多表里找对表”）。每个金标准格子是三元组（变量 = 行标签，组别，数值），读对的条件是**三者都对**，数值比较时只规范空白和负号/破折号：
   - **严格读对**：行按标签找到（标签重复的，如两个“Male”，按出现的先后对应；短标签要完全相等），组别按表头里的关键词找到，数值相等；这是金标准的定义。
   - **行顺序对**：不看表头，该行里非空的值按顺序和印出来的一致（量“如果按顺序归组会不会对”）。
   - **数值在对的行里**：数值在对的行的某一列里（不问是哪一列）。
   - 评分里没有任何模型：字符串相等，加行标签上一个固定的相似度阈值（`score_lib.py` 的开头写了每条规则）。

## 这对 `population.literature` 意味着什么

- 读基线表这一步，**可以做到几乎无错**，条件是用 Docling 这类版面感知的解析器；这 20 篇是 2024 到 2025 年出版社排版的有文字层的 PDF，它在所有这些版式上都读对：无竖线的开放式表、满格线的表、隔行底纹的表、跨两列的表头、两行的组名、行内两行的格子、表在双栏页的一栏里、一页里有两张表。
- 不要用“找线框”或“按空格切”这种做法来读论文表，也不要用行内数字的先后顺序去认组别；这两种做法出错时没有任何信号，一个错位的数字照样是个像样的数字。
- 读出来的表仍然要过 `population.literature` 自己的检查（例数、比例在 0 到 1 之间、均值与标准差成对出现等），这个台子没有替代那些检查。

## 这个台子没有证明什么

- **平台自己的文档解析接口的读表质量没有量**；Docling 的数字不能当作它的数字。
- 只有 20 篇、1104 格，且都是有文字层的现代 PDF、署名许可、按组分列、不分子列、不按行分层的表。**没有扫描件、表格以图片出现、横版旋转的表、跨页的表、补充材料里的表、中文论文、每个组再分“例数/百分比”两个子列的表。**
- 找表这一步由金标准代劳，所以没有量“在整篇论文里找到对的表”。
- 只量字符串读对没有；一格 `46.68 ± 10.4` 被读成 `46.68 ± 10.4`，不等于它被正确理解成均值 46.68、标准差 10.4（均值还是中位数、标准差还是标准误、百分数还是例数），那是下游的事，这里没量。
- 金标准是一个模型从页面图转写的，不是两个人独立标的；交叉核对只能查出转写错和 XML 与 PDF 不一致，查不出两边一致的错。
- pdfplumber 的三种用法是没调参的基线。认真调过或自己写了列归并的 pdfplumber 流水线会比这好，上表里“找到对的行”（文字对齐 72.5%，不找表 92.4%）和“数值在对的行里”说明信息就在那里，差的是把它归到组别上。

## 没跑成的

- **平台自己的文档解析接口。**按仓库的配置（`documentParserClient.mjs`：基址加可选的令牌文件）用仓库自己的客户端去调，已配置的测试服务器 `/health` 回 200，但客户端调的两个文档路由 `/api/v1/extract/text/file` 和 `/api/v1/parse/file` 都回 HTTP 404（Tornado 的错误回溯），没有发送任何令牌（这台机器的配置里没有令牌文件；这个解析器此前量到是不要令牌的）。所以这一行空着，不是 0 分。`run_inhouse_parser.mjs` 留着，路由恢复后用 `OPEN_SCIENCE_DOCUMENT_PARSER_URL=... node run_inhouse_parser.mjs <pdf 目录> <输出目录>` 把文本取回来，放在 `parse/inhouse/<PMC 编号>.txt` 下再运行 `evaluate.py`，评分会按文本里的 Markdown 或 HTML 表自动加上这一行。
- **Docling 的体量。**虚拟环境 1.6 GB 加模型 0.5 GB，约 2.1 GB，比要求的 2 GB 多了约 0.1 GB；当时磁盘还有空，量完即删。CPU 上 20 篇共 629 秒（2 线程，每篇 10 到 127 秒；先单独试一篇时，含加载模型共 38 秒）。

## 怎么复现

```bash
python3 select_papers.py --work /tmp/vcr-baseline-tables/pdfs      # 取 PDF、XML、许可，筛出有基线表的页
python3 -I run_pdfplumber.py /tmp/vcr-baseline-tables/pdfs /tmp/vcr-baseline-tables/parse/pdfplumber.json $(python3 -c "import json;print(*[p['pmcid'] for p in json.load(open('papers.json'))])")   # 需要 pdfplumber
python3 -I run_docling.py /tmp/vcr-baseline-tables/pdfs /tmp/vcr-baseline-tables/parse/docling      # 需要 docling 和 CPU 版 torch
python3 xml_check.py --pdfs /tmp/vcr-baseline-tables/pdfs         # 金标准与 XML 的交叉核对
python3 evaluate.py --parse /tmp/vcr-baseline-tables/parse        # 写 results.json；加 --print 打印本文的表
```

| 文件 | 作用 |
|---|---|
| `gold/*.json` | 20 张基线表的金标准（模型读页面图转写） |
| `papers.json` | 入选论文：PMC 编号、期刊、年份、许可、页码、PDF 的 SHA-256 |
| `select_papers.py` | 检索、取文件、找基线表所在的页 |
| `run_pdfplumber.py`、`run_docling.py`、`run_inhouse_parser.mjs` | 三个解析器的运行脚本 |
| `score_lib.py` | 逐格评分（规则写在文件开头） |
| `evaluate.py` | 汇总，写 `results.json`，打印表 |
| `xml_check.py` | 金标准与 JATS XML 的交叉核对 |
| `parser-status.json` | 没跑成的和为什么 |
| `results.json` | 每个解析器、每篇论文的汇总 |
