# Heart-rate task through the batch trajectory path — 2026-11-07

## Status: the path is built and checked on a synthetic fixture; the PhysioNet 2012 arm has not been run

The PhysioNet 2012 sets (A, B, C and the outcome files) and the ACTG175 table are private inputs that live on the owner's machine, not on the development box this round ran on. So the real-data numbers below are absent, not estimated. Nothing here is a result about patients.

## What was added

[hr_batch_eval.mjs](./hr_batch_eval.mjs) takes the `hr-{b,c}-paired.csv` and `hr-baseline.json` that `hr_baseline.py` already writes, builds each stay's first six hours as a frozen history with the prediction origin at hour 6 and the target at hour 24 (a horizon of 0.75 days), and runs the stays through the product's own batch path: `createForecastProviders` with a local deterministic adapter (no network, no model call), so the batching, the per-person ledger and the origin cut are the ones the platform uses, and then `evaluateForecast` for the metrics and the persistence baseline. Two arms: persistence (the last early heart rate), and the regression the engine fitted on split A, read from a predictions CSV and applied as frozen. The selection is frozen: nothing is chosen on B or C. The denominator is the whole split: the stays `hr_baseline.py` dropped for lacking an early or a 24-hour heart rate are carried in from its counts, and `submitted + dropped` is every stay. Only aggregates are written.

Command on the machine that holds the data (after `run.sh` has written the clinical directory and the engine's predictions, one `USUBJID,prediction` CSV per split):

```sh
node OpenScience/evals/vcr-professional-plugins/hr_batch_eval.mjs --clinical <clinical dir> --split b \
  --predictions <hr-pred-b predictions csv> --out <clinical dir>/hr-batch-b.json
node OpenScience/evals/vcr-professional-plugins/hr_batch_eval.mjs --clinical <clinical dir> --split c \
  --predictions <hr-pred-c predictions csv> --out <clinical dir>/hr-batch-c.json
```

## What was run here

`apps/server/test/vcrTrajectoryEval.test.mjs` (3 tests, passing): on 40 authored stays, the persistence error computed through the batch path equals the closed-form mean absolute error to 1e-9; a regression arm that equals the truth scores zero and beats persistence by point estimate; stays the adapter declines are rejected in the ledger, counted in the denominator, and reported as missing forecasts in the evaluation. A CLI smoke on 400 synthetic stays (authored linear relation, 30 stays recorded as dropped before the batch) reported submitted 400, completed 400, whole split 430, and ran both arms; those numbers describe the fixture, not heart rates.

## What the real run will and will not show

It reproduces, through the batch path, the frozen regression-against-persistence comparison of [RUN-20261105.md](./RUN-20261105.md) (B 3,748/4,000 and C 3,758/4,000 eligible stays), with the ledger and the full denominator beside it. It adds no learned parameter, no tuned threshold and no clinical-validation claim. The interval on each metric is a patient-cluster bootstrap; the adapter gives no per-prediction uncertainty, and the ledger says so.
