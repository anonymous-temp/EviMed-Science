# 修订说明（后台记录，不属于交付的筛选结果本身）

本次作业的 action 是 `screen`，冻结输入是 `method-relations-input.json`。筛选只做一件事：判断给定的配对里哪些值得花下一次更贵的阅读，并说清读者该拿什么去核对那次阅读。本文件记录这次筛选的理由、对冻结输入的核对结果，以及按契约不需要产出的东西。

## 一、输入与技能正文之间的差异（如实记录，不做补齐）

| 技能正文描述的输入 | 本次冻结输入实际带的 |
| --- | --- |
| `schemaVersion`、`action`、`jobId` | `schemaVersion`、`action`；**没有 `jobId`** |
| `methods[]`（name + description） | `pairs[]`，每条含 `a`、`b` 两个方法对象（只有 `id`、`name`、`description`） |
| `group`、`assignments`、`mountedTools` | 均无（screen 用不到） |

因此：

- 输出里的 `jobId` 记为 `null`。输入没有给出 job id，不自行编造一个写进交付物。
- 筛选单位是配对，不是「把方法分组再读」。交付物按题面逐条给出配对的保留与丢弃，同时在顶层 `pairs` 数组里对三条配对各留一条处置记录，方便逐条核对。
- 三条配对共用三个方法（`pre-submission-freeze-check`、`reporting-checklist-addressability`、`claim-verdict-audit`），按 `name` 逐对判定，没有新增、合并或改写任何配对。
- 契约里 `screened.rejected` 的每条只有一个 `method` 字段，而这里被丢弃的单位是一条配对。若把配对里的两个方法各写成一条 rejected，就会误报「这两个方法本身被搁置」——它们在别的配对里是被保留的。所以丢弃的那条写成一条 rejected 条目，`method` 记这对方法的联合名，另加 `pair` 与 `methods` 两个字段写明它指的是哪条配对。

## 二、筛选理由（读者拿它去核对正文）

判断只依据 `name` 与 `description`；这一步拿不到正文，所以保留的理由一律写成「待正文核对的假设」，不写成结论。

- **pair-1 保留** —— `pre-submission-freeze-check` 与 `reporting-checklist-addressability`。两条都落在同一份多文档交付物的最后一次通读上，且疑似互相咬合：一条在定稿前固定每个产物的副本、并要求每次保全比对都发生在两个确实不同的产物之间；另一条把内容写进一份数字、引用与标题已被冻结的文档，而它构建的正是一张表。要核对的是：先固定副本、再编辑、再比对，是否是这两条共同执行的一个具体操作（另一条的产物与编辑是否正好落进这一条的保全范围），还是两者只是同处一个环节。
- **pair-3 保留** —— `reporting-checklist-addressability` 与 `claim-verdict-audit`。两条都在同一种绑定上做工：让文档里的一个标记能解到它点名的目标，并要求那个目标确实承载所说的内容。一条负责让每一个标记点到一个读者能打开、且确实放着该内容的位置；另一条逐条判哪个引用标记解错了条目、哪个数字坐在并不承载它的来源上。要核对的是：标记到目标的解析与判定，在两边是否是同一个具体操作，还是各做各的。
- **pair-2 丢弃** —— `pre-submission-freeze-check` 与 `claim-verdict-audit`。两边只共享交付阶段的通用词汇（artefact、citation、numbers、notice 与 verdict、frozen），不共享操作；时机相反（字节冻结之前 vs 已交付之后），对象也不同（保全比对本身有没有空转、表产物是否以表头行开头 vs 每句陈述能否在它自己引的来源上站住）。找不到一个两边以同样方式执行的具体操作，读在一起只会得到一个关于交付阶段的判断。

据此，输入三条配对的处置是：保留 2 条、丢弃 1 条。三条全留等于没有筛选。

## 三、可追溯性核对（traceability-review）

契约要求这一步在不取外部来源的前提下，把每条引用回冻结输入里逐字比对。本次的执行结果：

- `method-relations.json` 的 reason 字段里出现的英文引文片段共 7 处（pair-1 两条、pair-3 两条、被丢弃的 pair-2 三条），逐字定位在冻结输入的方法描述中，全部一致；比对脚本按「去掉引文外的中文叙述后剩下的 ASCII 串」逐个在对应方法的 `description` 里查找，无一处落空。
- 对每条保留的配对，交付物里引用的两条方法描述都属于该配对的两个成员，没有跨方法引用。
- 丢弃理由里对两条方法的引文同样落在各自方法自己的描述内。
- 本次没有 `## Verification` 与 `## Constraints` 条目需要保全：screen 不读正文、不重写任何方法，`revisions` 为空。
- 交付物没有指名任何工具、脚本、文件或依赖，因此不存在「改写了来源里没有的东西」这类问题。

## 四、按契约不产出的东西，以及原因

- **不产出 `assignments`**：`assignments` 属于 `decide`。筛选不是判定，保留一个配对只是提议去读正文；在这里写出六种关系中的任何一种，都会把「便宜的一遍」变成「没读正文就下结论」。
- **不产出 `revisions`**：`revisions` 属于 `build`。没有 assignment，也就没有可执行的改写。
- **不做去 AI 味改写（manuscript-humanize）**：该步骤的适用范围是被改写的方法正文的 Purpose 段与工作流散文。本次没有任何方法正文被写出或改写，交付物里的散文只有筛选理由，按契约留在本说明与 JSON 的 reason 字段里，不进入任何方法文本，因此这一步无对象可改。等后续 `decide`/`build` 真正产出改写正文时再执行，并保留改动前的副本以便逐项回退。
- **不新增配对**：只判给定的三条。
