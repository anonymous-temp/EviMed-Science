# AGENTS.md

This file provides guidance to AI coding agents (Codex, Claude Code, etc.) working in this workspace. Assume you know nothing about the project; start here.

## What this workspace is

`EviMed Science` is the **SaaS platform monorepo**: first a general-purpose agent platform — writing, office documents, spreadsheets, slides, code, data, web research, scheduled work — and second, on top of it, a professional agent platform for medicine (循证医学 / evidence-based medicine). The medical method, vocabulary and checks load when the task or the content is medical, as enhancement and labels, never as a precondition for other work (owner, 2026-10-12). Product code lives in ordinary directories with separate stacks and toolchains. There is no root build; `cd` into the relevant subtree before running project commands.

| Path | What it is | Stack | Authoritative docs |
|---|---|---|---|
| `OpenScience/` **(production)** | Hosted SaaS — the general agent platform and its medical professional layer; where all product work happens | React · TS · Node | `OpenScience/AGENTS.md` |
| `项目代码/` (Python agents) | 6 Python AI agents consumed by the SaaS runtime, plus `knowledge-plugin/` — the knowledge-source plugin the frontier feed reads (its own service, contract and database) | Python · FastAPI / CLI | each has its own `README.md` / `CLAUDE.md` / `AGENTS.md` — read those first |
| `接口文档/` | Markdown API specs for shared capabilities | — | `.md` files in place |
| `项目代码/` (Java services) | **ARCHIVED (frozen 2026-07-24)** — 5 Spring Cloud microservices, superseded by the `OpenScience/` rewrite; untracked reference only, do not build or extend | Java 8/21 · Spring Boot · Maven | the archived section below |

**The hosted SaaS under `OpenScience/` is the production system and the single source of new product work.** It is a ground-up rewrite of the drug-evaluation capabilities that the five Java services used to provide; the Java tree is archived, not a fork to keep in sync. New evidence/evaluation logic goes into `OpenScience/` (its MCP tools, skills, and server), never back into the Java services. General capabilities — documents, spreadsheets, slides, code, data, the open web — are first-class work there as well and come before a new medical capability; and before building any piece, look for the upstream one that already does it (see “Owner decisions adopted 2026-10-12”).

Git model: the workspace root is the single authoritative repository (branch `main`, published at `https://github.com/anonymous-temp/EviMed-Science` under the MIT License — `LICENSE`, third-party notices in `NOTICE`). `OpenScience/` and the six Python specialist agents and the knowledge-source plugin under `项目代码/` are normal tracked directories, not submodules. Commit and push from the workspace root. The **five Java services are untracked as of 2026-07-24** (`.gitignore` — kept on disk for reference, out of the repo); `项目代码/scientific-agent-skills-main/` and `grok-build-main/` are ignored reference snapshots.

Working language: discussion in Chinese is fine, but **code, files, comments, and commits are English** (per `OpenScience/AGENTS.md`). When a subtree has its own `AGENTS.md`/`CLAUDE.md`, that file wins for that subtree. `CLAUDE.md` at the workspace root is the Claude-Code-variant of this file — keep them in sync when editing rules.

Architecture: the React frontend ships as a hosted web app only (the desktop shell was deleted on 2026-09-04). The agent kernel is **DeepSeek Harness (DSH)**, and it is the only one — OpenCode was deleted on 2026-09-01, with no rollback lever and no second code path to keep alive. The browser never reaches a kernel: it calls `apps/server`, which holds the one connection to the DSH kernel in that project's runtime (a container on this host, or an Alibaba AgentBay session when `OPEN_SCIENCE_RUNTIME_PROVIDER=agentbay`). That connection is a single WebSocket at `/api/remote.mux` carrying every logical stream, addressed by slashed method names (`session/create`, `session/prompt`, `session/page`, `session/cancel`, …) and authenticated by a browser-session cookie the control plane mints itself; the kernel's event feed arrives on the `$events` stream of that same socket. `apps/server` decodes those frames into `@evimed/domain`'s `RunEvent` and serves its own stream at `GET /api/runs/:id/events`, so a kernel change is not a frontend change — the old pass-through route is retired and answers 410 by name. `packages/harness-port` is the anti-corruption layer and the only package that may import `@deepseek-ai/*` (including in a JSDoc `import()` type), so a rename upstream is one file. `packages/socket` (`@evimed/dsh-socket`) is the composition layer: the `evimed-universal` preset and its plugins are what turn a bare kernel into the EviMed runtime. The pin is written once — `@deepseek-ai/dsh@0.2.1-rc.2` (with cordis 4.0.5 and a `publishedBefore` install cutoff that `scripts/ops/kernel-install.mjs cutoff` computes from the closure and a test holds equal, never typed) in `OpenScience/deps-version.json`, adopted 2026-10-17 (0.2.1 made every sub-agent a managed activation: the call returns the child's id and its result arrives as a settlement notice, which the run policy keeps inside the root's turn; the LoopX plugin runs under the kernel's exact-version exemption); 0.1.7 wrote session format 4, which 0.1.5 cannot read, so going back below 0.1.7 loses the sessions written since — and so is every bundle's beside it (the citation, annotation and Mermaid bundles, LoopX, the OpenViking memory plugin): tests assert every derived copy (Dockerfile ARG, seam manifest, peer dependency, release manifest) equals it and `apps/server/test/pinsWrittenOnce.test.mjs` fails on a version written beside a bundle's name anywhere else. Upstream is a developer preview that promises breaking changes, so adoption is decided by live-wire probing plus our own battery, never by a tag label. Safety defaults are non-negotiable: workspace-only access, and provider keys held by the control plane's gateways, never by the runtime container.

Long-running goals are **LoopX**'s (2026-10-11, PR #11): the complete upstream distribution — CLI 1.4.0 (from 1.3.1 on 2026-10-17, after real goals on the pinned kernel), the DSH plugin `dsh-loopx-plugin` 0.1.1-beta.6 and its workflow skills, Apache-2.0 — is built into the runtime image by `deploy/runtime-dsh/install-loopx.mjs` from digest-pinned archives (`deps-version.json` `loopx`) and never installed during a turn; telemetry is off. The model's skill catalogue keeps two of the eight workflow skills the CLI installs, the entry skill and `loopx-project`; the build leaves the six repository-management workflows out of the image and names them in its receipt (2026-10-17, 2,478 characters off every session's catalogue), and takes out of `loopx-project` the three pointers it keeps to the one of them it names (`loopx-doc-registry`; a digest-bound edit of that file, written back to the CLI's readback manifest, 2026-10-19). Its GoalBar (start / pause / read / watch through `loopx.goalbar`, admitted by `runtimeUiServer.mjs` like a prompt for start) and its same-session continuation driver run in the kernel; two build-time, digest-bound adaptations of the plugin's bytes (`loopx-compat.mjs`: the DSH 0.1.7 tool-role activation envelope, and a pause note to a busy model under a producer-owned source kind) are recorded with their upgrade path in `deps-version.json`. Conversation runs on two lines. The default one is a general work assistant (rewritten 2026-10-12; it began on 2026-07-26 as a medical answer line): unrouted requests are dispatched to the managed **`open-domain-answer`** agent package (`runtime/skills/evimed/open-domain-answer/`, titled Conversation, no required tool). What the conversation works with (2026-10-12/13). ### The evidence-quality gate (`apps/server/src`, the densest area of the codebase)

Most active work lands in the server boundary, and its center of gravity is not request handling but **deciding whether a finished run may be delivered**. This gate is the professional layer's: it governs the deliverables of the clinical-evidence capabilities, and an ordinary file in a general conversation meets only the advisory `file-deliverable` checks. The gate is no longer only in `apps/server` — that is the single most important thing to know about it:

- **The delivery rules exist exactly once, in `packages/domain/src/clinicalEvidence.mjs` (~3.8k lines).** They used to exist twice — on the server, and again in a 3,039-line run-side Python preflight the skill told every run to satisfy before delivering. The instruction was only honest while the two agreed, and they disagreed three times in production, each time costing a finished package. Both sides now import the same module: the run side through `evimed_submit_deliverable`, the control plane through `apps/server/src/clinicalEvidenceQuality.mjs`, which is a 31-line re-export shim holding no logic — a rule added there instead of in the domain would be invisible to the run, which is the failure that file exists to make impossible. `test/clinicalEvidenceSingleImplementation.test.mjs` asserts both entries resolve to one implementation and reach the same verdict.
- What the rules say: `validateClinicalEvidencePackage` + `citationIntegrityIssues`. Claims are typed `direct` (verbatim quote bond to one source), `synthesized` (cross-source conclusion; ≥2 preserved sources, each quoted, plus a confidence label), or `derived` (the analyst's own estimate; must name its quote-anchored inputs, method, assumptions, and sensitivities, must be marked as derived in the report, and may never carry practical safety advice). They also ban runtime/retrieval leakage — tool names, gateway names, artifact paths, first-person retrieval diaries — from report prose.
- `packages/domain/src/clinical-safety-rules.json` — drug- and scenario-specific safety rules kept **as data so pharmacists can edit them without touching server code**. Generic non-drug-specific rules stay in the `.mjs`. Add a medicine/scenario rule here, not in code.
- `apps/server/src/agentRuns.mjs` (~5.3k lines) — the run ledger and delivery decision. Records progress as observed message/tool counts change (so a run that dies in its first minute is distinguishable from one still working, instead of both waiting out the timeout), says what a run's tools could not give it as notices — one per tool, and a failure a later call of the same tool got past is not one — without letting any of it decide the verdict (2026-10-04: a tool failure never fails a run that ended on its own, so `runtime_tool_error` is no longer written; the two source-code sets stay for the run side's retry), and drives the **repair loop**: a failing package is patched in place and sent back with the specific issue, never regenerated wholesale.
- **A gate verdict never withholds a delivery (ruling of 2026-09-17).** Measured on twelve live runs: 63% of run time went to the submit/repair loop, 0 of 12 packages passed clean, and of the 52 findings that withheld them 65% were the package's own bookkeeping (coverage-ledger line numbers, run-receipt statistics, self-declared quality checks), 15% prose patterns with visible false positives, and about 10% the one thing the gate exists for — a quotation that is not in the source it names. So: `CLINICAL_CHECK_TIERS` in `clinicalEvidence.mjs` names the only checks that are `required` inside the run (`blocking`: the package cannot be read, or a reader cannot see the defect; `safety`: clinical framing), everything unnamed is advice, and the bookkeeping is gone: a package is the report and the evidence matrix, and the six files it used to keep about itself (search log, run receipt, question ledger, citation ledger, citation audit, `references.bib`) were deleted with every check that read them once the non-blocking control batch had run (memory-ablation v10) — what was searched and preserved is the platform's own record. At the end of a run what was written is delivered with `verification: "unverified"` and the findings attached — `SAFETY — ` first, then `MUST FIX — ` — and the reader sees each claim marked ✓/⚠ in the report's 「依据」 popover (`claim_verification` command → `claimVerification` in the domain). `failed` is for: nothing on disk, a runtime that died, a cancel, a spent budget, a contract this deployment no longer has, and a preserved source whose bytes changed after a tool wrote them. Server-side repair rounds are off (`OPEN_SCIENCE_GATE_REPAIR_ROUNDS`, default 0); the run still repairs inside its own turn against the same rules. Do not move a check back to withholding without a measured false-positive rate and a gate-off control (principles 4 and 11).
- The run-side `preflight.py` scripts that remain (`capabilities/*/scripts/preflight.py`) check the pre-delivery steps, not the delivery rules. Each is copied into four trees — `capabilities/`, `capability-skills/`, `runtime/skills/evimed/`, and the prepack-generated `packages/socket/capability-skills/` — and `test/capabilityPreflightCopiesAgree.test.mjs` holds the copies byte-identical, because an edit to one of them would ship a run checking itself against rules the gate no longer holds and would look exactly like nothing having happened.

Surrounding infrastructure: `runtimeManager.mjs` (~4.1k lines, the largest module — DSH container lifecycle and launch plans), `dshMux.mjs` / `dshEventPump.mjs` / `dshBrowserAuth.mjs` / `dshProfilePatch.mjs` (the kernel wire: the multiplexed WebSocket, the event decode, the minted session cookie, the generated profile patch), `runtimeControllerServer.mjs` (privileged Docker operations behind a unix socket, versioned by `RUNTIME_CONTROLLER_PROTOCOL_VERSION`), `modelGateway.mjs` (DeepSeek boundary; certifies the model that actually runs rather than the one named in source), `publicSourceGateway.mjs` (server-side DOI/Unpaywall resolution, and the web-read mode behind `web_read` — any public page, robots.txt honoured, paced per site, rendered in AgentBay's cloud browser when drawn in script, PDFs through the parser; every hop's DNS answer is checked and the socket pinned to it, and private/link-local addresses are refused before fetch; a page our own read cannot render is tried once through DeepSeek's Fetch API after those checks, labelled `via: "deepseek-fetch"` as a rendition with no byte snapshot, `OPEN_SCIENCE_WEB_READ_DEEPSEEK_FALLBACK_ENABLED`), `webSearchGateway.mjs` (the open-web search behind `web_search`: SearXNG through the Tokyo edge and the host, Qwen web search when switched on, and DeepSeek's Search API from 2026-10-17 — its dated rows lead each merge round, the control plane's key only, 5 requests a second, ¥5 per thousand under purpose `web-search`, `OPEN_SCIENCE_WEB_SEARCH_DEEPSEEK_ENABLED`; **The learning loop** (plan §5; EvoDS × ToolVerse × SkillPyramid, corrected 2026-10-24). It learns only from the researcher's own work: every dispatching driver under `scripts/` and `evals/` marks its runs `automated` (`apps/server/test/automatedDrivers.test.mjs` fails one that does not, unless it is listed with its reason), and an automated, internal, clinical-context, paused, reset, trial or incomplete-transcript run teaches nothing (`learningRefusal`; every refusal is counted). A distillation reads a **trajectory digest** (`trajectoryDigest`, pure, in `@evimed/domain`) — each turn's first request verbatim, every correction with its position, the structure fingerprint of what was delivered (`artifactShapes.mjs`), the order of the tools the run really executed (the run's `tool-trace/2` file, completed calls only; the transcript's calls when a run has none) with the platform's choreography tools removed by a closed list — and an excerpt anchored ±12 messages on each correction, where it used to read the last few dozen lines of the conversation (which were the submit-and-repair tail). Evidence has four producers (`learningEvidence.mjs`; ledger rows of trigger `learning-evidence`, one per run): what the person typed into the run, each steer read by the same judge in `steer` mode when the run ends (the newest three); a **follow-up judge** (one Flash call on their next message in the same conversation within 30 minutes, whether it came through the kernel page, the page's dispatch or a messaging channel: correction, preference, rejection, accept, `adopt` — the person asks that the way it was just done be kept — or none; the quotation checked as a substring of that message, nothing credential- or identifier-shaped kept, recognised by shape and never by a word list); `used`, the owner opening or downloading one of the run's delivered files (the files routes, the kernel pane's file panel, a result export; once per run, no words); and `silent`, a run that drew no reaction, settled by a `learning-evidence` job 30 minutes after it. `adopt` is read by few-shot judgement, never by rules over language: the judge's instructions carry fixed contrasts (「这次就这样吧」 accept, 「以后都这样」 adopt, 「记住我喜欢短的」 preference, 「格式就按这个，内容再补两条」 correction), the request carries the six examples nearest the message from a labelled bank kept as data (`packages/domain/src/follow-up-examples.json`, chosen by the knowledge base's embedder, character n-grams when it is down), a first `adopt` is asked again with the examples in the other order and stands only when both agree, and it needs a finished run that delivered something; measured on the held-out half of `evals/follow-up-judge` (precision 1.00, recall 0.93 on 2026-10-25). **Silence is unknown, not approval**: a run is clean only when it was accepted, adopted or used and never corrected (`learningRunOutcome`); a silent run teaches nothing either way. A lesson is `correction` (never sampled), `adopted` (at once, the run's way of working for the kind of work the person named), `script` (below) or `routine` — τ = 3 clean trajectories of one scope (a capability id, or the ordinary conversation) and one artifact shape within 90 days (`routineLessonFor`); the sampled `delivered` trigger and `OPEN_SCIENCE_LEARNING_DISTILL_SAMPLE_SHARE` are gone and `repair_accepted` stays at share 0. `method-distillation` (1.6.1) first splits a lesson into single rules and keeps the ones that will recur, writes a layout's places as filled only from what the person gave (a method that said 「每条先写结论，再写依据」 had later runs invent the basis, 2026-10-24), reads the eight nearest existing methods by embedding similarity (`methodSimilarity.mjs`: the knowledge base's DashScope embedder, an in-memory vector cache, a lexical fallback the result names), keeps its evidence as `provenance.evidence` quotations that are substrings of what the model was shown (from two characters for the person's own reaction — 「太长了」 is evidence — and from eight for anything else), and records the `scope`; a merge inherits each source's evidence and every project its sources were learnt in (deleting the last of them stops it), and leaves its originals in force until the merged method has cleared the harm test on its own runs, then stops them through a `supersedes` relation. A rewritten method — an amend or a merge — is replayed against up to five runs of its scope the person accepted (`methodReplay.mjs`, consolidate action `replay`: one Flash call per run, both quotations checked as substrings of what the judge was shown); two grounded contradictions roll it back to its previous text, or retire a merge that had none, restorably, with the reason `replay_regressed` (the judge's false-positive rate is read on `evals/method-replay` first). **Code skills** (`scriptLessons.mjs`): a Python program the person's runs keep carrying — taken out of a tool call by its format, normalised by Python's own parser in the runtime controller's disposable container and identified by the hash of its tree — that recurs in three runs of two conversations within 90 days queues a `script` lesson (`evimed_learning.script_uses`, kept for the window, taken by project deletion, memory reset and account deletion, in the export); the method it yields carries `scripts/` only after the disposable executor ran them and their own test (`code_skill_unverified` otherwise). A method takes effect at once and is restorable in one click. **Mount** (`learnedMethodMount.mjs`, `METHOD_MOUNT`) is per conversation, not per runtime start: candidates matching the scope, ranked by similarity to the conversation's first message, one exploration slot, the `depends_on` closure with at most one abstract and three functional methods, within the byte budget, each with its reason (`similarity`, `dependency`, `explore`, `recent`) in `_selection.json` and in the run's receipt; approving, amending, retiring or rolling back a method refreshes the running runtimes at once, and a conversation keeps the files it began with. **Counters and demotion**: a run that opened a method and was corrected, or was clean (accepted, adopted or used and not corrected), is counted against that method (`appliedCorrected` / `appliedClean`, read back from the evidence rows hourly by `methodAppliedOutcomes.mjs`, once per run); the harm test (a sequential test with the bounds of `METHOD_SCIENTIFIC_HARM_TEST`) reads them: a method whose runs were rejected four times is harmful and is stopped, a few clean runs clear it; a method whose card rode in answered runs for the work and was never opened is stopped (`never_opened`; the exploration slot is exposure, not a count), as are one superseded, one replaced by a method in force and not used, the least-used of a library over 50 (`library_cap`) and an unproven merge carried ten times unopened or unused for 14 days (`unproven_merge_expired`) — each with a stated reason, restorably; a method that names a deleted feature is refused at write (`method_stale_feature`, the closed list `retiredFeatures.mjs`). Nothing is withheld from a run on purpose to measure it. **Consolidation** (`methodConsolidation.mjs`, the hourly `sleep` and `integrate` on a new method): an embedding shortlist (each method's five nearest neighbours above a 0.50 candidate floor — provisional, 0.20 under production's closest measured pair; the result carries `topScore`, `p50` and `p90` to calibrate it), the relation brief (`method-relations` 1.1.0) only for a group whose members changed since its stamp (`learning.decided`), all six relations recorded (`shared_part`, `subset` with its `WIDER`, `merge`, `abstract_pattern`, `conflicts_with`, `supersedes` with its `REPLACES`), dependency levels written back, and a result that says what it skipped and why (`noop[]`; `open_science_learning_consolidate_noop_total{reason}`, `…_relations_total{type}`) — a pass that did nothing never reports success without a reason. Operations: `scripts/ops/learning-sweep.mjs` retires restorably what names a retired feature (a report first; `--apply`, `--restore`), `scripts/ops/official-packs.mjs` reports the starter packs and restores a stopped official method, `scripts/ops/learning-evidence-report.mjs` reads the evidence by account, and the time of an account's last learning evidence is a gauge. ## Development principles (platform-wide)

Adopted 2026-08-29 from the regex/gate root-cause review; action items and rationale in `docs/superpowers/plans/2026-08-29-development-principles-and-text-output-todo.md`. These distill the DSH spec (`docs/superpowers/specs/`) for day-to-day work; the spec stays authoritative on decisions.

1. **Place logic by capability class.** Deterministic properties (schemas, file existence, verbatim quote matching, numbers, closed vocabularies such as tool names) → code. Language judgment (intent, tone, register, prose quality) → model. "LLM never does statistics" has a twin: **regex never does language**. Both misplacements are defects.
2. **Contracts bind outputs, not inputs.** Enforcement validates deliverables against decidable contracts; behavior shaping lives in prompts/skills. Input-side keyword walls over open language never converge — do not extend them.
3. **A gate verdict is a return value** carrying specific, actionable issues the run repairs in place (compiler-style). Never silent blocking, never wholesale regeneration.
4. **Blocking points are budgeted: 6 system-wide.** A new check ships as a notice/metric first and needs an observed real-world distribution before it may block.
5. **No new open-vocabulary prose regex.** Closed-vocabulary checks (tool names derived from `toolNames.mjs`) and format checks (DOI/PMID/CLM ids) are fine; medicine/scenario rules go in `clinical-safety-rules.json`; every other register/prose judgment goes to the model-judge path — model judges, code re-verifies the checkable parts, failed verdicts are dropped, not softened. Tempted to widen a prose pattern? Write an eval case instead.
6. **Every incident becomes an eval case, not a keyword.** Evals are what make general fixes safe to attempt.
7. **Priors live in context, not control flow.** Domain knowledge goes into SKILL.md/prompts — editable text that degrades gracefully and does not cap the model — not into `if`/regex.
8. **Build to delete.** Harness scaffolding is a depreciating asset; when adding some, note which model capability would make it deletable. The moat (contract and gate rules, source catalog and private data APIs, specialist engines, capsule distillation, eval corpora) stays outside the harness.
9. **Professional workflows are capability packages** (`capability.yaml` + SKILL.md + a contract validator + ≥3 real briefs in `evals/`), not new code paths; an ordinary task needs none — its units are a skill, a tool and the general file contract, and its evaluation unit is a task family of the general baseline (`evals/general-tasks`), at least three tasks each. Internal capabilities dispatched only by a platform job (`method-distillation`, `method-relations`, and the two 循证进化 packages `tool-builder` and `evolution-scout`) are exempt from the brief rule and are evaluated by the job-level harness their ledger row names — `evals/method-quality` for the learning loop, `evals/paper-gold` for 循证进化 (`evals/acceptance-ledger.json` → `definitions.briefCount`). Write a DSH plugin only to touch a seam — the socket is the only plugin surface.
10. **Text-output layer.** (a) Channel separation: every backstage genre (revision notes, review findings, process logs) has a designated file — that is what entitles report prose to ban them. (b) Register cleanup (`manuscript-humanize`) is a final pass that keeps quotes, numbers, citations, and claim markers byte-identical; the reviewer is never the writer (fresh context). (c) Numbers are rendered artifacts, not typed prose — until "no hand-typed numbers" lands, changing any number is a sweep operation: enumerate every occurrence and every dependent derived claim, re-verify, then done.

### What "pluginize every module" means — and does not

- Pluginization is three properties, not a loader: **uniform shape** per layer (table above); **individually enable / disable / test**, with native DSH + DeepSeek conversation as the control that keeps working when a module is off; **one-line registration**, and the core never imports a feature module.
- Keep one serving DSH kernel and the `evimed-universal` composition. The control plane never imports downloaded extension code; active research installations stay read-only with HMR disabled. Platform-image bundles retain their existing exact-pin and startup-probe path.
- The owner-authorized extension center may prepare exact packages and personal skill revisions outside a full platform-image build, using native DSH inspection/installation in a bounded disposable preparer. It receives no customer workspace, production/provider credentials or serving-host socket. Activate only immutable, verified generations at the safe runtime boundary; current runs retain their recorded generation.
- Unknown community host code never enters the trusted kernel through self-service. Use admitted isolated tools, restricted viewers and native personal-skill providers, or platform-reviewed native enhancements. Qualification binds package integrity, adapter, DSH pin, image, permission profile and actual applicable SaaS tests. Source review, downloaded bytes and package self-reported health are not compatibility proof; an optional extension failure does not withhold unrelated research.
- Look first for the upstream piece that already does it (a DSH row or plugin, an official skill, a mature library, OpenViking's native engine); only when none fits, prefer DSH's public extension points in this order: tool → plugin row → preset row → skill → MCP server → storage domain. Never patch `node_modules`; if upstream must change, record reason, patch, version and upgrade path in `deps-version.json` notes.
- A tool has one responsibility; it does not bundle intent detection, planning, execution, review and the final reply. Parameters state required / optional / default / unit / range; results state fact, source, caliber, missing items and scope. Improve what the model receives before patching what it says.
- Generic tools stay independent of domain plugins: date/time, file, search and citation tools never depend on the capability catalogue, a capsule or the memory service.

### Runtime-gate discipline (principles 11–20)

11. **Native is the control.** DSH + DeepSeek without our plugins is the baseline. A plugin earns its place by measured improvement in real conversations — baseline / plugin on / plugin off, same inputs and model config, sampled more than once — not by design or unit tests.
12. **Plain questions get zero-tool answers.** No forced planning, recall, retrieval, tool quota or phase switch per turn. Tool order may follow a real data dependency (delegation needs the plan's deliverable ids; the gate needs the files) and never a staged workflow dressed as one. The retired routers and mode presets stay retired (spec D5).
13. **No whole-answer release conditions.** Length, sections, keyword presence, template conformity or year counts never gate a reply. No default second-model approval, whole-answer interception or rewrite loop; quality judges run offline in `evals/` or as notices (`review`; `coverageJudge` off by default).
14. **Engineering boundaries stay in code and never move to the model**: authentication, tenancy, data ownership, operation authorization, input validity, the path guard, budgets. A check applies to the specific read / compute / write it protects; one failed operation never blocks the rest of the conversation. Invalid compute parameters refuse that computation with a reason — never a fabricated result, never a collateral shutdown.
15. **Limits protect resources, not opinions.** Every timeout, concurrency cap and budget has a reason, a key in `config.mjs` and an observable counter, and none may silently alter the user's question. Release checks, automated tests and runtime conversation gates are three layers; fewer conversation gates never means fewer engineering checks.
16. **Prompts stay short and stable.** The persona carries roles and principles only; tool usage and domain detail live in tool descriptions, SKILL.md and knowledge resources. No per-failure prohibition, no bug list in the global prompt, no fixed tool / window / paragraph mandates. Replies use the user's language; internal fields, error codes and engine internals stay out of the body unless they help the reader.
17. **Time, subject and missing data.** One context source for the current date and time zone, injectable for tests (the runtime container is UTC — write windows in UTC or set `TZ`). Vague ranges are interpreted by the model with a stated assumption; exact calculations go to deterministic tools. Answer what is determinable, ask only for what changes the next step, never invent the missing item; a user's supplement continues the task in place.
18. **Memory is one port with provenance.** Conversation history is DSH's; long-term memory enters through the memory gateway (whose `search` carries the capsule's half) and the capsule, and nowhere else. Distinguish user statement, tool fact, assistant inference and user-confirmed conclusion — an inference never auto-promotes to a fact, except that a choice the person made in two different conversations becomes a preference (owner decision 2026-10-25); one conversation alone never promotes. Every read / write / delete carries source, owner and namespace (the source is the file's and its session's). An optional memory or knowledge service being down returns a status and the conversation continues; never fake a hit or a write.
19. **Failure keeps the partial result.** When labeling, formatting or explanation fails after a computation succeeded, the computation stands. Exceptions are traceable — never swallowed, never reported as success, never retried without bound.
20. **Five questions before any new rule, route or validation**, answered in the PR: (a) language understanding, or an exact engineering operation? (b) solvable by better data, tool results or a short instruction? (c) does it stop a question native DSH + DeepSeek could answer? (d) does it touch only the operation that needs it, or the whole conversation? (e) is there a real reproduction and a control result? No evidence, no gate.

### Verifying a conversation change

Any change to conversation behavior — persona, guidance, a socket plugin, a tool description, routing — is verified on a real DSH + DeepSeek session; mocks, HTTP 200 and `stream_end` prove nothing. Cover multi-turn follow-up, data supplement, subject switch, boundaries and tool failure, not one ideal turn. Check separately: was the tool result right, did the model use it right, did the answer address the question; also watch latency, wasted calls, repeated questions, cut-offs and continuity. Keep the actual outputs and name the code version; a targeted re-test is not a full rerun. Tests assert observable behavior, never a fixed tool order.

### Ruling: `yjh051108/dsh-routing-suite` (re-evaluated 2026-09-15; first ruled out 2026-08-24)

**Not adopted, not adapted.** Three parts: (1) `injector/` hot-injects plugin packages into a running DSH profile and hands the model `dev_inject_plugin` / `dev_reload_package` — the hosted runtime is a read-only pre-initialized profile with HMR disabled, so the mechanism is the thing we forbid; (2) `preset/router-*` classifies the first user message with keyword regex into personas and unlocks tools in four staged phases behind `phase_advance` and a `delivery_check` gate — against principles 2, 12 and 13 and spec D5 — and it is a coding-agent preset (write / edit / str_replace_editor / todo_write) built around tools we deliberately do not mount; (3) `graded/` is a mandatory brainstorm → lock → check-in → red-team protocol with another product's facts hard-coded into its injected text.
