## What this workspace is

`EviMed Science` (循证医学 / evidence-based medicine) is the **SaaS platform monorepo**. Product code lives in ordinary directories with separate stacks and toolchains. There is no root build; `cd` into the relevant subtree before running project commands.

|---|---|---|---|
| `OpenScience/` **(production)** | Hosted SaaS — the current rewrite; where all product work happens | React · TS · Node · Tauri 2 · Rust | `OpenScience/AGENTS.md` |
| `项目代码/` (Python agents) | 6 Python AI agents consumed by the SaaS runtime, plus `knowledge-plugin/` — the knowledge-source plugin the frontier feed reads (its own service, contract and database) | Python · FastAPI / CLI | each has its own `README.md` / `CLAUDE.md` / `AGENTS.md` — read those first |
| `接口文档/` | Markdown API specs for shared capabilities | — | `.md` files in place |
| `项目代码/` (Java services) | **ARCHIVED (frozen 2026-07-24)** — 5 Spring Cloud microservices, superseded by the `OpenScience/` rewrite; untracked reference only, do not build or extend | Java 8/21 · Spring Boot · Maven | the archived section below |

**The hosted SaaS under `OpenScience/` is the production system and the single source of new product work.** It is a ground-up rewrite of the drug-evaluation capabilities that the five Java services used to provide; the Java tree is archived, not a fork to keep in sync. New evidence/evaluation logic goes into `OpenScience/` (its MCP tools, skills, and server), never back into the Java services.

Git model: the workspace root is the single authoritative repository (branch `main`, cloned from `git@gitee.com:zwan7221/evimed-science.git` per the root `README.md`). `OpenScience/` and the six Python specialist agents and the knowledge-source plugin under `项目代码/` are normal tracked directories, not submodules. Commit and push from the workspace root. The **five Java services are untracked as of 2026-07-24** (`.gitignore` — kept on disk for reference, out of the repo); `项目代码/scientific-agent-skills-main/` and `grok-build-main/` are ignored reference snapshots.

Working language: discussion in Chinese is fine, but **code, files, comments, and commits are English** (per `OpenScience/AGENTS.md`). When a subtree has its own `AGENTS.md`/`CLAUDE.md`, that file wins for that subtree. `CLAUDE.md` at the workspace root is the Claude-Code-variant of this file — keep them in sync when editing rules.

Architecture: the same React frontend ships as a Tauri desktop app **or** a hosted web app (desktop is optional; the hosted SaaS is the release target). That connection is a single WebSocket at `/api/remote.mux` carrying every logical stream, addressed by slashed method names (`session/create`, `session/prompt`, `session/page`, `session/cancel`, …) and authenticated by a browser-session cookie the control plane mints itself; the kernel's event feed arrives on the `$events` stream of that same socket. `apps/server` decodes those frames into `@evimed/domain`'s `RunEvent` and serves its own stream at `GET /api/runs/:id/events`, so a kernel change is not a frontend change — the old pass-through route is retired and answers 410 by name. `packages/harness-port` is the anti-corruption layer and the only package that may import `@deepseek-ai/*` (including in a JSDoc `import()` type), so a rename upstream is one file. `packages/socket` (`@evimed/dsh-socket`) is the composition layer: the `evimed-universal` preset and its plugins are what turn a bare kernel into the EviMed runtime. The pin is written once — `@deepseek-ai/dsh@0.1.5-rc.2` in `OpenScience/deps-version.json` (the newest published; rc.1 cannot be pinned, because its own subpackage ranges resolve to rc.2) — and tests assert every derived copy (Dockerfile ARG, seam manifest, peer dependency, release manifest) equals it. Upstream is a developer preview that promises breaking changes, so adoption is decided by live-wire probing plus our own battery, never by a tag label. Safety defaults are non-negotiable: workspace-only access, manual approval mode, API keys in the OS keychain only.

Open-domain answering runs on two product lines (2026-07-26): unrouted open-domain questions are dispatched to the managed **`open-domain-answer`** agent package (`runtime/skills/evimed/open-domain-answer/`) — answers-first persona with a proportional quality floor (`skillsLoaded` + reply-prose citation hygiene; no file deliverables) — while the fifteen public capability packages (eighteen under `capabilities/`; `source-understanding`, `method-distillation` and `method-relations` are `visibility: internal` — the first dispatched only by the source pipeline, the other two only by the learning loop) keep the full file-delivery gates, reserved by `specialistRouting.mjs` for explicit report intent or named-specialty requests. `dataset-research-scoping` (2026-08-06) is the data-first entry point: a request that starts from data the researcher already holds routes there rather than to `clinical-evidence-synthesis`, which synthesizes literature and has no profiling step. The LLM fallback classifier (`specialistClassifier.mjs`) is **on by default** (`OPEN_SCIENCE_LLM_ROUTING_ENABLED`), runs only after the regex router misses, and fails safe to the answer line.

### The evidence-quality gate (`apps/server/src`, the densest area of the codebase)

Most active work lands in the server boundary, and its center of gravity is not request handling but **deciding whether a finished run may be delivered**. The gate is no longer only in `apps/server` — that is the single most important thing to know about it:

- **The delivery rules exist exactly once, in `packages/domain/src/clinicalEvidence.mjs` (~3.8k lines).** They used to exist twice — on the server, and again in a 3,039-line run-side Python preflight the skill told every run to satisfy before delivering. The instruction was only honest while the two agreed, and they disagreed three times in production, each time costing a finished package. Both sides now import the same module: the run side through `evimed_submit_deliverable`, the control plane through `apps/server/src/clinicalEvidenceQuality.mjs`, which is a 31-line re-export shim holding no logic — a rule added there instead of in the domain would be invisible to the run, which is the failure that file exists to make impossible. `test/clinicalEvidenceSingleImplementation.test.mjs` asserts both entries resolve to one implementation and reach the same verdict.
- What the rules say: `validateClinicalEvidencePackage` + `citationIntegrityIssues`. Claims are typed `direct` (verbatim quote bond to one source), `synthesized` (cross-source conclusion; ≥2 preserved sources, each quoted, plus a confidence label), or `derived` (the analyst's own estimate; must name its quote-anchored inputs, method, assumptions, and sensitivities, must be marked as derived in the report, and may never carry practical safety advice). They also ban runtime/retrieval leakage — tool names, gateway names, artifact paths, first-person retrieval diaries — from report prose.
- `packages/domain/src/clinical-safety-rules.json` — drug- and scenario-specific safety rules kept **as data so pharmacists can edit them without touching server code**. Generic non-drug-specific rules stay in the `.mjs`. Add a medicine/scenario rule here, not in code.
- `apps/server/src/agentRuns.mjs` (~5.3k lines) — the run ledger and delivery decision. Records progress as observed message/tool counts change (so a run that dies in its first minute is distinguishable from one still working, instead of both waiting out the timeout), classifies source failures via `recoverableEvidenceSourceErrorCodes` / `terminalEvidenceSourceErrorCodes`, and drives the **repair loop**: a failing package is patched in place and sent back with the specific issue, never regenerated wholesale.
- **A gate verdict never withholds a delivery (ruling of 2026-09-17).** Measured on twelve live runs: 63% of run time went to the submit/repair loop, 0 of 12 packages passed clean, and of the 52 findings that withheld them 65% were the package's own bookkeeping (coverage-ledger line numbers, run-receipt statistics, self-declared quality checks), 15% prose patterns with visible false positives, and about 10% the one thing the gate exists for — a quotation that is not in the source it names. So: `CLINICAL_CHECK_TIERS` in `clinicalEvidence.mjs` names the only checks that are `required` inside the run (`blocking`: the package cannot be read, or a reader cannot see the defect; `safety`: clinical framing), everything unnamed is advice, and the bookkeeping is gone: a package is the report and the evidence matrix, and the six files it used to keep about itself (search log, run receipt, question ledger, citation ledger, citation audit, `references.bib`) were deleted with every check that read them once the non-blocking control batch had run (memory-ablation v10) — what was searched and preserved is the platform's own record. At the end of a run what was written is delivered with `verification: "unverified"` and the findings attached — `SAFETY — ` first, then `MUST FIX — ` — and the reader sees each claim marked ✓/⚠ in the report's 「依据」 popover (`claim_verification` command → `claimVerification` in the domain). `failed` is for: nothing on disk, a runtime that died, a cancel, a spent budget, a contract this deployment no longer has, and a preserved source whose bytes changed after a tool wrote them. Server-side repair rounds are off (`OPEN_SCIENCE_GATE_REPAIR_ROUNDS`, default 0); the run still repairs inside its own turn against the same rules. Do not move a check back to withholding without a measured false-positive rate and a gate-off control (principles 4 and 11).
- The run-side `preflight.py` scripts that remain (`capabilities/*/scripts/preflight.py`) check the pre-delivery steps, not the delivery rules. Each is copied into four trees — `capabilities/`, `capability-skills/`, `runtime/skills/evimed/`, and the prepack-generated `packages/socket/capability-skills/` — and `test/capabilityPreflightCopiesAgree.test.mjs` holds the copies byte-identical, because an edit to one of them would ship a run checking itself against rules the gate no longer holds and would look exactly like nothing having happened.

Surrounding infrastructure: `runtimeManager.mjs` (~4.1k lines, the largest module — DSH container lifecycle and launch plans), `dshMux.mjs` / `dshEventPump.mjs` / `dshBrowserAuth.mjs` / `dshProfilePatch.mjs` (the kernel wire: the multiplexed WebSocket, the event decode, the minted session cookie, the generated profile patch), `runtimeControllerServer.mjs` (privileged Docker operations behind a unix socket, versioned by `RUNTIME_CONTROLLER_PROTOCOL_VERSION`), `modelGateway.mjs` (DeepSeek boundary; certifies the model that actually runs rather than the one named in source), `publicSourceGateway.mjs` (server-side DOI/Unpaywall resolution, and the web-read mode behind `web_read` — any public page, robots.txt honoured, paced per site, rendered in AgentBay's cloud browser when drawn in script, PDFs through the parser; every hop's DNS answer is checked and the socket pinned to it, and private/link-local addresses are refused before fetch), `controlPlaneDatabase.mjs` (Postgres pool), `memoryIntelligence.mjs` (extraction/recall over `researchMemory.mjs`, the control plane's own memory store).

Memory is one shape (2026-09-11): research-memory notes and structured records are rows in the control plane's PostgreSQL schema `evimed_memory` behind `apps/server/src/researchMemory.mjs`, imported once out of the retired usememos tables; memory capsules stay in `evimed_product`. ## Development principles (platform-wide)

Adopted 2026-08-29 from the regex/gate root-cause review; action items and rationale in `docs/superpowers/plans/2026-08-29-development-principles-and-text-output-todo.md`. These distill the DSH spec (`docs/superpowers/specs/`) for day-to-day work; the spec stays authoritative on decisions.

1. **Place logic by capability class.** Deterministic properties (schemas, file existence, verbatim quote matching, numbers, closed vocabularies such as tool names) → code. Language judgment (intent, tone, register, prose quality) → model. "LLM never does statistics" has a twin: **regex never does language**. Both misplacements are defects.
2. **Contracts bind outputs, not inputs.** Enforcement validates deliverables against decidable contracts; behavior shaping lives in prompts/skills. Input-side keyword walls over open language never converge — do not extend them.
3. **A gate verdict is a return value** carrying specific, actionable issues the run repairs in place (compiler-style). Never silent blocking, never wholesale regeneration.
4. **Blocking points are budgeted: 6 system-wide.** A new check ships as a notice/metric first and needs an observed real-world distribution before it may block.
5. **No new open-vocabulary prose regex.** Closed-vocabulary checks (tool names derived from `toolNames.mjs`) and format checks (DOI/PMID/CLM ids) are fine; medicine/scenario rules go in `clinical-safety-rules.json`; every other register/prose judgment goes to the model-judge path — model judges, code re-verifies the checkable parts, failed verdicts are dropped, not softened. Tempted to widen a prose pattern? Write an eval case instead.
6. **Every incident becomes an eval case, not a keyword.** Evals are what make general fixes safe to attempt.
7. **Priors live in context, not control flow.** Domain knowledge goes into SKILL.md/prompts — editable text that degrades gracefully and does not cap the model — not into `if`/regex.
8. **Build to delete.** Harness scaffolding is a depreciating asset; when adding some, note which model capability would make it deletable. The moat (contract and gate rules, source catalog and private data APIs, specialist engines, capsule distillation, eval corpora) stays outside the harness.
9. **New features are capability packages** (`capability.yaml` + SKILL.md + a contract validator + ≥3 real briefs in `evals/`), not new code paths. Write a DSH plugin only to touch a seam — the socket is the only plugin surface.
10. **Text-output layer.** (a) Channel separation: every backstage genre (revision notes, review findings, process logs) has a designated file — that is what entitles report prose to ban them. (b) Register cleanup (`manuscript-humanize`) is a final pass that keeps quotes, numbers, citations, and claim markers byte-identical; the reviewer is never the writer (fresh context). (c) Numbers are rendered artifacts, not typed prose — until "no hand-typed numbers" lands, changing any number is a sweep operation: enumerate every occurrence and every dependent derived claim, re-verify, then done.

### What "pluginize every module" means — and does not

- Pluginization is three properties, not a loader: **uniform shape** per layer (table above); **individually enable / disable / test**, with native DSH + DeepSeek conversation as the control that keeps working when a module is off; **one-line registration**, and the core never imports a feature module.
- No second kernel, no second composition, no runtime code loading in the control plane or the hosted runtime. A third-party DSH bundle enters through the `dsh-cite` path (`pluginService.mjs`: pinned version, build-smoke, nightly matrix, recorded in `plugin-support.json`) — never a hot-injected package.
- Prefer DSH's public extension points in this order: tool → plugin row → preset row → skill → MCP server → storage domain. Never patch `node_modules`; if upstream must change, record reason, patch, version and upgrade path in `deps-version.json` notes.
- A tool has one responsibility; it does not bundle intent detection, planning, execution, review and the final reply. Parameters state required / optional / default / unit / range; results state fact, source, caliber, missing items and scope. Improve what the model receives before patching what it says.
- Generic tools stay independent of domain plugins: date/time, file, search and citation tools never depend on the capability catalogue, a capsule or the memory service.

### Runtime-gate discipline (principles 11–20)

11. **Native is the control.** DSH + DeepSeek without our plugins is the baseline. A plugin earns its place by measured improvement in real conversations — baseline / plugin on / plugin off, same inputs and model config, sampled more than once — not by design or unit tests.
12. **Plain questions get zero-tool answers.** No forced planning, recall, retrieval, tool quota or phase switch per turn. Tool order may follow a real data dependency (delegation needs the plan's deliverable ids; the gate needs the files) and never a staged workflow dressed as one. The retired routers and mode presets stay retired (spec D5).
13. **No whole-answer release conditions.** Length, sections, keyword presence, template conformity or year counts never gate a reply. No default second-model approval, whole-answer interception or rewrite loop; quality judges run offline in `evals/` or as notices (`review`; `coverageJudge` off by default).
14. **Engineering boundaries stay in code and never move to the model**: authentication, tenancy, data ownership, operation authorization, input validity, the path guard, budgets. A check applies to the specific read / compute / write it protects; one failed operation never blocks the rest of the conversation. Invalid compute parameters refuse that computation with a reason — never a fabricated result, never a collateral shutdown.
15. **Limits protect resources, not opinions.** Every timeout, concurrency cap and budget has a reason, a key in `config.mjs` and an observable counter, and none may silently alter the user's question. Release checks, automated tests and runtime conversation gates are three layers; fewer conversation gates never means fewer engineering checks.
16. **Prompts stay short and stable.** The persona carries roles and principles only; tool usage and domain detail live in tool descriptions, SKILL.md and knowledge resources. No per-failure prohibition, no bug list in the global prompt, no fixed tool / window / paragraph mandates. Replies use the user's language; internal fields, error codes and engine internals stay out of the body unless they help the reader.
17. **Time, subject and missing data.** One context source for the current date and time zone, injectable for tests (the runtime container is UTC — write windows in UTC or set `TZ`). Vague ranges are interpreted by the model with a stated assumption; exact calculations go to deterministic tools. Answer what is determinable, ask only for what changes the next step, never invent the missing item; a user's supplement continues the task in place.
18. **Memory is one port with provenance.** Conversation history is DSH's; long-term memory enters through `memorySubstrate` / the capsule and nowhere else. Distinguish user statement, tool fact, assistant inference and user-confirmed conclusion — an inference never auto-promotes to a fact. Every read / write / delete carries source, owner and namespace. An optional memory or knowledge service being down returns a status and the conversation continues; never fake a hit or a write.
19. **Failure keeps the partial result.** When labeling, formatting or explanation fails after a computation succeeded, the computation stands. Exceptions are traceable — never swallowed, never reported as success, never retried without bound.
20. **Five questions before any new rule, route or validation**, answered in the PR: (a) language understanding, or an exact engineering operation? (b) solvable by better data, tool results or a short instruction? (c) does it stop a question native DSH + DeepSeek could answer? (d) does it touch only the operation that needs it, or the whole conversation? (e) is there a real reproduction and a control result? No evidence, no gate.

### Verifying a conversation change

Any change to conversation behavior — persona, guidance, a socket plugin, a tool description, routing — is verified on a real DSH + DeepSeek session; mocks, HTTP 200 and `stream_end` prove nothing. Cover multi-turn follow-up, data supplement, subject switch, boundaries and tool failure, not one ideal turn. Check separately: was the tool result right, did the model use it right, did the answer address the question; also watch latency, wasted calls, repeated questions, cut-offs and continuity. Keep the actual outputs and name the code version; a targeted re-test is not a full rerun. Tests assert observable behavior, never a fixed tool order.

### Ruling: `yjh051108/dsh-routing-suite` (re-evaluated 2026-09-15; first ruled out 2026-08-24)

**Not adopted, not adapted.** Three parts: (1) `injector/` hot-injects plugin packages into a running DSH profile and hands the model `dev_inject_plugin` / `dev_reload_package` — the hosted runtime is a read-only pre-initialized profile with HMR disabled, so the mechanism is the thing we forbid; (2) `preset/router-*` classifies the first user message with keyword regex into personas and unlocks tools in four staged phases behind `phase_advance` and a `delivery_check` gate — against principles 2, 12 and 13 and spec D5 — and it is a coding-agent preset (write / edit / str_replace_editor / todo_write) built around tools we deliberately do not mount; (3) `graded/` is a mandatory brainstorm → lock → check-in → red-team protocol with another product's facts hard-coded into its injected text. Its DSH range covers our pin, but its seams (`agent/inbox/claimed`, `system-prompt/assemble`, `tools.restrict`) are not in `seam-manifest.json`. Borrowed as pattern only: `injector/docs/SPEC.md` is a good source-level account of the cordis entry / fiber lifecycle for `seam-probe` and `dshProfilePatch` work; the first-turn prefill cost (tool catalogue size and description length are the price of the first request — keep schemas short, details in results); near-field guidance injected on `agent/pre-step` in the same request rather than a second inbox message, which `run-policy` already does.
